# ADR-019: Orchestration over choreography — Game service owns the bet saga FSM

**Status**: Accepted
**Date**: 2026-05-27
**Phase**: 5

## Context

Phase 5 introduces the first true cross-service flow in the system: a player places a bet, the Game service must reserve the funds in the Wallet service, and the bet must transition `PENDING → ACTIVE` (on debit success) or `PENDING → REFUNDED` (on `InsufficientFunds`) or `PENDING → REFUNDED` (on timeout). The flow spans at least three distinct steps — `Bet.PENDING` + `wallet.command.debit` published in one Postgres TX, Wallet processing the debit and emitting `wallet.event.debited` / `wallet.event.debit_rejected`, Game's inbox handler transitioning the Bet — and adds branching the messaging-spine cannot express on its own: insufficient-funds short-circuit, `SAGA_TIMEOUT_MS=5000` auto-refund, and compensation when a late `wallet.event.debited` arrives after the saga has already timed out (must issue `wallet.command.credit` to undo the debit).

REQ-SAGA-01 specifies the two-step saga shape (Game → Wallet debit → Game `bet.active` or `bet.refunded`), REQ-SAGA-02 demands persistent saga state surviving `kill -9`, and REQ-SAGA-03 demands the 5-second timeout with auto-refund. ADR-013 already locked `@IdempotentSubscribe` propagating the transactional `EntityManager` to handlers, so cross-service handler writes commit in a single Postgres TX (inbox claim + aggregate mutation + outbox row) — but the FSM that decides "what does Bet transition to given the inbound event?" is not a messaging concern, it is a domain orchestration concern.

The microservices.io saga literature converges on two patterns: choreography (each service publishes events; downstream services react; no central state) and orchestration (one service owns the saga FSM and emits commands; participants are passive). The Phase 5 research (`05-RESEARCH.md` §"Architectural Responsibility Map" + §"Pattern 1") flags ≥3-step + branching + timeout + compensation as the canonical orchestration-over-choreography trigger. The bet placement saga ticks every box.

Phase 4 already locked the Bet aggregate as own-aggregate (ADR-014) with the per-bet micro-TX sweep pattern; the saga's FSM transitions must thread through that same single-row TX discipline (no Round-lock dependency, no parent-aggregate hydration to mutate a child Bet). Phase 9's leaderboard projector will be choreography (read-only projection consuming `game.events`), so the choreography-vs-orchestration choice is per-flow, not per-system.

Three saga-coordination shapes were on the table at the Plan 05-03 design point.

## Considered

- **Option A — Choreography (each service reacts to events; no central FSM)** — Game emits `bet.placed`, Wallet listens, Wallet emits `wallet.debited` or `wallet.debit_rejected`, Game's downstream listener transitions the Bet. No `bet_saga_state` table — saga progress is implicit in the events that have flowed. Pros: loosest coupling between services; each service knows only its own bounded context. Cons: the timeout and compensation logic must be expressed somewhere — and with no central FSM, the natural place is "poll both sides every N seconds and reconcile." That is exactly the kind of distributed-FSM-by-polling that 05-RESEARCH §Pitfalls calls out as the saga anti-pattern. "If Wallet didn't reply in 5s, refund" cannot be expressed locally — you need to know what Wallet did AND what Game did to decide whether to compensate or to wait. Restart recovery (REQ-GAME-09 + REQ-SAGA-02) becomes "scan inboxes and outboxes on both sides and reconstruct intent" — un-testable, un-observable, indefensible at arguição. The pattern is correct for read-model projections (Phase 9 leaderboard) but wrong for write-side workflows.
- **Option B — Orchestration in Game service (chosen)** — Game owns the saga FSM via `bet_saga_state` (`games-service` DB), Game emits `wallet.command.debit` (imperative command, not event), Wallet is a passive participant that processes the command and emits the corresponding event back. Game's `WalletDebitedHandler` / `WalletDebitRejectedHandler` consume Wallet's events and transition the saga state machine (`DEBIT_PENDING → CONFIRMED | TIMED_OUT | COMPENSATED`) inside the per-bet micro-TX. The `SagaTimeoutSweeper` (Plan 05-07) is the timeout driver — recursive `setTimeout` per ADR-017, `OnApplicationBootstrap` per research Pitfall 5, `FOR UPDATE SKIP LOCKED` claim of expired DEBIT_PENDING rows. Pros: single source of truth for saga progress (`bet_saga_state` row); timeout + compensation logic is local to one service; `@IdempotentSubscribe` + ADR-013 `txEm` propagation lets handler transitions commit in a single TX (inbox claim + bet mutation + saga mutation + outbox row); restart recovery is "find DEBIT_PENDING sagas past deadline, refund" — one SQL query at boot + the timeout sweeper continuing to run; defensible at arguição because the FSM is testable in isolation (Plan 05-09 integration scenarios prove every transition). Cons: Game owns the cross-service workflow — defensible because the bet IS a Game-domain concept (Wallet's only role is ledger bookkeeping); requires the `bet_saga_state` table + EntitySchema + repository + aggregate, a non-trivial chunk of code shipped in Plan 05-03.
- **Option C — Separate orchestrator service (third service whose only job is to drive sagas)** — `saga-service` owns `bet_saga_state`, consumes events from both Game and Wallet, emits commands to both. Pros: cleanest separation; Game and Wallet remain bounded contexts ignorant of the workflow. Cons: scope inflation — another NestJS deployable, another Postgres database, another set of migrations, another set of outbox/inbox tables, another set of smoke probes; the bet is conceptually a Game-domain concept (Round.acceptBet enforces the FSM at the aggregate boundary per Plan 05-01), so factoring the saga out of Game introduces a fictitious bounded context whose only entity is the saga row. At challenge scale (single recruiter arguição, not multi-team Conway's-Law constraints) the cost-benefit is upside-down — Phase 10 explicitly documents this as the scale-out path if the project ever grew, but does not implement it.

## Decision

**Option B — orchestration in the Game service.** Game service owns `bet_saga_state` (`services/games/src/domain/bet-saga-state.aggregate.ts`, persisted in `bet_saga_state` table via Plan 05-03 migration). The saga FSM is:

```
DEBIT_PENDING ──wallet.debited──▶ CONFIRMED        (Bet.confirm() → ACTIVE; outbox bet.active)
              ──wallet.debit_rejected──▶ REJECTED  (Bet.refund(INSUFFICIENT_FUNDS); outbox bet.refunded)
              ──deadline_expired──▶ TIMED_OUT      (Bet.refund(SAGA_TIMEOUT); outbox bet.refunded)
TIMED_OUT     ──wallet.debited (late)──▶ COMPENSATED (outbox wallet.command.credit; restore balance)
```

The four canonical state-machine transitions live in the saga aggregate (`bet-saga-state.aggregate.ts`); the inbound transition triggers come from `@IdempotentSubscribe` handlers (`WalletDebitedHandler`, `WalletDebitRejectedHandler` — Plan 05-05) and the `SagaTimeoutSweeper` background driver (Plan 05-07). Wallet is a passive participant — it processes `wallet.command.debit` / `wallet.command.credit` commands and emits `wallet.event.debited` / `wallet.event.debit_rejected` events; it has no knowledge of the saga or the Bet.

Cross-aggregate consistency for the per-handler TX threads ADR-013's `txEm` through four writes: inbox claim row, Bet aggregate UPDATE, BetSagaState aggregate UPDATE, outbox row. All four commit in a single Postgres TX or none do — the at-least-once-delivery + exactly-once-processing guarantee from Phase 2 carries through.

Restart recovery (REQ-GAME-09 + REQ-SAGA-02) is owned by the `SagaTimeoutSweeper` running on every node: at `OnApplicationBootstrap` (Phase 4 Pitfall 5 — fires after MikroORM connect), the sweeper begins its recursive-`setTimeout` cycle (ADR-017 pattern); each tick claims up to 100 expired `DEBIT_PENDING` rows via `SELECT ... FROM bet_saga_state WHERE status='DEBIT_PENDING' AND deadline_at < now() FOR UPDATE SKIP LOCKED LIMIT 100` and refunds them in per-bet micro-TXs. No "scan inboxes and outboxes on both sides and reconstruct" — the saga state IS the recovery oracle.

Justified by microservices.io guidance ("orchestration is appropriate when the saga has ≥3 steps with branching") + the bet's identity as a Game-domain concept (the `Bet` aggregate per ADR-014 lives in `services/games/src/domain/`, never crosses the service boundary) + the per-handler-TX guarantee from ADR-013 (`txEm` threading) + Phase 10's documented scale-out path (extract orchestrator to a separate service if and only if multi-team Conway's-Law pressure ever requires it).

## Consequences

- **Locked in (saga ownership)**: Game service is the orchestrator; `bet_saga_state` table is the single source of truth for bet saga progress. Wallet service stays passive — it processes commands, emits events, never reasons about saga state. The same shape applies to any future cross-service write workflow (e.g., a hypothetical "tournament prize claim" saga would also live in the originating service).
- **Locked in (FSM transitions)**: the four canonical transitions (`DEBIT_PENDING → CONFIRMED | REJECTED | TIMED_OUT | COMPENSATED`) are exhaustively enumerated; new states require an ADR amendment. Plan 05-09 integration tests cover every transition (place-bet, insufficient-funds, timeout, compensation via AMQP binding manipulation, cashout, double-cashout, true-SIGKILL drill).
- **Locked in (TX boundary)**: every state-machine transition commits via ADR-013's `txEm`-threaded handler signature — inbox + Bet + saga + outbox in one Postgres TX. Cross-service consistency is at-least-once-delivery + exactly-once-processing per Phase 2; the saga FSM is the cross-aggregate consistency boundary, not a multi-aggregate TX.
- **Locked in (DI shape — `@Global()` MessagingSpineModule)**: P5.10 surfaced a DI defect introduced at P5.04: `GameCoreModule` (child of `AppModule`) could not see `OutboxRepository` injected into `PlaceBetUseCase` / `CashOutUseCase` / `SagaTimeoutSweeper` / handlers because `MessagingSpineModule` was registered without `@Global()`, so its provider closure was visible only to its direct importer (`AppModule`). The fix (commit `a7ee5e2`) adds `@Global()` to `MessagingSpineModule` and re-exports the four canonical providers — `OutboxRepository`, `InboxRepository`, `DeadLetterRepository`, `MikroOrmModule.forFeature(...)`. Any future feature module that injects spine repositories (saga handlers, projector handlers, FE-facing read use cases) inherits the global visibility — no per-module re-import required. Documented in `packages/messaging-spine/README.md` as a public contract of the module.
- **Locked in (timeout driver — recursive `setTimeout`)**: `SagaTimeoutSweeper` uses recursive `setTimeout` per ADR-017 (NOT `setInterval`, per research Pitfall 6); each tick claims up to 100 expired rows via `FOR UPDATE SKIP LOCKED` so multiple sweeper instances (in a hypothetical multi-node future) would not double-refund the same bet. Single-node scope documented per ADR-017's `pg_try_advisory_lock` scale-out path.
- **Locked in (saga is per-flow, not per-system)**: Phase 9 leaderboard remains choreography (projector consumes `game.events`, no central state). The choreography-vs-orchestration choice is a per-flow design decision, not a system-wide architectural style. ADR-019 covers the bet saga; future write-side cross-service workflows would need their own ADRs to opt into orchestration.
- **Foreclosed**: Option A choreography for bet placement (would require distributed-FSM-by-polling; un-testable; restart recovery becomes a reconciliation algorithm); Option C separate orchestrator service (scope inflation; fictitious bounded context; Phase 10 documents as scale-out path only).
- **Operational cost**: one extra Postgres table (`bet_saga_state`) per Game service instance; one extra background worker (`SagaTimeoutSweeper`); ~µs per saga step for inbox lookup + UPDATE; negligible vs the round-trip cost of any other layer.
- **Test surface**: Plan 05-09 ships 7 integration scenarios (place-bet, insufficient-funds, bet-outside-betting, timeout, compensation via AMQP binding manipulation, cashout, double-cashout) plus the true-SIGKILL drill (`docker compose kill -s SIGKILL games`); Plan 05-10 ships smoke probes 33-38 with the live saga trace captured in `bet_saga_state` proving the FSM end-to-end against the production DB.
- **Anticipated recruiter question**: "Why not choreography? Isn't that the canonical microservices saga shape?" — defended by the ≥3-step + branching + timeout + compensation argument (microservices.io guidance), the bet's identity as a Game-domain concept, and the testability + observability of `bet_saga_state` as the single FSM source of truth.
- **Anticipated recruiter question**: "What if Game and Wallet are owned by different teams in a real org?" — defended by Phase 10's documented scale-out path: extract `saga-service` as a third bounded context if and only if Conway's-Law team boundaries ever require it; at challenge scale (single recruiter arguição) the cost-benefit is upside-down.
- **Anticipated recruiter question**: "Why did `@Global()` only land in P5.10 and not P5.04 when the spine was first wired?" — defended honestly: the spine was extracted in Phase 2 with both services importing it once each (AppModule directly), so non-global visibility was sufficient through Phase 4; Phase 5 was the first time a feature module (`GameCoreModule`) needed to inject saga handlers that depend on `OutboxRepository`, surfacing the gap. The fix is forward-compatible — any future feature module inherits global visibility — and the defect was caught at live integration (P5.10) before any green-field code shipped.

Cross-references: ADR-013 (`@IdempotentSubscribe` `txEm` propagation — the per-handler-TX foundation this ADR builds on); ADR-014 (Bet-as-own-aggregate — the per-bet micro-TX sweep pattern carries through); ADR-017 (recursive `setTimeout` + `OnApplicationBootstrap` — reused verbatim by `SagaTimeoutSweeper`).

## Alternatives Rejected

- **Option A — Choreography (each service reacts to events; no central FSM)** — timeout + compensation logic distributed across services; restart recovery becomes a reconciliation algorithm; un-testable + un-observable + indefensible at arguição; correct for read-model projections (Phase 9) but wrong for write-side workflows.
- **Option C — Separate orchestrator service (third bounded context)** — scope inflation (another deployable, another DB, another migration set); fictitious bounded context whose only entity is the saga row; bet is conceptually a Game-domain concept; documented in Phase 10 as the scale-out path if Conway's-Law team boundaries ever require it, not implemented at challenge scale.
