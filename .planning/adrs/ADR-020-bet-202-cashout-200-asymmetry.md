# ADR-020: Bet placement asymmetry — `202 Accepted` for bet, synchronous `200 OK` for cashout

**Status**: Accepted
**Date**: 2026-05-27
**Phase**: 5

## Context

Phase 5 ships the two REST mutation endpoints that Phase 4 deliberately deferred: `POST /games/bet` (REQ-GAME-06) and `POST /games/bet/cashout` (REQ-GAME-07). Both endpoints are the player's only write surface against the game core; their response semantics propagate forward to Phase 6 (WS gateway pushes `bet:active` / `bet:cashed_out` to the lobby), Phase 7 (FE bet panel UX between request and confirmation), and Phase 9 (auto-features need to know when a bet has "really" landed).

The two operations look superficially symmetric — both touch the Bet aggregate, both involve money — but their workflow shapes are fundamentally different.

**Bet placement** crosses the Game ↔ Wallet service boundary. Per ADR-019, the bet saga is orchestrated: Game writes `Bet(PENDING)` + `bet_saga_state(DEBIT_PENDING)` + outbox `wallet.command.debit` in a single Postgres TX; the OutboxPublisher ships the command via RabbitMQ; Wallet's `WalletDebitHandler` processes it (atomic UPDATE + Transaction append + outbox `wallet.event.debited` or `wallet.event.debit_rejected`); Wallet's OutboxPublisher ships the event back; Game's `WalletDebitedHandler` transitions the saga (`Bet.confirm()` → `ACTIVE`, outbox `bet.active`). The round-trip is at minimum two AMQP hops + two Postgres TX commits + two OutboxPublisher poll cycles. Best-case observed latency in P5.10 live trace: ~2 seconds from `POST /games/bet` to `bet.active` outbox publication.

**Cashout** is a single-service decision in Game. Per REQ-SAGA-04, Game atomically transitions `Bet → CASHED_OUT` + writes the payout outbox row; Wallet credit is downstream bookkeeping that the player never waits for. The cashout decision (multiplier-at-acceptedAt) is computed synchronously inside the controller before any await per REQ-WS-05 (server-clock authority). One Postgres TX, no AMQP round-trip on the request path.

REQ-DOM-02 enforces single-bet-per-player-per-round at the DB (partial unique index `bets_one_active_per_player`); REQ-DOM-01 enforces the Round FSM at the aggregate boundary; REQ-WS-05 demands server-clock-stamped `cashoutAcceptedAt` before any await. These three invariants constrain the response-shape choice but do not dictate it — the choice is about UX latency and the at-least-once-delivery contract from Phase 2.

The choice is also constrained by Bustabit / Aviator-style product expectations: a player tapping "Bet" expects the bet to appear in the live feed "instantly" (sub-second), but understands that confirmation might lag; a player tapping "Cashout" expects the payout figure on screen immediately (the multiplier is climbing, the freeze-overlay-on-crash UX in Phase 7 requires the cashout figure to be known synchronously to drive the celebration animation).

Three response-shape combinations were on the table at Plan 05-04 / Plan 05-06 design time.

## Considered

- **Option A — Both endpoints synchronous (`200 OK`)** — `POST /games/bet` blocks the HTTP request until `wallet.event.debited` or `wallet.event.debit_rejected` lands in Game's inbox; `POST /games/bet/cashout` returns synchronously as today. Pros: simplest client semantics (one shape for both endpoints, REST orthodoxy). Cons: the bet request thread is held across at-least-two AMQP hops + two Postgres TX commits + two OutboxPublisher poll cycles — best-case 2s, worst-case `SAGA_TIMEOUT_MS=5000` if Wallet is slow. Holding an HTTP request thread for 5 seconds violates every reasonable client-timeout default (NestJS default body parser timeout, Kong default upstream timeout, the FE's TanStack Query default `staleTime`). Worse, the at-least-once-delivery contract from Phase 2 means the request might time out while the saga is mid-flight and the Bet is committed — the client gets a 504, retries, the partial unique index rejects with 409, and now the player is staring at "your bet failed" UI while the bet is in fact PENDING in the DB. To salvage Option A you would need long-polling or a request-scoped event listener inside the controller — ergonomic nightmare and brittle. And real-time UX would STILL need WS for "your bet is now ACTIVE" because the live feed broadcasts to ALL players, not just the one whose request is in flight.
- **Option B — Both endpoints async (`202 Accepted` + WS confirm)** — `POST /games/bet/cashout` returns `202 Accepted` with `{cashoutId, status:PENDING}`; the actual multiplier and payout figures arrive via WS `bet:cashed_out`. Pros: symmetric response shape; matches the bet-placement saga's pattern. Cons: cashout is the most latency-sensitive operation in the entire product. The player taps Cashout while the multiplier is climbing — they need the payout figure on screen immediately to drive the celebration animation (Phase 7 REQ-FE-14 — "cashout triggers a celebration") and to confirm that they hit the multiplier they wanted. Deferring to WS adds one more round-trip of latency (HTTP response → WS push) before the figure appears — observable to the player as a "delay" that breaks the tactile feedback loop. Cashout has no cross-service round-trip on the request path (Wallet credit is downstream bookkeeping); the only operation between `cashoutAcceptedAt` and the response is the per-bet micro-TX (Round status check + Bet.cashOut transition + outbox row), which commits in < 50ms. There is no technical reason to defer the response.
- **Option C — Asymmetric: `202 Accepted` for bet placement, synchronous `200 OK` for cashout (chosen)** — `POST /games/bet` returns `202 Accepted` with `{betId, status:PENDING}` immediately after the single Postgres TX commits (Bet PENDING + saga DEBIT_PENDING + outbox wallet.command.debit); the FE then waits for the WS `bet:active` push (Phase 6) for confirmation. `POST /games/bet/cashout` returns `200 OK` with `{multiplier, payoutCents}` synchronously after the per-bet micro-TX commits; the Wallet credit is downstream bookkeeping the player never waits for. Pros: each endpoint's response shape matches the actual workflow shape underneath it; bet's cross-service round-trip is acknowledged in the response code (`202` = "we accepted your request; the result is not final yet"); cashout's locality is reflected in the synchronous `200` + payload; both shapes are individually canonical REST. Aligns with how Bustabit-style products behave in practice (the bet button shows "Pending..." briefly; the cashout button shows the payout figure immediately). Cons: the API surface is asymmetric, which a recruiter might pattern-match as "design inconsistency" — defensible by walking through the workflow-shape argument; minor doc cost.

## Decision

**Option C — `POST /games/bet` returns `202 Accepted`, `POST /games/bet/cashout` returns `200 OK`.**

Bet placement endpoint (`services/games/src/presentation/controllers/bet-command.controller.ts`, Plan 05-04):

- Method: `POST /games/bet`
- Request body: `{ amountCents: bigint }`
- Successful response: `202 Accepted` with `{ betId: string, status: "PENDING", roundId: string }`
- The single Postgres TX commits: Bet(PENDING) + BetSagaState(DEBIT_PENDING with `deadline_at = now() + SAGA_TIMEOUT_MS`) + outbox(wallet.command.debit). The TX commits within milliseconds; the `202` returns immediately.
- The FE will observe transition to `ACTIVE` via WS `bet:active` (Phase 6) typically within 2 seconds (P5.10 observed median) of the `202`, or via `bet:refunded` if Wallet rejected (insufficient funds) or the saga timed out.
- Error responses: `409 Conflict` for FSM rejections (`ROUND_NOT_IN_BETTING_PHASE`, `BET_ALREADY_PLACED`); `400 Bad Request` for validation; `401 Unauthorized` for unauthenticated.

Cashout endpoint (`services/games/src/presentation/controllers/bet-command.controller.ts`, Plan 05-06):

- Method: `POST /games/bet/cashout`
- Request body: empty (cashout is implicit on the player's current active bet)
- Successful response: `200 OK` with `{ betId: string, status: "CASHED_OUT", multiplier: number, payoutCents: bigint, cashedOutAt: ISO8601 }`
- `acceptedAt = new Date()` is the literal first executable line of the controller method (per REQ-WS-05 / Plan 05-06 line 69) — captured before any await, before any DB read, before any module-level service call. This is the server-clock authority for cashout-vs-crash race resolution.
- `multiplier = roundLoop.getMultiplierAt(acceptedAt)` (Plan 05-02 pure synchronous source) is computed in-memory immediately after `acceptedAt`; the per-bet micro-TX then commits `Bet.cashOut(multiplier, acceptedAt)` + outbox `bet.cashed_out` + outbox `wallet.command.credit`. The response payload is the synchronous result; the Wallet credit flows downstream via the outbox.
- Error responses: `409 Conflict` for FSM rejections (`ROUND_NOT_RUNNING`, `NO_ACTIVE_BET`, `BET_NOT_CASHABLE`); `401 Unauthorized` for unauthenticated.

Cross-references: ADR-019 (orchestration ownership — Game owns the saga FSM; `bet.active` outbox event emitted by `WalletDebitedHandler` is the WS-bound payload Phase 6 will surface); ADR-013 (`txEm` propagation — every transition commits in a single TX); ADR-014 (per-bet micro-TX — cashout touches one Bet row, no Round-lock contention); REQ-WS-05 (server-clock-stamped `cashoutAcceptedAt` before any await — the cashout race resolution canon).

Rationale: each endpoint's response code matches its actual workflow shape. Bet placement crosses a service boundary, requires AMQP round-trip, and cannot complete synchronously without holding the request thread for seconds — `202 Accepted` is the canonical REST code for "we accepted your request and are processing it asynchronously" (RFC 9110 §15.3.3). Cashout is single-service, single-TX, and the payout figure is the player's primary feedback — synchronous `200 OK` is correct. The asymmetry is a feature of correctness, not a bug.

## Consequences

- **Locked in (public REST contract)**: `POST /games/bet` → `202 Accepted` with `{betId, status:"PENDING", roundId}`; `POST /games/bet/cashout` → `200 OK` with `{betId, status:"CASHED_OUT", multiplier, payoutCents, cashedOutAt}`. Phase 6 WS gateway must consume `bet.active` / `bet.refunded` from `game.events` and push them to the player's `user:{playerId}` private room so the FE can resolve the pending state. Phase 7's bet panel UX explicitly shows "Pending..." between the `202` and the WS push (FE-side timeout fallback at 5.5s — saga timeout + 500ms grace — shows "Bet failed, please retry").
- **Locked in (cashout latency budget)**: the cashout request path budget is `cashoutAcceptedAt → multiplier compute → per-bet micro-TX commit → response` — observed at P5.10 ~< 100ms. Any future change that adds an await before `acceptedAt` (e.g., a hypothetical "load player profile" lookup) violates REQ-WS-05 and must be rejected at code review.
- **Locked in (DLX alignment — cross-service queues use source-exchange DLX)**: P5.10 surfaced a topology defect at live boot: `games-service`'s `games.wallet-events.q` queue was declared with `EXCHANGES.GAME_DLX` but the `@IdempotentSubscribe` decorator derives the DLX from the source exchange via `deriveDlxFromExchange()` → `wallet.events` → `wallet.dlx`, causing a `PRECONDITION_FAILED` on QueueDeclare (exchange-DLX mismatch). The fix (commit `a7ee5e2`) aligns the queue config to `EXCHANGES.WALLET_DLX`. The lesson — **cross-service consumer queues use the source exchange's DLX, not the consuming service's DLX** — is documented in `packages/messaging-spine/README.md` and applies to every future cross-service event subscription (e.g., Phase 9's leaderboard projector consuming `game.events` will use `EXCHANGES.GAME_DLX`).
- **Locked in (saga timeout UX)**: `SAGA_TIMEOUT_MS=5000` is the deadline after which a `DEBIT_PENDING` saga is auto-refunded by `SagaTimeoutSweeper` (Plan 05-07). The FE's pending-UX timeout is `SAGA_TIMEOUT_MS + 500ms grace` = 5.5s; after that the FE surfaces "Bet failed, please retry" even if the WS push has not arrived. The grace accommodates clock skew + OutboxPublisher poll latency + WS broadcast latency.
- **Locked in (compensation path is invisible to client)**: if a `wallet.event.debited` arrives late (after the saga already timed out), `WalletDebitedHandler` transitions the saga `TIMED_OUT → COMPENSATED` and emits `wallet.command.credit` to restore the player's balance. The player has already seen "Bet failed" via the timeout path; the compensation is bookkeeping invisible to the request/response cycle. Plan 05-09's compensation scenario (AMQP `unbindQueue` / `bindQueue` manipulation) is the canonical test.
- **Locked in (HTTP status code semantics)**: `202` for bet, `200` for cashout — never the reverse. A future code review must reject any change that returns `200` from bet (would imply the saga completed in the request path, which is impossible given the cross-service round-trip) or `202` from cashout (would imply the cashout deferred to async, breaking REQ-WS-05's server-clock authority and Phase 7's celebration animation).
- **Foreclosed**: Option A both-synchronous (would hold the bet request thread for seconds; client timeout + at-least-once-delivery interact badly); Option B both-async (would defer the cashout payout figure behind a WS round-trip, breaking the tactile feedback loop; no technical reason to defer cashout).
- **Operational cost**: the FE must implement two distinct UX shapes (bet pending → WS confirm vs cashout immediate); the docs (README + arguição prep) must walk through the asymmetry justification; minor.
- **Test surface**: Plan 05-04 integration covers `POST /games/bet 202 + saga.DEBIT_PENDING` + `bet.confirm` via WS-equivalent (outbox bet.active row); Plan 05-06 integration covers `POST /games/bet/cashout 200` synchronous with multiplier + payoutCents in the response body. Plan 05-09's seven scenarios cover the full matrix (happy + insufficient-funds + bet-outside-betting + timeout + compensation + cashout + double-cashout). Plan 05-10 smoke probes 33-38 cover the live HTTP path (probes 34-37 deferred for timing per the P5.10 deferred-items log).
- **Anticipated recruiter question**: "Why isn't the API symmetric? Both endpoints touch the Bet aggregate and money — they should have the same response shape." — defended by the workflow-shape argument: bet placement crosses a service boundary and requires AMQP round-trip (the `202` is honest about the asynchronous reality); cashout is single-service and single-TX (the `200` is honest about the synchronous reality). The asymmetry IS the design.
- **Anticipated recruiter question**: "Why not WebSocket-only for both (eliminate HTTP)?" — defended by the request/response contract argument: HTTP is the canonical surface for player-initiated mutations (idempotency keys, status codes, CSRF protection, Kong rate limiting); WS is the canonical surface for server-initiated broadcasts (live feed, multiplier ticks, round transitions). Conflating them collapses the auth model (every WS message would need authentication) and the error-handling model (HTTP 4xx/5xx are well-understood; WS error codes are not). Phase 6 WS layer is purely server→client push; Phase 7's bet UX uses HTTP for the action + WS for the confirmation, the cleanest separation.
- **Anticipated recruiter question**: "What if `SAGA_TIMEOUT_MS` is too short and the player loses confidence?" — defended by the env-overridable nature of the constant (REQ-INFRA-05; documented in `.env.example`) + the FE's pending UX explicitly showing the elapsed time + the compensation path ensuring no money is ever lost even if the saga times out and the late debit arrives. The 5s default is tuned to Bustabit-style player expectations; tunable per operator.

Cross-references: ADR-013 (txEm propagation — every TX-bound transition commits atomically); ADR-014 (per-bet micro-TX — cashout's locality is a direct consequence); ADR-017 (recursive `setTimeout` — `SagaTimeoutSweeper`'s timer pattern); ADR-019 (orchestration — `bet.active` is emitted by Game's `WalletDebitedHandler`, not Wallet directly).

## Alternatives Rejected

- **Option A — Both endpoints synchronous (`200 OK`)** — bet request thread held across at-least-two AMQP hops + two TX commits; client-timeout vs at-least-once-delivery interaction creates 504-then-409 retry traps; salvaging via long-polling is ergonomically indefensible; WS would still be needed for the live feed anyway.
- **Option B — Both endpoints async (`202 Accepted` + WS confirm)** — cashout has no technical reason to defer (single-service, single-TX, < 100ms); deferring breaks the tactile feedback loop required by Phase 7's celebration animation; the multiplier figure is the player's primary feedback and must be synchronous.
