# ADR-022: 30 Hz server tick + 60 fps client interpolation

**Status**: Accepted
**Date**: 2026-05-28
**Phase**: 6

## Context

The multiplier is the central animated object of the Crash game: a curve that climbs `e^(GROWTH_RATE * t / 1000)` from `1.00x` at `roundStartedAt` until the round crashes at the provably-fair crash point. Every connected player must see the same value at the same wall-clock instant (server-authoritative, per PITFALLS C2 / H1 — the server's multiplier is the only authority; a client must never compute a higher multiplier than the server would honor for a cashout) AND the curve must render smoothly enough that a player tapping Cashout feels a tactile, frame-accurate relationship between what they see and what they get.

These two requirements pull in opposite directions. Server authority argues for the server pushing the multiplier value frequently so clients never drift. Smooth rendering argues for 60 fps animation. Pushing 60 authoritative values per second per client is bandwidth-expensive and, worse, couples render smoothness to network jitter — a dropped or late packet becomes a visible stutter. The reconciliation, drawn from the Gabriel Gambetta client-side-prediction canon (RESEARCH §"Anti-Patterns" cites "Gabriel Gambetta canon, ARCHITECTURE §8"; SUMMARY §8 conflict resolution: "30Hz server tick + 60fps client rAF"), is to decouple the two rates: the server emits authoritative ticks at a modest rate, and each client interpolates between ticks at its own render rate using the SAME deterministic formula the server uses, anchored to the same `roundStartedAt`. The client is not guessing — it is recomputing the same pure function the server computes, and using the server ticks as periodic ground-truth corrections rather than as the render source.

REQ-WS-06 requires ticks be emitted as `volatile.emit` so a slow consumer cannot stall the broadcast loop. `SERVER_TICK_HZ=30` is an Open Configuration Value (REQUIREMENTS Open Configuration Values table; `GROWTH_RATE=0.06`). REQ-FE-02 / REQ-FE-03 (Phase 7) specify the client side: Canvas 2D at 60 fps via `requestAnimationFrame`, computing the multiplier locally from `e^(GROWTH_RATE * t / 1000)` anchored to `roundStartedAt`, correcting toward the server tick via EWMA clock-offset (tween, never snap). Phase 6 ships only the server half; the client half lands in Phase 7.

A second, unrelated constraint surfaced during Phase 6 live bring-up (Plan 06-09) and is recorded here as a Consequence because it is inseparable from how the tick is actually delivered: the Socket.IO server cannot attach to Bun's `@nestjs/platform-express` HTTP server, so the entire WS surface — including the tick — runs on a standalone Socket.IO server on a dedicated port. Three server-tick-rate options were on the table at the Plan 06-04 design point.

## Considered

- **Option A — 60 Hz server tick** — the server emits the authoritative multiplier 60 times per second (every ~16.7 ms), matching the client's render rate one-to-one so the client renders each tick directly with no interpolation. Pros: conceptually simplest client (render-what-you-receive, no local formula); no client/server formula-divergence risk. Cons: doubles the tick bandwidth versus 30 Hz for no smoothness gain — the client still has to interpolate or tween across the inevitable network jitter (packets do not arrive on a clean 16.7 ms grid), so the "no interpolation" benefit is illusory; 60 authoritative values per second per connected client is the highest sustained broadcast load in the system; couples render smoothness directly to packet arrival timing, so a single late packet is a visible stutter rather than a silently-interpolated-over gap. The RESEARCH §"Anti-Patterns" rejects it: "60 Hz server tick (2× bandwidth, no smoothness gain)."
- **Option B — per-frame server broadcast** — the server pushes a value on every animation frame it would render (effectively unbounded, hundreds of Hz). Pros: none at game scale. Cons: ~600× the bandwidth of a sane tick rate (RESEARCH ADR-022 anticipated entry: "per-frame server broadcast (~600× bandwidth)"); the server does not even have a frame rate — it is a headless game loop — so "per-frame" is a category error imported from client thinking; catastrophically wasteful. Rejected on sight.
- **Option C — 10 Hz server tick** — the server emits every 100 ms, relying heavily on client interpolation to fill the long gaps. Pros: lowest bandwidth. Cons: 100 ms between authoritative corrections is too coarse for accurate EWMA clock-offset reconciliation — the client's local clock and the server's diverge enough over 100 ms that the tween either visibly lags or has to make large corrective jumps when a tick finally lands; the cashout-vs-crash race window (±50 ms per the cashout-race property test, Plan 06-08) is finer-grained than the tick interval, so a 10 Hz tick gives the client a stale multiplier for up to 100 ms around the most decision-critical moment of the round. RESEARCH §"Anti-Patterns" rejects it: "10 Hz tick (too coarse for accurate clock-offset EWMA)."
- **Option D — 30 Hz server tick + 60 fps client rAF interpolation (chosen)** — the server emits the authoritative multiplier every 33 ms (`Math.max(1, Math.round(1000 / SERVER_TICK_HZ))` = 33 ms at the default 30 Hz); the client renders at 60 fps via `requestAnimationFrame`, computing the multiplier locally each frame from `e^(GROWTH_RATE * t / 1000)` anchored to `roundStartedAt`, and reconciling toward each arriving 30 Hz tick via EWMA clock-offset (tween, never snap). Pros: ~50% of 60 Hz's bandwidth; render smoothness is decoupled from network jitter (the client always has a local frame-accurate value, ticks are periodic corrections); 33 ms is fine-grained enough for accurate EWMA reconciliation and finer than the ±50 ms cashout race window; the server tick is a tiny ~30-byte payload (`{roundId, multiplier, t}`) that `volatile.emit` can drop freely under backpressure without stalling the loop. Cons: requires the client to carry the same `e^(GROWTH_RATE * t / 1000)` formula as the server (formula divergence would cause drift) — mitigated by sharing the formula as a pure function and by the periodic server-tick correction; the EWMA reconciliation logic is non-trivial client code (deferred to Phase 7 FE).

## Decision

**Option D — 30 Hz server tick emitted via `volatile.emit`, with 60 fps client-side interpolation via `requestAnimationFrame`.**

Server side (Phase 6, `services/games/src/application/multiplier-broadcast.service.ts`, Plan 06-04):

- `MultiplierBroadcastService` runs a recursive `setTimeout` loop (NOT `setInterval` — ADR-017 pattern, RESEARCH §Pitfall 1: recursive `setTimeout` schedules the next tick only after the previous send returns, so `volatile.emit`'s writable-buffer check is more likely to pass and packets drop cleanly under backpressure rather than queueing).
- Tick interval = `Math.max(1, Math.round(1000 / env.SERVER_TICK_HZ))` — 33 ms at the default `SERVER_TICK_HZ=30`; the `Math.max(1, …)` guards a degenerate high-Hz config.
- Each tick computes `now = new Date()`, pulls `roundLoop.getMultiplierAt(now)` (the synchronous server-clock multiplier source, Phase 5 Plan 05-02), and emits `round:tick` with `{ roundId, multiplier: m.toNumber(), t: now.getTime() }` to room `lobby` via `server.to('lobby').volatile.emit(...)`.
- The tick payload multiplier is a plain JS number (3-decimal float is acceptable for a display value at 30 Hz, RESEARCH OQ 3 — this matches `CashoutResponseDto.multiplier: number` at `bet-command.controller.ts:80`). The AUTHORITATIVE money values (cashout payout, crash point) remain `Money` / Multiplier snapshots and never ride the tick.
- If `getMultiplierAt` throws (the round transitioned out of RUNNING between schedule and fire), the tick is silently dropped and the loop reschedules via the `finally` block — no per-tick log entry (would flood at 30 Hz, RESEARCH §Pitfall 2).
- `MultiplierBroadcastService` is the SOLE owner of `volatile.emit` in the codebase — the gateway and all lifecycle/bet emit paths use regular `emit` (grep-verified zero `volatile` references in `game-ws.gateway.ts`).

Client side (Phase 7, REQ-FE-02 / REQ-FE-03 — out of scope for Phase 6, recorded here for completeness): Canvas 2D at 60 fps via `requestAnimationFrame` + `devicePixelRatio` scaling + `clearRect`; multiplier computed locally each frame from the shared `e^(GROWTH_RATE * t / 1000)` formula anchored to `roundStartedAt`; corrected toward each arriving 30 Hz tick via EWMA clock-offset tween (never snap).

Justified by the Gabriel Gambetta client-prediction canon (decouple authoritative-update rate from render rate; client interpolates the same deterministic function) + SUMMARY §8 / ARCHITECTURE §8 conflict resolution (30 Hz server + 60 fps client) + REQ-WS-06 (`volatile.emit` slow-consumer safety) + the ±50 ms cashout-race granularity requiring a tick finer than 100 ms + the ~50% bandwidth saving over 60 Hz with no smoothness loss.

## Consequences

- **Locked in (server tick rate)**: 30 Hz via `SERVER_TICK_HZ` env (default 30), emitted on a recursive-`setTimeout` loop at `Math.max(1, Math.round(1000 / SERVER_TICK_HZ))` ms. The rate is env-overridable for non-prod but the recursive-`setTimeout` + `volatile.emit` mechanism is fixed.
- **Locked in (`volatile.emit` for ticks)**: REQ-WS-06 satisfied — `MultiplierBroadcastService.fireTick` is the only `volatile.emit` call site; a slow consumer drops tick packets at its own transport rather than backpressuring the broadcast loop. T-06-09 mitigation, verified by `multiplier-broadcast.service.test.ts` (the stub captures `.volatile.emit` access, not `.emit`).
- **Locked in (tick payload shape)**: `{ roundId, multiplier: number, t: number }` — ~30 bytes, display-precision float multiplier, server wall-clock `t`. No bet-feed or balance data on the tick (RESEARCH §Pitfall 1 — keep the tick tiny; T-06-11 accept — no player-level data leaks to lobby).
- **Locked in (client interpolation contract — Phase 7)**: the FE computes the multiplier locally from `e^(GROWTH_RATE * t / 1000)` anchored to `roundStartedAt` (carried in `round:snapshot` + `round:started`) and reconciles toward the 30 Hz tick via EWMA clock-offset tween. The shared formula MUST be the same pure function on both sides to prevent drift — Phase 8's deterministic-replay test (REQ-REPLAY-01/03) will additionally prove the renderer reproduces captured multiplier samples byte-for-byte.
- **Locked in (standalone Socket.IO server on `WS_PORT=4101`, websocket-only transport)**: discovered during Plan 06-09 live bring-up. engine.io's `attach()` calls `server.listeners("request")` unconditionally, but Bun's `@nestjs/platform-express` HTTP server lacks the Node `EventEmitter.listeners()` method, throwing `server.listeners is not a function` and crash-looping the games container. The fix (commit `c026012`) runs a standalone Socket.IO server on a dedicated `WS_PORT=4101` — engine.io creates its own `node:http` server which on Bun DOES expose `.listeners()` — with `transports: ['websocket']` (websocket-only) and `allowUpgrades: false` to skip the HTTP long-polling handshake entirely. Kong's `~/ws/?$` route proxies to `games:4101`. This is a Bun-specific infrastructure constraint, not a design choice, but it is now load-bearing: the tick (and every WS event) is delivered over this standalone-port websocket-only server, and any future change to the HTTP adapter must preserve the separate WS port.
- **Locked in (EWMA reconciliation deferred to Phase 7 FE)**: the server ships only the authoritative 30 Hz tick. The clock-offset EWMA tween that makes the curve smooth is client code and lands in Phase 7 (REQ-FE-03). Phase 6 has no client; the integration test `ws-tick-volatile.test.ts` (Plan 06-08) asserts the ~30 Hz emit frequency within tolerance, not the client smoothing.
- **Foreclosed**: Option A 60 Hz server (2× bandwidth, illusory no-interpolation benefit, render coupled to jitter); Option B per-frame server broadcast (~600× bandwidth, category error); Option C 10 Hz (too coarse for EWMA, stale around the ±50 ms cashout race).
- **Operational cost**: 30 tiny packets/sec/client on the lobby room, droppable under backpressure via `volatile`. The recursive-`setTimeout` loop is a single timer per games instance, started on RUNNING entry and stopped on CRASHED entry by the Plan 06-05 lifecycle bridge.
- **Test surface**: `multiplier-broadcast.service.test.ts` (Plan 06-04 — start/stop idempotency, payload shape, mid-tick throw handling, `volatile.emit` usage, zero `setInterval`); `ws-tick-volatile.test.ts` (Plan 06-08 — ~30 Hz frequency within tolerance, REQ-WS-06). Live smoke probe 42 (observe ≥30 ticks in 2 s RUNNING) is timing-deferred to Phase 7/10 — the tick path is functionally proven by the round loop cycling live at P6.09 + the integration test.
- **Anticipated recruiter question**: "Why 30 Hz and not 60? Won't 30 look choppy?" — defended by the decoupling argument: render smoothness comes from the client's 60 fps rAF loop interpolating the shared `e^(GROWTH_RATE * t / 1000)` formula, not from the tick rate; the 30 Hz tick is a periodic authoritative correction, not the render source, so 30 Hz renders identically smooth to 60 Hz at half the bandwidth.
- **Anticipated recruiter question**: "Why is there a separate WS port instead of sharing the HTTP server?" — defended honestly as a Bun-runtime incompatibility surfaced at live bring-up (engine.io's `attach()` calls `server.listeners()` which Bun's express adapter lacks); the standalone Socket.IO server on `WS_PORT=4101` with websocket-only transport sidesteps it cleanly, Kong proxies `~/ws/?$` to it, and the trade-off (one extra listening port) is documented and minimal.

Cross-references: ADR-017 (recursive `setTimeout` + `OnApplicationBootstrap` — the timer pattern reused by `MultiplierBroadcastService`); ADR-021 (single lobby — the room the tick broadcasts to); Plan 05-02 (`RoundLoopService.getMultiplierAt` — the synchronous server-clock multiplier source the tick pulls from); Plan 06-04 SUMMARY (T-06-09/10/11 tick mitigations); Plan 06-09 SUMMARY (standalone WS port + Bun http-attach fix). Phase 7 REQ-FE-02/03 carry the client interpolation half; Phase 9 REQ-AUTO-01 (server-enforced auto-cashout) will subscribe to this same 30 Hz tick loop in-process.

## Alternatives Rejected

- **Option A — 60 Hz server tick** — 2× bandwidth for no smoothness gain; the "render-what-you-receive, no interpolation" benefit is illusory because network jitter still forces tweening; couples render smoothness to packet arrival.
- **Option B — per-frame server broadcast** — ~600× bandwidth; "per-frame" is a category error for a headless server game loop; catastrophically wasteful.
- **Option C — 10 Hz server tick** — 100 ms between corrections is too coarse for accurate EWMA clock-offset reconciliation and is coarser than the ±50 ms cashout race window, leaving the client with a stale multiplier around the most decision-critical moment.
