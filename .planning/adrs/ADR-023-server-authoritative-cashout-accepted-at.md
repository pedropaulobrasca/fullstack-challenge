# ADR-023: Server-authoritative `cashoutAcceptedAt` at the HTTP controller's first executable line

**Status**: Accepted
**Date**: 2026-05-28
**Phase**: 6

## Context

Cashout is the single most race-sensitive operation in the Crash game. The multiplier climbs continuously and the round crashes at a provably-fair crash point; a player tapping Cashout is racing the crash. The system must resolve every cashout deterministically: either the cashout was accepted at a wall-clock instant strictly before the crash (valid payout at the multiplier-for-that-instant) or it arrived at-or-after the crash (rejected `409 Conflict`). There must NEVER be a double-cashout (two payouts for one bet) and NEVER a post-crash payout (a payout computed at a multiplier the round never legitimately reached). The decisive input is a single timestamp — `cashoutAcceptedAt` — and the entire correctness of the race resolution rests on WHO stamps it and WHEN.

The threat (PITFALLS C2, RESEARCH §"Cashout race") is client-supplied or late-stamped time. If the client sends its own timestamp, a malicious client backdates it to claim a higher multiplier than it deserves. If the server stamps the time late — after a DB read, after acquiring a lock, after any `await` — the stamp drifts past the true arrival instant by however long those operations took, which under load can be tens of milliseconds: enough to turn a should-have-lost cashout into a paid one, or vice versa. The only defensible stamp is the server's own clock, captured as the very first thing the request handler does, before any asynchronous work.

REQ-WS-05 specifies this, but its wording is the source of the interpretation question this ADR resolves: it says `cashoutAcceptedAt` is "stamped at gateway middleware, before any await." Taken literally, "gateway middleware" sounds like it mandates a WebSocket gateway inbound-message handler (a Socket.IO `@SubscribeMessage` or an `io.use` middleware). But cashout in this system is NOT a WS message — it is a `POST /games/bet/cashout` HTTP endpoint, locked by ADR-020 (bet-202 / cashout-200 asymmetry) as a synchronous `200 OK` returning `{multiplier, payoutCents}`. Phase 5 already implemented the server-clock stamp at the controller's first line (Plan 05-06, `bet-command.controller.ts:69`). The Phase 6 question is therefore not "how do we build cashout" — it already exists — but "does Phase 6's WS gateway change the cashout path, and how do we reconcile REQ-WS-05's 'gateway middleware' wording with the HTTP-controller reality?"

The RESEARCH answers it directly (§"REQ-WS-05 wording vs. reality"; §"ADRs Anticipated" ADR-023): "The requirement literally says 'stamped at gateway middleware.' In practice, cashout is a `POST /games/bet/cashout` HTTP endpoint, not a WS message; the 'gateway' interpretation is the NestJS controller layer. Phase 5 already implements this (`acceptedAt = new Date()` at line 69 of `bet-command.controller.ts`, before any `await`). Phase 6 does NOT migrate cashout to a WS message; ADR-023 documents the existing HTTP-controller-as-gateway interpretation explicitly." This ADR is the codification — it does not change code, it locks the interpretation and the invariant so the arguição has a defensible record and so no future plan migrates cashout to a WS handler without re-opening this decision. Three placements of the cashout server-stamp were on the table.

## Considered

- **Option A — WS inbound `cashout` message handler** — migrate cashout off HTTP onto a Socket.IO `@SubscribeMessage('cashout')` handler, stamping `acceptedAt = new Date()` as the first line of the message handler. This is the most literal reading of REQ-WS-05's "gateway middleware." Pros: the timestamp is captured in the same connection the player is already using for ticks (no separate HTTP request); superficially matches the requirement's wording. Cons: the WS message handler runs on the SAME Node/Bun event loop as the 30 Hz `MultiplierBroadcastService` tick broadcast loop (ADR-022). A cashout message arriving while the tick loop is mid-emit competes for the same event-loop turns — the `acceptedAt = new Date()` line cannot execute until the current synchronous tick work yields, so the stamp is captured LATER than it would be on an isolated thread, and the lateness is correlated with broadcast load (the busier the lobby, the later the stamp). This TIGHTENS the race rather than relaxing it — exactly the wrong direction for the most race-sensitive operation. Additionally, a WS message has no clean per-request response surface: HTTP gives a uniform `200 {multiplier, payoutCents}` / `409 {code}` that the FE consumes with standard status-code handling (ADR-020); a WS ack callback or a follow-up event is a bespoke error model the FE would have to special-case. And it would collapse the auth model — every inbound WS message would need its own authorization check, whereas the HTTP path already carries the JWT through the standard guard.
- **Option B — HTTP controller server-stamp at the first executable line (chosen, already implemented Phase 5)** — `POST /games/bet/cashout`'s controller method captures `const acceptedAt = new Date()` as its literal first executable statement, before any `await`, before any DB read, before any service call. The HTTP request runs on its own isolated request handling, not sharing event-loop turns with the tick broadcast loop in a way that delays the stamp relative to arrival. Pros: the stamp is captured at the earliest defensible instant; the request thread is isolated from the tick loop's synchronous work; HTTP gives the clean `200`/`409` response surface ADR-020 locked; the JWT flows through the existing guard; cashout was already built this way in Phase 5 (Plan 05-06) and proven live at P5.10. Cons: requires interpreting REQ-WS-05's "gateway middleware" as "the NestJS controller layer," which this ADR makes explicit and defensible (a NestJS controller IS a kind of gateway — the HTTP entry gateway into the application).
- **Option C — client-supplied timestamp** — the client sends the instant it tapped Cashout; the server trusts it. Pros: captures the player's true intent instant with zero server-side latency. Cons: trivially forgeable — a malicious client backdates the timestamp to claim a higher multiplier or to dodge a crash. Violates the foundational rule (CLAUDE.md WebSocket section: "Never trust client time"). Non-starter; listed only for completeness.

## Decision

**Option B — `cashoutAcceptedAt` is the server's own clock, captured as the first executable line of the `POST /games/bet/cashout` HTTP controller method, before any `await`. "Gateway middleware" in REQ-WS-05 is interpreted as the NestJS controller layer — the HTTP entry gateway into the application.**

The locked implementation is the existing Phase 5 code (`services/games/src/presentation/controllers/bet-command.controller.ts`, Plan 05-06, line 69):

```
const acceptedAt = new Date();
```

This is the literal first executable statement of the cashout controller method — captured before any DB read, before `roundLoop.getMultiplierAt`, before the per-bet micro-TX, before any module-level service call. Immediately after, `multiplier = roundLoop.getMultiplierAt(acceptedAt)` (Plan 05-02 pure synchronous source) computes the authoritative multiplier for that exact instant, and the per-bet micro-TX commits `Bet.cashOut(multiplier, acceptedAt)` + outbox `bet.cashed_out` + outbox `wallet.command.credit` (ADR-020, REQ-SAGA-04). The `acceptedAt` instant is the ONLY authority for cashout-vs-crash race resolution: if `acceptedAt` is before the round's crash instant, the cashout is valid at the multiplier-for-`acceptedAt`; if at-or-after, the FSM guard rejects with `409`.

**Phase 6 does NOT migrate cashout to a WS inbound message.** The WS gateway is purely server→client push (round lifecycle, tick, bet feed); player-initiated mutations stay on HTTP (ADR-020). The `WsBridgeConsumer` (Plan 06-06) consumes the `bet.cashed_out` outbox event from `game.events` and fans it to the lobby (masked multiplier only — T-06-16) and to `user:{playerId}` (`bet:my_cashed_out`, with payout) — but that is the server BROADCASTING the already-decided cashout, not accepting the cashout. The decision was made and stamped at the HTTP controller; the WS layer only narrates it.

### Why NOT a WS inbound message

The decisive argument against Option A is event-loop contention. The 30 Hz `MultiplierBroadcastService` tick loop (ADR-022) runs on the same single-threaded event loop a WS message handler would run on. A `@SubscribeMessage('cashout')` handler's `acceptedAt = new Date()` cannot execute until the event loop reaches it — and if a tick emit is mid-flight, the stamp waits behind it. The stamp's lateness would correlate with broadcast load: under a busy lobby (many sockets, frequent ticks), the stamp drifts later, tightening the race precisely when timing precision matters most. An isolated HTTP request handler does not interleave with the tick loop's synchronous emit work in the same stamp-delaying way. On top of the timing argument: HTTP gives a clean, uniform `200 {multiplier, payoutCents}` / `409 {code}` response surface (ADR-020, RFC-canonical status codes the FE already handles), whereas a WS message would require a bespoke ack/error-event model; and the HTTP path carries the JWT through the existing guard, whereas a WS message handler would need per-message authorization. The RESEARCH OQ context is explicit: a WS inbound cashout "would compete with tick loop and complicate the race window without benefit."

Justified by the event-loop-isolation argument (HTTP request handler does not share stamp-delaying event-loop turns with the 30 Hz tick loop) + the clean HTTP `200`/`409` response surface (ADR-020) + the "never trust client time" rule (CLAUDE.md) + the fact that the controller-first-line stamp was already built and proven live in Phase 5 (Plan 05-06, P5.10 trace) + the Phase 6 property test (Plan 06-08 `cashout-race.property.test.ts`) covering the ±50 ms window across 50 fast-check cases.

## Consequences

- **Locked in (server-clock authority)**: `cashoutAcceptedAt = new Date()` at the first executable line of the cashout controller is the SOLE authority for cashout-vs-crash race resolution. Client-supplied time is never trusted. Any future change that inserts an `await`, a DB read, or any work before the `acceptedAt` stamp violates REQ-WS-05 and MUST be rejected at code review (ADR-020 already locked this as a code-review gate).
- **Locked in (REQ-WS-05 interpretation)**: "gateway middleware" = the NestJS HTTP controller layer. A NestJS controller is the HTTP entry gateway into the application; stamping at its first line satisfies the requirement's intent (earliest server-side capture, before any await) even though it is not a Socket.IO middleware. This interpretation is the canon — future readers of REQ-WS-05 reference this ADR.
- **Locked in (cashout stays on HTTP)**: cashout is NOT migrated to a WS inbound message in Phase 6 or any future phase without a superseding ADR. The WS gateway is server→client push only; player mutations are HTTP (ADR-020). The `WsBridgeConsumer` broadcasts the already-decided `bet.cashed_out` — it does not accept cashouts.
- **Locked in (race invariant)**: every cashout resolves to exactly one of {valid payout at multiplier-for-`acceptedAt` where `acceptedAt` < crash instant, `409 Conflict` where `acceptedAt` ≥ crash instant}. Never a double-cashout (the Bet FSM `ACTIVE → CASHED_OUT` is a one-shot transition guarded at the aggregate boundary, REQ-DOM-03); never a post-crash payout (the multiplier is computed at `acceptedAt`, and an `acceptedAt` after crash fails the RUNNING-phase guard with `409 ROUND_NOT_RUNNING`).
- **Foreclosed**: Option A WS inbound `cashout` message (event-loop contention with the tick loop tightens the race; bespoke WS error model; per-message auth); Option C client-supplied timestamp (trivially forgeable; violates "never trust client time").
- **Operational cost**: none new — the stamp is one synchronous `new Date()` call. The cashout request-path budget (`acceptedAt → multiplier compute → per-bet micro-TX commit → response`) was observed at P5.10 ~< 100 ms (ADR-020).
- **Test surface**: Phase 6 Plan 06-08 ships `tests/property/cashout-race.property.test.ts` — `fast-check` 50 runs, each picking a `dt` within ±50 ms of the crash instant, asserting the invariant: exactly ONE of {valid payout with timestamp before crash, `409` conflict}, NEVER a double-cashout or post-crash payout (REQ-WS-05, PITFALLS C2). `numRuns` reduced to 50 with documented justification (booting a real round + RabbitMQ + Postgres + hammering cashouts is heavyweight, RESEARCH §Anti-Patterns / risk note). Phase 5 Plan 05-06 unit suite verified `acceptedAt` is line 69, the literal first executable line.
- **Anticipated recruiter question**: "REQ-WS-05 says 'gateway middleware' — why is the stamp in an HTTP controller and not a WebSocket middleware?" — defended by the interpretation argument (a NestJS controller IS the HTTP entry gateway) + the event-loop-isolation argument (a WS message handler shares stamp-delaying turns with the 30 Hz tick loop, tightening the race) + the clean HTTP `200`/`409` surface + the "never trust client time" rule. The intent of REQ-WS-05 — earliest defensible server-side capture before any await — is fully satisfied.
- **Anticipated recruiter question**: "Couldn't a WS cashout be faster than an HTTP round-trip?" — defended: the dominant latency is the player's network RTT, identical for WS and HTTP; what matters for correctness is not total latency but WHERE the authoritative timestamp is captured, and the HTTP handler captures it on an isolated request thread free of tick-loop contention, which is strictly better for race precision than a WS handler interleaving with the broadcast loop.

Cross-references: ADR-020 (bet-202 / cashout-200 asymmetry — cashout's synchronous `200` + `acceptedAt = new Date()` first line at `bet-command.controller.ts:69`; the `200`/`409` response surface this ADR depends on); ADR-022 (30 Hz tick — the broadcast loop a WS cashout handler would contend with on the event loop); ADR-014 (per-bet micro-TX — the cashout transition touches one Bet row); ADR-019 (orchestration — `bet.cashed_out` outbox event the `WsBridgeConsumer` narrates); REQ-DOM-03 (Bet FSM one-shot `ACTIVE → CASHED_OUT` — the double-cashout guard); Plan 05-06 (the locked implementation); Plan 06-08 (`cashout-race.property.test.ts`). Phase 9 REQ-AUTO-01 (server-enforced auto-cashout) reuses this same server-clock primitive: the 30 Hz tick loop will compare each tick's multiplier to the player's target and auto-issue a cashout server-stamped the same way.

## Alternatives Rejected

- **Option A — WS inbound `cashout` message handler** — the handler shares the event loop with the 30 Hz tick broadcast loop, so the `acceptedAt` stamp waits behind in-flight tick work and drifts later under broadcast load, tightening the most race-sensitive operation; no clean per-request response surface; per-message auth burden. Competes with the tick loop and complicates the race window without benefit.
- **Option C — client-supplied timestamp** — trivially forgeable (backdate to claim a higher multiplier or dodge a crash); violates the "never trust client time" rule (CLAUDE.md WebSocket section). Non-starter.
