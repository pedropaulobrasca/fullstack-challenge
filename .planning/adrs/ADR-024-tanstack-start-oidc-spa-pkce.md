# ADR-024: TanStack Start + `oidc-spa` for OIDC Authorization Code + PKCE (S256)

**Status**: Accepted
**Date**: 2026-05-29
**Phase**: 7

## Context

The frontend is a single-page TanStack Start app that authenticates the player against the Keycloak `crash-game` realm and then carries the resulting access token into two distinct trust-crossing channels: the REST calls (`GET /wallets/me`, `POST /games/bet`, `POST /games/bet/cashout`) and the Socket.IO WebSocket handshake. The realm's `crash-game-client` is a PUBLIC client — there is no client secret to keep, which makes the OIDC Authorization Code flow with PKCE (S256) the mandatory profile (a public SPA must prove possession of the authorization request via the code_verifier/code_challenge, because it cannot authenticate with a secret). Phase 6 already locked the server side: the WS handshake validates the Keycloak JWT via cached JWKS and rejects unauthenticated upgrades (ADR-012, ADR-021, REQ-WS-01). The frontend's job in Phase 7 is the client half of REQ-AUTH-01/02/03:

- **REQ-AUTH-01** — redirect unauthenticated users to Keycloak via Authorization Code + PKCE (S256).
- **REQ-AUTH-02** — persist the token client-side and silently renew it before expiry.
- **REQ-AUTH-03** — coordinate renewal across multiple tabs so all tabs rotate exactly once per token refresh (no refresh storm).

The hard constraint is correctness under concurrency, not feature count. A naive token layer that hand-rolls PKCE (generate verifier, SHA-256 the challenge, stash the verifier across the redirect, exchange the code), then hand-rolls silent renewal (a timer firing a hidden-iframe or refresh-token grant before expiry), then hand-rolls multi-tab coordination (a `BroadcastChannel` leader-election so N tabs don't each fire their own renew at the same second) is exactly the surface PITFALLS Pitfall 5 calls out as the "refresh storm": when every tab independently notices the token is near expiry and races to refresh it, the realm sees N concurrent refresh-token grants, rotation invalidates the in-flight ones, and tabs thrash into a re-login loop. Each of those three pieces is individually subtle and collectively a multi-day, high-bug-density investment that buys nothing the arguição rewards — it is plumbing, not product.

The socket also imposes a freshness constraint the auth layer must honor: the WS handshake JWT is validated once at connection (CLAUDE.md WebSocket section — no mid-connection re-auth), so every reconnect must present a *fresh, non-expired* token. The auth layer therefore cannot be a one-shot "grab a token at login and cache it" — it must expose a per-call accessor that returns a currently-valid (auto-refreshing) token so each socket reconnect handshakes with a live JWT.

RESEARCH Pattern 7 anticipated this with the `oidc-spa` library but assumed a `createReactOidc` / `beforeLoadFn` API surface. The 07-02 de-risking spike resolved the installed reality: `oidc-spa@10.2.3` exposes a single `oidcSpa.createUtils()` instance yielding `useOidc` (React), `getOidc` (non-React, for the socket/api), `enforceLogin` (route guard), and `OidcInitializationGate` — and the spike confirmed it is single-instance (one underlying core feeds both the React hook and the socket accessor, so there is no dual-instance token-parity problem). The choice this ADR records was made across that 07-02 spike (instance strategy ratified) and the 07-04 wiring (the auth function reads a fresh token per reconnect).

## Considered

- **Option A — `oidc-spa@10.2.3` single `createUtils` instance (chosen)** — one `oidcSpa.createUtils({...})` instance bootstrapped from `getConfig().keycloak`; `enforceLogin` used directly as the game route's `beforeLoad` guard; the socket's auth function and `protectedFetch` read `getAccessToken()` (auto-refreshing) from the same instance's `getOidc()`. PKCE-S256, silent renewal, and the multi-tab `BroadcastChannel` election are all library-internal — zero hand-rolled token code in the app. Pros: REQ-AUTH-01/02/03 collapse to library configuration; the single-instance design (07-02 spike) means the React tree and the socket share one token source with no parity drift; `getAccessToken()` per-call gives the socket a fresh JWT on every reconnect for free; the token lives in memory (not `localStorage`), shrinking the XSS-exfiltration surface; PKCE-S256 is the library default for a public client so it cannot be misconfigured down to plain. Cons: a dependency we don't author, so its refresh/broadcast behavior is a black box we verify by observation (the 07-02 two-tab spike) rather than by reading our own code; the v10.2.3 API differs from the RESEARCH-assumed names, so the wiring had to be re-derived against the installed type surface.
- **Option B — raw `oidc-client-ts`** — the lower-level OIDC client `oidc-spa` itself builds on. We would wire `UserManager` with PKCE, configure `automaticSilentRenew`, and add our own multi-tab coordination. Pros: one less abstraction layer; full control over every OIDC knob. Cons: `oidc-client-ts` gives PKCE + silent renew but leaves the *multi-tab* coordination and the React/router integration to us — exactly the storm-prone surface (Pitfall 5) and the `beforeLoad` guard plumbing `oidc-spa` already solves; more configuration to get wrong (silent-renew iframe origin, `monitorSession`, storage backend) for a public SPA where the secure default matters more than the knob.
- **Option C — hand-rolled PKCE + refresh** — generate the verifier/challenge ourselves, persist the verifier across the redirect, exchange the code, run our own pre-expiry refresh timer, and write our own `BroadcastChannel` leader election. Pros: zero auth dependency; complete transparency. Cons: re-implements a security-critical, concurrency-sensitive protocol from scratch; it is the canonical "rolled my own auth" red flag and the precise multi-day, high-bug-density investment PITFALLS Pitfall 5 warns against; any mistake in verifier handling or refresh coordination is a security or availability bug, not a cosmetic one. Non-starter for a submission whose value is *defensible* engineering, not bravado.

## Decision

**Use `oidc-spa@10.2.3` via a single `oidcSpa.createUtils()` instance.** The game route is guarded by `enforceLogin` as its `beforeLoad`; the socket auth function and `protectedFetch` both read `getAccessToken()` (auto-refreshing) from the same instance's `getOidc()`. PKCE-S256, silent renewal, and multi-tab `BroadcastChannel` coordination are library-internal — the app contains zero hand-rolled token code.

The locked implementation is `frontend/src/auth/oidc.ts` (07-04): one `oidcSpa.createUtils()` instance exporting `useOidc` / `getOidc` / `enforceLogin` / `OidcInitializationGate` plus a `bootstrapAuth()` that lazily calls `bootstrapOidc({ implementation: "real", issuerUri, clientId, scopes: ["profile","email"] })` from `getConfig().keycloak`. The game route (`routes/index.tsx`) sets `beforeLoad: enforceLogin` while keeping the 07-03 `ssr: false`. `ws/socket.ts` is a lazy `getSocket()` singleton whose auth FUNCTION (`auth: (cb) => resolveAuthToken().then(cb)`) awaits `getOidc()` and reads `getAccessToken()` per (re)connect — a fresh, currently-valid token on every reconnect, never a cached one. `lib/api.ts` provides `apiFetch` (public) + `protectedFetch` (Authorization Bearer from `getAccessToken`, never logged).

This is the FE realization of the single-getOidc strategy the user ratified at the 07-02 checkpoint: one instance feeds both the React components (`useOidc`) and the imperative socket/api accessors (`getOidc`), so there is no second OIDC core and no second refresh mechanism to coordinate against the first.

### Why NOT hand-rolled (Option C) or raw `oidc-client-ts` (Option B)

The decisive argument is that REQ-AUTH-02 and REQ-AUTH-03 are concurrency-correctness requirements, not feature requirements, and the library already solves them correctly. Silent renewal must fire before expiry without a visible interruption; multi-tab coordination must guarantee that N tabs produce exactly one refresh per rotation. Hand-rolling either (Option C) re-implements a security-critical protocol whose failure modes are the refresh storm (Pitfall 5) and token-handling bugs — the opposite of defensible. Raw `oidc-client-ts` (Option B) still leaves the multi-tab election and the router-guard integration to us, which is the storm-prone part. `oidc-spa` provides PKCE-S256, silent renew, and the `BroadcastChannel` election as library configuration with zero hand-rolled token code, and the 07-04 grep confirms it: `auth/oidc.ts` contains no `setInterval`, no `setTimeout`, and no `BroadcastChannel` — REQ-AUTH-02/03 are satisfied entirely inside the library. The 07-02 spike additionally disproved the dual-instance parity worry (one `createUtils` instance feeds both surfaces), removing the only architectural reason we might have reached for a lower-level client.

## Consequences

- **Locked in (one OIDC instance)**: there is exactly one `oidcSpa.createUtils()` instance; `useOidc` (React) and `getOidc` (socket/api) read from it. No second OIDC core, no second token source. A future plan that introduces a second instance reintroduces the token-parity problem the single-getOidc strategy eliminated.
- **Locked in (no hand-rolled token code)**: PKCE-S256, silent renewal, and multi-tab coordination are library-internal. No hand-rolled refresh timer or `BroadcastChannel` may be added to `auth/oidc.ts` — a second mechanism causes the refresh storm (Pitfall 5; see ADR-027, which is the standing guard against exactly this). Code review rejects any `setInterval`/`setTimeout`/`BroadcastChannel` in the auth module.
- **Locked in (fresh token per reconnect)**: the socket auth is a FUNCTION reading `getAccessToken()` per (re)connect, never a captured token string — every reconnect handshakes with a currently-valid JWT, satisfying the WS "validate once at handshake, no mid-connection re-auth" rule (CLAUDE.md, ADR-021). A future change that caches the token at first connect and reuses it across reconnects would hand a stale JWT to a reconnect after expiry and be rejected at the handshake.
- **Locked in (token in memory, not `localStorage`)**: the access token lives in memory, shrinking the XSS-exfiltration surface; this is `oidc-spa`'s default and we do not override it to a persistent store.
- **Foreclosed**: Option B raw `oidc-client-ts` (still leaves multi-tab + router-guard plumbing to us — the storm-prone surface); Option C hand-rolled PKCE/refresh (re-implements a security-critical, concurrency-sensitive protocol; the canonical "rolled my own auth" red flag).
- **Operational cost**: one runtime dependency (`oidc-spa@10.2.3`, already in the 07-02 dep set — no new install, threat T-07-SC honored). The realm must expose `crash-game-client` as a public PKCE-S256 client (already true per the locked Keycloak facts). Live login + socket handshake is exercised at the phase live-smoke / Phase 10 Playwright.
- **API-drift note for future readers**: RESEARCH Pattern 7 assumed `createReactOidc` / `beforeLoadFn`. The installed v10.2.3 surface is `oidcSpa.createUtils()` → `{ bootstrapOidc, useOidc, getOidc, OidcInitializationGate, enforceLogin }`; the logged-in `getOidc()` exposes `getAccessToken(): Promise<string>` (auto-refreshing), NOT `getTokens()`; the guard is `enforceLogin` used directly as `beforeLoad`, NOT a `beforeLoadFn({...})` factory. This was flagged in the 07-02 spike and wired in 07-04 against the installed types.
- **Anticipated recruiter question**: "Why didn't you implement PKCE yourself to show you understand it?" — defended: understanding PKCE is shown by choosing the *correct* profile (Authorization Code + PKCE S256 for a public client) and by knowing the failure mode that makes hand-rolling dangerous (the multi-tab refresh storm, Pitfall 5); re-implementing a security protocol the realm and a battle-tested library already get right is the red flag, not the credential. The defensible move is the secure default plus the verification (07-02 two-tab spike) that the storm does not occur.

Cross-references: ADR-012 (per-service JWT validation via cached JWKS — the server side this client feeds); ADR-021 (single lobby + JWT-at-handshake — why the socket needs a fresh token per reconnect); ADR-027 (multi-tab refresh via `oidc-spa` `BroadcastChannel` — the standing guard against a second refresh mechanism); REQ-AUTH-01/02/03; RESEARCH Pattern 7; PITFALLS Pitfall 5 (refresh storm); 07-02 spike (single-getOidc ratification + API-drift note); 07-04 (the locked `auth/oidc.ts` + `ws/socket.ts` + `lib/api.ts` wiring).

## Alternatives Rejected

- **Option B — raw `oidc-client-ts`** — gives PKCE + silent renew but leaves multi-tab coordination and the router-guard integration to us, which is the storm-prone surface `oidc-spa` already solves; more secure-default knobs to get wrong for a public SPA.
- **Option C — hand-rolled PKCE + refresh + `BroadcastChannel`** — re-implements a security-critical, concurrency-sensitive protocol from scratch; the canonical "rolled my own auth" red flag and the multi-day, high-bug-density refresh-storm surface PITFALLS Pitfall 5 warns against.
