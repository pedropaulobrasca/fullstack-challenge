# ADR-025: Canvas 2D (rAF + `devicePixelRatio` + `clearRect`) for the crash curve over SVG / WebGL

**Status**: Accepted
**Date**: 2026-05-29
**Phase**: 7

## Context

The center of the game page is a continuously-updating multiplier curve. It must render at 60 fps with crisp output on retina/HiDPI displays while the multiplier climbs every frame, then freeze cleanly on crash. This is REQ-FE-02 (Canvas 2D at 60 fps via `requestAnimationFrame`, `devicePixelRatio` scaling, `clearRect` between frames), it is the visual half of REQ-FE-03 (the locally-computed multiplier the curve plots), and CLAUDE.md §Frontend already states the renderer rule outright: "Multiplier curve on Canvas 2D with `requestAnimationFrame` + `devicePixelRatio` + `clearRect`. No SVG, no WebGL." Phase 7 CONTEXT records the same as decision D-05. So the question this ADR resolves is not "what should the renderer be" — that was locked in CLAUDE.md before Phase 7 — but the defensible *rationale* for the lock, which the arguição probes.

The rendering surface has three properties that make the choice consequential. First, it is *continuous*: the curve geometry changes every single frame for the ~7-15 s of a RUNNING round, so this is not a static chart that paints once. Second, it must be *retina-crisp*: a 1× backing store stretched onto a 2× display gives a visibly soft line, so the backing store has to scale by `devicePixelRatio`. Third, it must *freeze on the server-authoritative crash value*, not on the last animation frame the rAF loop happened to draw (T-07-16) — the displayed crash multiplier is `round.crashValue` from the WS `round:crashed` event, not whatever the local interpolation reached.

The renderer also sits inside the re-render-scoping discipline of ADR-026: the rAF loop writes the rendered multiplier to the isolated multiplier store and the canvas draws *off the React render path* (reading store state via `getState()` inside the frame callback) so the component does not re-render 60×/second. That constraint interacts with the renderer choice — a DOM-based approach (SVG) would put 60 fps of mutation back onto the DOM/React layout path the isolation was designed to avoid.

## Considered

- **Option A — Canvas 2D (rAF + `devicePixelRatio` + `clearRect`) (chosen)** — a `<canvas>` whose backing store is sized `cssW/H * devicePixelRatio`; an rAF loop that, each frame, `setTransform(dpr,...)` then `clearRect` FIRST, then strokes the multiplier path. Pros: the immediate-mode model is the natural fit for a per-frame-redrawn curve — clear, recompute, stroke, with no retained scene graph to diff; `devicePixelRatio` backing-store scaling gives crisp retina output with one `setTransform`; it stays entirely off the DOM/React layout path (ADR-026 isolation holds — the canvas pixels update without a component re-render); it is the lowest-complexity option that meets every requirement; and it is exactly the documented lock (CLAUDE.md §Frontend, D-05). Cons: immediate-mode means *we* own the draw loop (sizing, dpr, clear, stroke) rather than declaring shapes — but that ownership is small and lives in one pure `drawCurve` function.
- **Option B — SVG path** — render the curve as an SVG `<path>` whose `d` attribute updates each frame. Pros: declarative, resolution-independent by construction (vector, no dpr math), trivially styleable with CSS. Cons: every frame mutates a DOM node, forcing the browser to re-parse the path and re-run layout/paint for the SVG subtree at 60 fps — DOM mutation at frame rate is the classic jank source for a continuously-updating path, and it pushes 60 fps of work back onto the DOM/React path that ADR-026's store isolation exists to keep quiet. The declarative win is irrelevant for a single animated line and is paid for in per-frame layout cost.
- **Option C — WebGL** — render the curve via a WebGL context (shaders, vertex buffers). Pros: GPU-accelerated, scales to enormous geometry and effects. Cons: massive over-engineering for a single 2D line — it adds shader authoring, context-loss handling, and buffer management with zero payoff at this geometry scale; the complexity is real and the benefit is nil for one curve at 60 fps, which Canvas 2D already hits comfortably.

## Decision

**Canvas 2D with `requestAnimationFrame` + `devicePixelRatio` backing-store scaling + `clearRect`-first each frame.** SVG is rejected because mutating a DOM path at 60 fps janks and re-introduces the per-frame DOM/layout cost the ADR-026 isolation removes; WebGL is rejected as over-engineering for a single 2D line. Canvas 2D is the documented, sufficient, lowest-complexity choice (CLAUDE.md §Frontend, D-05).

The locked implementation is the 07-06 curve feature:

- `features/curve/draw-curve.ts` — a pure `drawCurve(ctx, { width, height, dpr, multiplier, status, crashValue, reducedMotion })` that `setTransform(dpr,...)` then `clearRect` FIRST every frame, strokes a `createLinearGradient` emerald → cyan path with a SINGLE `shadowBlur` glow (zeroed when `reducedMotion`), renders crash-red on `CRASHED`, and draws the central value in `Fira Code` (64px desktop / 44px mobile). All color and curve-geometry literals (margin, sample count, scale, line width) live ONLY here.
- `features/curve/use-raf-curve.ts` — the rAF loop that runs while `round.status === 'RUNNING' && roundStartedAt != null`, computes the local multiplier, and writes it via the isolated multiplier store; on `CRASHED` it writes `round.crashValue` once (T-07-16, server-authoritative freeze — not the last interpolation frame) then `cancelAnimationFrame`; a status-transition subscription re-arms/cancels the loop imperatively, and cleanup unsubscribes + cancels (T-07-17, no leak).
- `components/crash-curve.tsx` — hosts the `<canvas>`, sizes `canvas.width/height = cssW/H * devicePixelRatio` via `ResizeObserver`, reads `prefers-reduced-motion` from `matchMedia`, mounts `useRafCurve`, and draws inside the loop's `onFrame` callback reading `round.store` via `getState()` so it never re-renders 60×/second (ADR-026 isolation extended to the pixel pipeline).

The 07-06 grep evidence confirms the lock held: no SVG and no WebGL anywhere in the curve feature/component, `clearRect` present, `devicePixelRatio` present in the component.

### Why NOT SVG (Option B) or WebGL (Option C)

SVG's declarative model is a liability here, not an asset: the curve is redrawn every frame, so an SVG path would mutate a DOM node 60×/second, forcing path re-parse + layout/paint on the SVG subtree at frame rate — the textbook jank pattern for a continuously-animated path — and it would put that work back on the DOM/React layout path that ADR-026's isolated multiplier store deliberately keeps idle. Canvas 2D's immediate-mode "clear then stroke" sidesteps both: there is no retained node to mutate and no layout to re-run, just pixels. WebGL would meet the frame-rate target but at the cost of shaders, context-loss handling, and buffer management for a single 2D line — complexity with no payoff at this geometry. Canvas 2D is the only option that is simultaneously fast enough (60 fps comfortably), crisp on retina (one `setTransform(dpr)`), and minimal in complexity, which is why CLAUDE.md locked it.

## Consequences

- **Locked in (Canvas 2D only)**: the multiplier curve renders on a `<canvas>` 2D context with rAF + `devicePixelRatio` + `clearRect`-first. No SVG curve path and no WebGL renderer may be added — a future plan that reaches for either re-opens this decision (and, for SVG, reintroduces the per-frame DOM cost ADR-026 removed).
- **Locked in (dpr backing-store scaling)**: the canvas backing store is sized `cssW/H * devicePixelRatio` (via `ResizeObserver` for responsive resizes); the 2D context is `setTransform(dpr,...)` so all draw coordinates stay in CSS pixels. Dropping the dpr scale gives a soft line on retina.
- **Locked in (clear-first invariant)**: every frame `clearRect`s before stroking; omitting it smears prior frames. The pure `drawCurve` owns this so it cannot be skipped by a caller.
- **Locked in (server-authoritative freeze)**: on `CRASHED` the curve freezes on `round.crashValue` (the WS-delivered server crash point), written once, NOT on the last local interpolation frame (T-07-16). The local rAF interpolation is for smoothness during RUNNING only; the terminal value is the server's.
- **Locked in (off-React-render draw)**: the canvas draws inside the rAF `onFrame` callback reading store state via `getState()`, so the host component does not re-render 60×/second — the ADR-026 isolation extended to the pixel pipeline. A future change that drives the canvas from React state (re-rendering per frame) would defeat both this ADR and ADR-026.
- **Locked in (geometry/color literals localized)**: all color and curve-geometry constants (margin, samples, scale, line width, glow) live ONLY in `draw-curve.ts`; the business constants (`growthRate`, EWMA `alpha`) are never literal in the feature (grep clean), they come from typed config (ADR-004 discipline carried to the FE).
- **Reuse forward**: the same Canvas 2D renderer is the single source of truth for Phase 8's deterministic replay (REQ-REPLAY-*) — replay animates a past round's curve at real-time speed using THIS renderer, not a separate playback path (anticipated Phase 8 ADR). Picking a second renderer for replay would break the byte-match-the-live-render guarantee Phase 8 asserts.
- **Reduced-motion**: the single `shadowBlur` glow is zeroed under `prefers-reduced-motion`; the curve still renders, just without the glow — one of the four sanctioned, reduced-motion-gated juice moments (07-08), never a particle storm.
- **Operational cost**: none new — Canvas 2D is a browser primitive, no dependency. The rAF loop is leak-free (T-07-17: cleanup unsubscribes + `cancelAnimationFrame`).
- **Foreclosed**: Option B SVG path (60 fps DOM mutation janks + re-introduces the per-frame layout cost ADR-026 removes); Option C WebGL (shader/context complexity with no payoff for one 2D line).
- **Anticipated recruiter question**: "Why not SVG — it's simpler and declarative?" — defended: declarative is an asset for static charts and a liability for a per-frame-redrawn curve, where mutating the DOM path at 60 fps janks and re-loads the layout path the store isolation (ADR-026) keeps idle; immediate-mode Canvas "clear then stroke" is the correct model for continuous animation, and dpr scaling gives the retina crispness SVG would otherwise be claimed to provide.

Cross-references: ADR-026 (isolated multiplier store — the rAF loop writes only that store, and the canvas draws off the React render path); ADR-022 (30 Hz server tick + 60 fps client interpolation — the curve is the 60 fps client half, computing the local multiplier between ticks); REQ-FE-02 / REQ-FE-03; CLAUDE.md §Frontend (the documented lock); Phase 7 CONTEXT D-05; 07-06 (the locked `draw-curve` / `use-raf-curve` / `crash-curve` implementation); Phase 8 REQ-REPLAY-* (the renderer reused by replay).

## Alternatives Rejected

- **Option B — SVG path** — mutating a DOM path at 60 fps re-parses the path and re-runs layout/paint at frame rate (classic jank for a continuously-animated line) and pushes per-frame work back onto the DOM/React layout path ADR-026's store isolation exists to keep quiet; the declarative win is irrelevant for one animated curve.
- **Option C — WebGL** — shader authoring, context-loss handling, and buffer management for a single 2D line; real complexity, zero payoff at this geometry — over-engineering.
