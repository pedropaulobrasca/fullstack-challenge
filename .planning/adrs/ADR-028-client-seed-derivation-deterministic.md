# ADR-028: Client-Seed Derivation — Deterministic from Previous Round Close (Reaffirmed)

**Status**: Accepted
**Date**: 2026-05-30
**Phase**: 8

## Context

Phase 8 ships two new client-side surfaces that re-derive crash points from the seed/clientSeed/nonce triple in the browser: the `VerificationDrawer` chain-proof (Plan 08-05 — verifies that `SHA-256(prevRound.serverSeed) === prevRound.seedHash`) and the `/verify/$roundId` route (Plan 08-06 — runs the full HMAC + Bustabit formula via `crypto.subtle` and compares against the server's reported crash point while explicitly ignoring the server's `matches` field). Both surfaces only work if the `clientSeed` for any settled round can be reconstructed deterministically from data the player can independently observe; if `clientSeed` were a server-private input the in-browser verification would either reduce to "trust the server's `clientSeed` echo" (defeating the point) or stall on missing data.

The locked derivation already exists at `services/games/src/application/client-seed.derivation.ts` and was canonized in Phase 4 ADR-015: round N's `clientSeed = SHA256(prevRound.id + ":" + prevRound.crashedAt.toISOString())`, with the genesis round using `SHA256(GENESIS_CLIENT_SEED)` (the deployment-fixed `"crash-game-genesis-client-seed"` constant in `packages/contracts/src/provably-fair/formulas.constants.ts`). The verify endpoint returns the persisted `clientSeed` directly so the browser does not need to re-derive it for the equality check — but the structural property that *makes* the in-browser verification meaningful is that the `clientSeed` *could* have been recomputed from public-before-BETTING-opens prior-round data. The recruiter's arguição can probe this: "show me that the server cannot rotate `clientSeed` after seeing bets."

Phase 8 also re-opens, in passing, the question of whether the player should be able to *supply* their own `clientSeed` — a stretch surface that some commercial crash games offer (player types entropy into a text box; the server combines it with the chain). The ROADMAP keeps this in the stretch backlog, but the Phase 8 plans had to confirm the v1 posture before building the verification UX on top of it: a player-contributed seed would change the entire drawer/`/verify` flow (the seed would no longer be derivable from prior-round data; the verify endpoint would have to return the player-supplied bytes; the drawer would need a "your seed for round N" input). Recording that confirmation here as a standing ADR — rather than letting it live only inside Phase 4's ADR-015 which predates the Phase 8 surfaces — gives a future plan a single citable lock when it considers touching the seed surface.

This is the seed half of the four Phase 8 decisions (D-04 in `08-CONTEXT.md`). The ROADMAP anticipated this under the label "ADR-023", but Phases 5/6/7 consumed 019..027 before Phase 8 closed; the decision takes the next-free number ADR-028 with the renumber note recorded in Phase 8's closeout.

## Considered

- **Option A — Deterministic from prior-round close, no player input (chosen, REAFFIRMS Phase 4)** — `clientSeed_N = SHA256(prevRound.id + ":" + prevRound.crashedAt.toISOString())`, with the genesis exception. Pros: the binding material is public before round N's BETTING window opens (round N-1's UUID was generated at round N-1's open, well before round N exists; the CRASHED-time stamp was server-stamped at round N-1's crash event, also before round N's BETTING), so the operator cannot pick `clientSeed_N` after seeing bets; the browser can independently recompute it from `/games/rounds/$prevId/verify` data — the structural anti-collusion property the recruiter can probe; the drawer's chain proof (`SHA-256(prev.serverSeed) === prev.seedHash`) and the `/verify` route's full re-derivation both stand on this determinism; zero change from Phase 4 (the implementation is byte-stable); no new UX surface (the player's session is unaffected). Cons: the player does not contribute entropy — defended by the per-round binding to prior public CRASHED data being the operator-untamperable axis, and by the chain commitment (ADR-016) being the second axis.
- **Option B — Player-contributed `clientSeed` per round** — the player types a string (or the FE generates one); the server combines it with the chain to derive the crash point; the verify endpoint returns the player's bytes. Pros: preserves player agency over one HMAC input; matches some commercial crash UX. Cons: requires an entire new UX (an input on the bet panel, a "your seed for round N" persistence/echo, a 'seed-rotation' policy when a player joins mid-round); requires a new saga step ("accept-player-seed-before-BETTING-closes" with a deadline + default-on-timeout); collapses the binding-to-prior-CRASHED-time anti-collusion proof (the per-round message is now player-controlled, which is fine, but the chain-of-rounds verification surface in the drawer disappears because there is no prior-round derivation chain to follow); doubles the verification UX surface (the player has to verify both that the server used the seed *they* supplied AND that the chain commitment is preserved); requires a v1 ADR to enumerate the policy choices (single seed for a session, per-round, must-be-set-before-bet, default-derive-on-empty); ROADMAP keeps it as REQ-STRETCH-adjacent.
- **Option C — `randomBytes(32)` per round (no derivation, no input)** — the server picks a fresh random `clientSeed` each round. Pros: no derivation code at all. Cons: forecloses chain verification (there is no public-before-BETTING-opens binding — the operator could roll `clientSeed_N` after seeing the bets in BETTING and the player cannot detect it); the `/verify` route would still work for the *current* round's seed/nonce equation but the drawer's prior-round chain-proof would have no structural reason to hold; the recruiter would land on "why is `clientSeed` not bound to something the operator cannot pick after bets?" with no defensible answer.

## Decision

**Option A — `clientSeed_N` is deterministically derived from prior-round close (`SHA256(prevRound.id + ":" + prevRound.crashedAt.toISOString())`), genesis uses the deployment-fixed constant, no player input.** Player-contributed seeds are explicitly out of v1 scope and remain on the stretch backlog. The decision reaffirms the Phase 4 lock (ADR-015) in the Phase 8 verification context, where new client-side surfaces depend on the determinism property being a citable invariant rather than an implementation detail.

The locked surfaces are:

- `services/games/src/application/client-seed.derivation.ts` — the pure function `deriveClientSeed(prevRound: PreviousRoundClose | null): string` byte-stable from Phase 4; round 1 returns `SHA256(GENESIS_CLIENT_SEED)`, round N returns `SHA256(prev.id + ":" + prev.crashedAt.toISOString())`.
- Plan 08-05 `VerificationDrawer` — fetches `/games/rounds/$prevId/verify` and asserts `SHA-256(prevRound.serverSeed) === prevRound.seedHash` via the browser-safe `sha256OfHexEncodedSeed` from `@crash/contracts/provably-fair-browser` (ADR-030). The chain step works *because* the prior round's `clientSeed` was determined by the round before it — the operator cannot rotate it.
- Plan 08-06 `/verify/$roundId` route — uses the `clientSeed` from the verify endpoint response directly (no in-browser re-derivation needed), but the structural property that the `clientSeed` *could have been* recomputed from prior-round data is what defends the verdict against arguição.
- Plan 08-09 README walkthrough — the recruiter-runnable example reproduces 2.94 from `(serverSeed = 0x0…01, clientSeed = "test", nonce = 0n)`; the literal `"test"` works in the example because it is the fixed Phase 4 test fixture (`packages/contracts/tests/derive-crash-point.test.ts`), not a player input.

### Why NOT player-contributed seeds (Option B)

The decisive argument is scope and verification-surface integrity. A player-contributed seed is a real feature with real value (player agency) but is a *different* product from the v1 commitment-chain-only model: it requires a new bet-panel UX, a per-round persistence + echo path on the verify endpoint, a saga-step for "accept player seed before BETTING closes" with a deadline + default-on-timeout policy, and a *second* verification UX in the drawer ("did the server use the seed I supplied?"). The v1 anti-collusion proof rests on two locked axes — the chain commitment (ADR-016, published at bootstrap, the operator commits before any round opens) and the per-round binding to prior CRASHED data (this ADR) — which together cover the operator-cannot-collude-after-bets property the recruiter probes. Adding a third axis (player entropy) does not strengthen that proof in v1; it adds UX surface and a saga branch we have not budgeted for. The stretch backlog captures it for v2 with a clean upgrade path: ADR-028 is superseded by a future ADR if and when player-supplied seeds ship.

### Why NOT fresh random per round (Option C)

`randomBytes(32)` for `clientSeed` each round would defeat the entire Phase 8 verification surface: the drawer's chain proof depends on the prior round's `clientSeed` being recomputable from the round-before-that, which in turn closes the audit chain back to the genesis constant; a fresh random `clientSeed` per round breaks that chain at every link and reduces the in-browser verification to "trust the server's echo of `clientSeed`". The verify endpoint would still emit a `MATCH` for the current-round HMAC equation, but the structural anti-collusion property — that the operator cannot rotate `clientSeed_N` after seeing the bets in BETTING — would vanish, and the recruiter's question "what stops you from picking `clientSeed_N` after seeing my bet?" would have no defensible answer.

## Consequences

- **Locked in (deterministic derivation)**: `clientSeed_N` is `SHA256(prevRound.id + ":" + prevRound.crashedAt.toISOString())` for N ≥ 2; genesis is `SHA256(GENESIS_CLIENT_SEED)`. The function is pure, lives in `services/games/src/application/client-seed.derivation.ts`, and is byte-stable from Phase 4 — no Phase 8 work changed it.
- **Locked in (no player input in v1)**: there is no bet-panel input for `clientSeed`, no per-round player-seed persistence column on `rounds`, no saga step for "accept player seed before BETTING closes". The bet panel UX assumes the seed is server-derived.
- **Locked in (Phase 8 surfaces stand on the determinism)**: the `VerificationDrawer` chain proof (Plan 08-05), the `/verify/$roundId` route (Plan 08-06), and the README walkthrough (Plan 08-09) all defend their verdicts against the recruiter's "could the operator have picked `clientSeed_N` after bets?" question by citing this ADR + the public-before-BETTING-opens binding material.
- **Foreclosed (Option B)**: player-contributed `clientSeed` requires a saga branch + a bet-panel UX + a v2 verification surface; an ADR supersession is required to land it. The stretch backlog (REQ-STRETCH-adjacent — not currently a numbered REQ-ID) captures the intent.
- **Foreclosed (Option C)**: per-round random `clientSeed` foretokens the chain-proof surface and reduces in-browser verification to "trust the server's echo" — would defeat REQ-FE-09/10 by design.
- **Anticipated recruiter question**: "Why doesn't the player contribute entropy to the seed?" — defended: the v1 anti-collusion proof rests on the chain commitment (ADR-016) + the per-round binding to prior CRASHED-time data (this ADR + ADR-015); the operator cannot rotate `clientSeed_N` after seeing bets because round N-1's UUID was generated before round N existed and `crashedAt` was stamped before round N's BETTING opened; adding a player-input axis is on the stretch backlog (v2) and would supersede this ADR cleanly; the drawer and `/verify` route assume this determinism and the recruiter can reproduce it from `curl /verify/$prevId` data in their own shell (Plan 08-09 walkthrough).

Cross-references: ADR-015 (Phase 4 — the original lock; this ADR is the Phase 8 reaffirmation in the verification-UX context), ADR-016 (chain commitment — the other anti-collusion axis), ADR-030 (browser-safe `@crash/contracts/provably-fair-browser` subpath — how the drawer hashes the prior server seed), Plan 08-05 SUMMARY (VerificationDrawer chain proof), Plan 08-06 SUMMARY (`/verify/$roundId` route), Plan 08-09 SUMMARY (recruiter README walkthrough); REQ-FE-09 (drawer), REQ-FE-10 (`/verify` route), REQ-FAIR-03 (Bustabit-canon formula).

## Alternatives Rejected

- **Option B — Player-contributed `clientSeed`** — requires a new bet-panel UX, a saga step for accept-before-BETTING-closes with deadline + default-on-timeout, a per-round player-seed persistence + echo on the verify endpoint, and a second verification surface in the drawer; adds real scope without strengthening the v1 anti-collusion proof which already stands on two locked axes (chain commitment + per-round binding to prior CRASHED data); kept in the stretch backlog for a clean v2 supersession.
- **Option C — `randomBytes(32)` per round** — forecloses the drawer's chain-proof surface (no prior-round derivation to follow), reduces in-browser verification to "trust the server's `clientSeed` echo", and removes the operator-cannot-rotate-after-bets defense — the central anti-collusion property Phase 8 verification builds on.
