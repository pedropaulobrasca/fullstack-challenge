# ADR-029: Replay Reuses Production Canvas Renderer via Driver Injection

**Status**: Accepted
**Date**: 2026-05-30
**Phase**: 8

## Context

REQ-REPLAY-03 requires the historical-round replay surface to reuse the production Canvas 2D renderer (locked by Phase 7 ADR-025) — no separate playback code path. The ROADMAP success criterion 4 then layers a stronger property on top: the replay must reproduce a past round byte-for-byte from `(serverSeed, clientSeed, nonce, bets[])`, and the rendered multiplier values at every sample point must equal the original frame samples. That equality is only structurally provable if the *same* `drawCurve` function — pixel-for-pixel — paints both the live and the replay frame; a copy-pasted "replay curve" with even cosmetically-different sweep math would defeat the byte-match guarantee at the source.

The Phase 7 renderer is three layers (07-06 plan):

- `features/curve/draw-curve.ts` — pure `drawCurve(ctx, { width, height, dpr, multiplier, status, crashValue, reducedMotion })`. Pixel-pipeline, no I/O, no time.
- `features/curve/use-raf-curve.ts` — the rAF loop that reads live state (round status, `roundStartedAt`, server tick, EWMA-reconciled clock offset), computes the local multiplier each frame via `localMultiplier(roundStartedAt, serverOffsetMs)`, and writes it via `useMultiplierStore.getState().setRendered(...)` — the only `setRendered` call site in the live game. On `CRASHED`, the loop writes `round.crashValue` once (server-authoritative freeze, T-07-16) and cancels.
- `components/crash-curve.tsx` — hosts the `<canvas>`, sizes the backing store by `devicePixelRatio` via `ResizeObserver`, mounts `useRafCurve`, and draws inside the loop's `onFrame` callback reading store state via `getState()` so the host component does not re-render 60×/second (ADR-026 isolation extended to the pixel pipeline).

The replay needs to drive the same `drawCurve` from a deterministic time-stepper instead of the live multiplier store: feed a `(t, speed) → multiplier` function (the pure `sampleReplayMultiplier`) into the same rAF loop and let it paint the same canvas. The Phase 8 question this ADR answers is *how* to plug a replay-time-stepper into a renderer that was authored to read live stores — without forking the draw code, without doubling the maintenance surface, and without letting the byte-match property degrade to "we tried to keep them in sync".

The ROADMAP anticipated this under the label "ADR-024", but Phases 5/6/7 consumed 019..027 before Phase 8 closed; the decision takes the next-free number ADR-029 with the renumber note recorded in Phase 8's closeout.

## Considered

- **Option A — Driver-injection seam on `useRafCurve` + optional `driver` prop on `CrashCurve` (chosen, locked by Plans 08-03 + 08-07)** — refactor `useRafCurve` to accept an optional `RafCurveDriver` object with `{ multiplier(): number, status(): RoundStatus, crashValue(): number | null, shouldStop(): boolean }`. The live default-driver reads `roundStartedAt + serverOffsetMs + useMultiplierStore` exactly as before (zero-diff for Phase 7 callers — `routes/index.tsx` passes nothing, the live game gets the live driver). The replay path builds a `makeReplayDriver({ roundId, growthRate, crashPoint })` that returns a driver whose `multiplier()` calls the pure `sampleReplayMultiplier({ startedAtWall, speed, paused }, t)` and whose `status()` flips to `CRASHED` past `crashTimeMs(growthRate, crashPoint)`. The `ReplayModal` (Plan 08-07) mounts the SAME `<CrashCurve />` with `driver={replayDriver}` and the same `drawCurve` paints both surfaces. Pros: the byte-match guarantee becomes a property of the renderer *itself*, not a duplicate implementation kept in sync by discipline — a regression in `drawCurve` affects both surfaces identically; the Phase 7 caller is zero-diff (Plan 08-03 Tests 1 + 2 prove all 5 Phase 7 crash-curve tests stay green); the determinism E2E test (Plan 08-08) is provable in pure math because both code paths reduce to `multiplierAt(t, growthRate)` capped at `crashPoint` — no browser fixture needed; the speed selector (1x/2x/4x) becomes a property of the driver's closure (`useReplayStore.getState().speed`) without rebuilding the stepper or perturbing the renderer; the four overlays + scrim + modal chrome stay in the modal, not in the renderer. Cons: introduces a small typed interface (the `RafCurveDriver` shape) into the curve feature and one optional prop on `CrashCurve`; the live default-driver factory is one file's worth of indirection; the driver-aware path inside `CrashCurve` has to read `status()` and `crashValue()` from the driver when one is supplied so the CRASHED freeze paints from the replay's stepper, not the round store — locked by Plan 08-07.
- **Option B — Separate `<ReplayCurve />` component with copy-pasted draw logic** — write a sibling component that duplicates the `drawCurve`/`useRafCurve`/`<canvas>` pipeline reading replay state directly. Pros: zero changes to the live renderer. Cons: forecloses the byte-match guarantee by construction — the two `drawCurve` implementations would have to be kept aligned by code review, and the determinism E2E (Plan 08-08) would have to assert against a *second* implementation's per-frame output, which is not the guarantee REQ-REPLAY-03 + criterion 4 ask for; doubles the maintenance surface (every dPR / glow / freeze-color / gradient change has to be made twice and provably aligned); the recruiter's "show me the replay uses the same renderer" question reduces to "we copied it" — defensively weak.
- **Option C — Pre-sample the entire curve into an array, then animate by index** — at replay open, compute `multipliers[]` for all frames at 1x, then play the array back at the selected speed. Pros: trivially-deterministic per-array-entry. Cons: forecloses the speed selector flexibility (1x/2x/4x) cleanly — speed changes have to interpolate or resample mid-animation; the renderer would no longer be reading "local multiplier at wall-clock t" the way the live game does, breaking the structural equivalence the byte-match guarantee depends on; this is the "render a movie" anti-pattern flagged in 08-RESEARCH § Anti-Patterns — the replay loses the rAF/EWMA shape that makes it pixel-equivalent to live, and the determinism E2E would have to assert against a discrete-array model that does not match the live continuous-formula model.

## Decision

**Option A — driver-injection seam on `useRafCurve` + optional `driver` prop on `CrashCurve`; the SAME `drawCurve` paints both live and replay.** Separate `<ReplayCurve />` is rejected because it forecloses the byte-match guarantee by construction; pre-sampled arrays are rejected because they break the structural equivalence to the live rAF/EWMA shape and lose the speed-selector flexibility.

The locked implementation is the 08-03 + 08-07 driver seam:

- `features/curve/use-raf-curve.ts` accepts an optional `RafCurveDriver`; when omitted (the live default — `routes/index.tsx` passes nothing) it builds the default driver from `useRoundStore + useMultiplierStore + serverOffsetMs + roundStartedAt` and the Phase 7 behavior is byte-identical (all 5 Phase 7 crash-curve tests green, Plan 08-03 Tests 1 + 2).
- `features/replay/replay-driver.ts` exports `makeReplayDriver({ roundId, growthRate, crashPoint })` returning a `RafCurveDriver` whose `multiplier()` calls the pure `sampleReplayMultiplier(state, t)` where `state` reads `useReplayStore.getState()` (live speed/paused/startedAtWall) per frame and `t = (now - startedAtWall) * speed`. `status()` flips to `CRASHED` past `crashTimeMs(growthRate, crashPoint)`. `crashValue()` returns the captured `crashPoint`. `shouldStop()` returns true past the freeze cap.
- `components/crash-curve.tsx` gained an optional `driver?: RafCurveDriver` + optional `ariaLabel?: string` prop. When the driver is supplied, the canvas draws inside the loop's `onFrame` reading the driver's `status()` and `crashValue()` so the CRASHED freeze (red flash + freeze) paints from the replay's stepper — D-05 enforced by code shape, not by parallel implementation.
- `components/replay-modal.tsx` mounts the SAME `<CrashCurve driver={replayDriver} ariaLabel="Replay of round {roundId}" />`. The modal owns the Dialog chrome, the speed toggle (`getConfig().replay.speeds` 1x/2x/4x), the overlays, and the scrim; the renderer is unchanged.

The 08-07 grep evidence confirms the lock held: `draw-curve.ts` is byte-unchanged in Phase 8; the only call site for `<CrashCurve />` in the modal is the live driver default in `routes/index.tsx` and the replay driver in `ReplayModalBody`; the determinism test (08-08) deep-equals `multiplierAt(t, growthRate)` against `sampleReplayMultiplier({startedAtWall:0, speed:1, paused:false, ...}, t)` across a 60-step × 16.6ms grid and they are equal because both code paths reduce to the same `Math.min(crashPoint, Math.exp(growthRate * t / 1000))` math — the byte-match is a pure-function property of `sampleReplayMultiplier` + `multiplierAt`, no browser fixture needed.

### Why NOT a separate `<ReplayCurve />` (Option B)

The decisive argument is that a copy-pasted draw path makes REQ-REPLAY-03 + criterion 4 a property *we promise to maintain*, not a property the *code structurally enforces*. The recruiter's whole question — "prove the replay uses the same renderer" — collapses if the answer is "we copied it and keep them aligned by code review"; a typed driver seam reduces the answer to "there is one `drawCurve`, here it is, and here are the two thin drivers that feed it" with the grep clean (one `drawCurve` definition, two `RafCurveDriver` implementations) backing the claim. The maintenance cost is the second hidden bill: every future dPR / glow / freeze-color change would have to be made twice and provably aligned, with the determinism E2E asserting against a second implementation's per-frame output — exactly the parallel-implementation drift that the byte-match guarantee is designed to forbid.

### Why NOT pre-sampled array (Option C)

Pre-sampling at replay open and animating by index is the "render a movie" anti-pattern: the replay's rendered values are now an array, not the output of `localMultiplier(t, growthRate)` evaluated per-frame, so the structural equivalence to the live rAF/EWMA shape that makes the replay pixel-equivalent to live is lost. Speed changes mid-animation become interpolation/resampling decisions; the determinism E2E has to assert against a discrete-array model that does not match the live continuous-formula model; and the speed-time equivalence (`sample(speed=k, t) === sample(speed=1, k*t)`) — the locked Plan 08-08 Test 3 — becomes a per-array-index claim instead of a property of the formula. The byte-match guarantee is cleanest when both surfaces reduce to one formula evaluated at the same `t`.

## Consequences

- **Locked in (one `drawCurve` function)**: there is one `features/curve/draw-curve.ts` painting both live and replay. A future plan that adds a sibling `replay-draw-curve.ts` re-opens this decision and reintroduces the parallel-implementation drift the driver seam exists to forbid.
- **Locked in (driver-injection seam)**: `useRafCurve` accepts an optional `RafCurveDriver`; `CrashCurve` accepts an optional `driver` prop; the live path is the default with zero-diff Phase 7 behavior (all 5 Phase 7 crash-curve tests green, Plan 08-03 Tests 1 + 2 enforce). The replay path passes `makeReplayDriver(...)` and the same canvas pipeline paints.
- **Locked in (byte-match is a renderer property, not a discipline)**: the determinism E2E (Plan 08-08) deep-equals live `multiplierAt(t, growthRate)` vs `sampleReplayMultiplier({startedAtWall:0, speed:1, paused:false, ...}, t)` across a fixed 60-step × 16.6ms grid; both reduce to `Math.min(crashPoint, Math.exp(growthRate * t / 1000))`; the equality is provable in pure math, no browser fixture.
- **Locked in (speed selector is a driver closure)**: the 1x/2x/4x ToggleGroup (ADR-031) flips `useReplayStore.getState().speed`; the driver's `multiplier()` closure reads it per frame and scales `t` by `speed`; the renderer never sees the speed and never rebuilds — the only mutation is on the replay store. The driver memoization keys are `[roundId, growthRate, crashPoint]`; `speed` and `playing` are NOT in the deps (Pitfall 7 — `startedAtWall` would reset on every speed click otherwise; Plan 08-07 SUMMARY records this).
- **Locked in (CRASHED freeze paints from driver)**: in the replay path, `<CrashCurve />` reads `status()` and `crashValue()` from the driver, not from `useRoundStore`, so the freeze color + frozen-value text paint from the replay's stepper. The live path is unchanged.
- **Foreclosed (Option B)**: a separate `<ReplayCurve />` component duplicating the draw pipeline — would reintroduce parallel-implementation drift and reduce REQ-REPLAY-03's "uses the same renderer" claim to maintenance discipline.
- **Foreclosed (Option C)**: pre-sampled multiplier array animated by index — breaks structural equivalence to the live rAF/EWMA shape; forecloses clean speed-selector semantics; the determinism E2E has to assert against a discrete-array model that does not match the live continuous-formula model.
- **Anticipated recruiter question**: "How do you prove the replay uses the same renderer the live game uses?" — defended: there is one `drawCurve`, grep clean; `<CrashCurve />` accepts an optional `driver` prop that the live route does not pass (default = live driver, byte-identical) and the replay modal passes `makeReplayDriver(...)`; the determinism E2E (Plan 08-08) deep-equals the two code paths' per-sample output across a fixed grid anchored to the Phase 4 oracle (2.94), so the byte-match guarantee is a checked property of the formula, not a maintained alignment between two implementations.

Cross-references: ADR-025 (Phase 7 — Canvas 2D + rAF + dPR + clearRect; the renderer this ADR reuses), ADR-026 (Phase 7 — isolated multiplier store; the driver seam preserves the isolation), ADR-031 (replay modal + 1x/2x/4x speed selector — the speed-as-driver-closure consumer), Plan 08-03 SUMMARY (useRafCurve refactor + zero-diff Tests 1 + 2), Plan 08-07 SUMMARY (ReplayModal + driver + speed toggle + history-chip wiring), Plan 08-08 SUMMARY (determinism byte-match E2E); REQ-REPLAY-01 (byte-for-byte reproduction), REQ-REPLAY-02 (replay modal), REQ-REPLAY-03 (renderer reuse).

## Alternatives Rejected

- **Option B — Separate `<ReplayCurve />` component with copy-pasted `drawCurve`** — forecloses the byte-match guarantee by construction (REQ-REPLAY-03 + criterion 4 reduce to "we promise to keep them aligned"); doubles the maintenance surface (every dPR / glow / freeze-color change has to land in two places and stay aligned); the recruiter's "show me the same renderer" question collapses to "we copied it".
- **Option C — Pre-sample multiplier array at replay open, animate by index** — the "render a movie" anti-pattern (08-RESEARCH § Anti-Patterns); breaks structural equivalence to the live rAF/EWMA shape; forecloses clean speed-selector semantics (1x/2x/4x become interpolation choices); the speed-time equivalence (Plan 08-08 Test 3) becomes a per-array-index claim instead of a property of the formula.
