# ADR-030: Browser-Safe `@crash/contracts/provably-fair-browser` Subpath with `crypto.subtle` (HMAC + SHA-256)

**Status**: Accepted
**Date**: 2026-05-30
**Phase**: 8

## Context

REQ-FE-10 requires the `/verify/$roundId` route to run the provably-fair algorithm fully client-side via `crypto.subtle` — no server recomputation, the verdict is computed in the browser from data the server cannot lie about. REQ-FE-09 layers on top: the verification drawer hashes the prior round's revealed `serverSeed` and compares against the stored commitment (`SHA-256(prev.serverSeed) === prev.seedHash`) — also in the browser, also without server trust. Both surfaces import the algorithm from `packages/contracts` so backend, frontend, and CLI verifier all run the same code path (the REQ-FAIR-04 invariant).

The existing `@crash/contracts/provably-fair` module shipped in Phase 4 (`packages/contracts/src/provably-fair/derive-crash-point.ts`) uses `node:crypto`'s `createHmac("sha256", serverSeed).update(message).digest("hex")` and `createHash("sha256").update(seed, "hex").digest("hex")`. This works fine on the backend and in the CLI verifier; it explodes in a Vite bundle because `node:crypto` is a Node built-in that browsers do not ship. Phase 7's spike (07-02) confirmed this empirically: importing the root `@crash/contracts` barrel into the FE bundle pulled `node:crypto` transitively and broke boot. Phase 7 worked around it by introducing the `@crash/contracts/multiplier` browser-safe subpath that exports only the pure `e^(growthRate * t / 1000)` math — but the provably-fair derivation needs HMAC + SHA-256, which `multiplier` does not provide.

There are two byte-encoding traps the browser implementation must get exactly right (08-RESEARCH Pitfalls 1 + 2; Plan 08-09 worked example documents them at the recruiter-runnable layer):

- **HMAC key encoding**: Node's `createHmac("sha256", serverSeed)` keys the HMAC on the *UTF-8 bytes of the 64-char hex string* `serverSeed`. It does NOT hex-decode `serverSeed` first. So the `crypto.subtle.importKey("raw", new TextEncoder().encode(serverSeedHexString), ...)` shape is the byte-equivalent — `TextEncoder` produces UTF-8 of the hex characters, which is what Node consumed.
- **SHA-256 chain proof encoding**: Node's `createHash("sha256").update(seed, "hex")` *hex-decodes* the 64-char hex string to its 32-byte payload before hashing. So the `crypto.subtle.digest("SHA-256", hexToBytes(serverSeedHex))` shape is the byte-equivalent — `hexToBytes` decodes hex to raw bytes, which is what Node's `update(_, "hex")` consumed.

These two encodings are *opposite* directions on the same input (`serverSeed` as a 64-char hex string): the HMAC path keeps it as text, the chain-proof path decodes it to bytes. Getting them wrong silently produces the wrong crash point (`3.02` instead of `2.94` for the Phase 4 oracle — empirically confirmed at Plan 08-09; the same `3.02` mode appears when `openssl dgst -sha256 -hmac "$SERVER_SEED"` is replaced with `-macopt hexkey:$SERVER_SEED`). The chosen browser implementation must lock both encodings in code AND in a regression test anchored to the Phase 4 oracle (`serverSeed = 0x0…01, clientSeed = "test", nonce = 0n, instantCrashBucket = 101 → crashPoint = 2.94`) so a future maintainer cannot silently re-introduce the reversed-encoding bug.

The ROADMAP anticipated this under the label "ADR-024" (D-06 in `08-CONTEXT.md`), but Phases 5/6/7 consumed 019..027 before Phase 8 closed; the decision takes the next-free number ADR-030 with the renumber note recorded in Phase 8's closeout.

## Considered

- **Option A — New `@crash/contracts/provably-fair-browser` subpath with async `crypto.subtle` (chosen, locked by Plan 08-01)** — ship a sibling subpath at `packages/contracts/src/provably-fair-browser/` that re-implements the derivation against `crypto.subtle.importKey` + `crypto.subtle.sign("HMAC", ...)` for the HMAC path and `crypto.subtle.digest("SHA-256", ...)` for the chain-proof path; export `deriveCrashPointAsync(input): Promise<number>`, `deriveCrashPointWithHmacHex(input): Promise<{crashPoint, hmacHex, first13Hex}>`, and `sha256OfHexEncodedSeed(hexString): Promise<string>`; package.json `exports` map adds `"./provably-fair-browser": "./src/provably-fair-browser/index.ts"`. Pros: keeps `node:crypto` out of the Vite bundle by isolation (the FE only imports the `/provably-fair-browser` subpath; the root barrel never reaches the FE; the Phase 7 `multiplier` subpath set the precedent); both byte-encoding contracts are anchored in source via a single shared `computeHmacHexInternal` helper (one place to read for byte semantics, one place to break for a regression); the Plan 08-01 2.94 oracle test asserts byte-for-byte equivalence with the Phase 4 server impl at the locked tuple, so a future-maintainer reversal of the two encodings fails the test immediately; the `deriveCrashPointWithHmacHex` variant returns the intermediate `hmacHex` + `first13Hex` for the `/verify` route's "show your work" verdict card; async-by-design matches `crypto.subtle`'s Promise-only API and is the canonical way to use it. Cons: introduces a parallel implementation of the formula (the math `Math.floor((100 * 2^52 - intH) / (2^52 - intH)) / 100` lives in both `provably-fair/derive-crash-point.ts` AND `provably-fair-browser/derive-crash-point.async.ts`); divergence risk mitigated by the 2.94 oracle test (asserts both produce 2.94) + colocated test file under `provably-fair-browser/` + Plan 08-08 determinism E2E which deep-equals the two formulas across a fixed grid.
- **Option B — Pure-JS `js-sha256` npm + synchronous API** — add `js-sha256` (and a sibling `js-hmac-sha256` or equivalent) to FE deps, use the synchronous API. Pros: synchronous flow (no await sprinkled through the drawer/verify route); no `crypto.subtle` Promise plumbing. Cons: hand-rolled (or third-party hand-rolled) crypto inside the bundle when the browser already ships a native, audited implementation; adds bundle weight for functionality that is already free in every supported browser; loses the `crypto.subtle` "the browser vendor audits this" defense in arguição; the byte-encoding traps are still present and the test surface is no smaller (we still need the 2.94 oracle); maintainers may assume the JS impl matches `crypto.subtle` exactly when the byte-encoding details (encoding of `update` calls, HMAC key handling) actually differ subtly across libraries — another silent-3.02 vector.
- **Option C — Vite/Rollup polyfill for `node:crypto` via a plugin (e.g., `rollup-plugin-node-polyfills` or vite `optimizeDeps.esbuildOptions.plugins`)** — keep importing from the root `@crash/contracts` barrel; have a plugin substitute a `node:crypto` browser polyfill at build time. Pros: zero changes to `@crash/contracts`. Cons: masks the bundle leak instead of fixing it — the Phase 7 spike's whole finding was "the root barrel leaks `node:crypto` into the FE bundle and this is a structural problem"; a polyfill imports a JS reimplementation of all of `node:crypto` (~30-50KB) into the bundle when the browser already has the native API; the polyfill is itself a maintenance dependency with its own byte-encoding semantics that may not match Node's; the recruiter's arguição question "why does your FE bundle ship a `node:crypto` shim?" lands on "we polyfilled instead of fixing the import boundary", which is defensively weak; future contracts additions (new derivations, new chain operations) silently leak any Node-specific behavior the polyfill happens to support but the browser does not (or vice versa).

## Decision

**Option A — new `@crash/contracts/provably-fair-browser` subpath with async `crypto.subtle` (HMAC + SHA-256), package.json `exports` map gated, two byte-encoding contracts locked in source JSDoc + tests.** Pure-JS `js-sha256` is rejected because it ships hand-rolled crypto into the bundle when the browser ships a native audited implementation, and the byte-encoding traps are not smaller; vite/rollup `node:crypto` polyfill is rejected because it masks the bundle leak instead of fixing it and ships ~30-50KB of JS reimplementation of `node:crypto`.

The locked implementation is the 08-01 subpath:

- `packages/contracts/src/provably-fair-browser/derive-crash-point.async.ts` — async `deriveCrashPointAsync(input): Promise<number>` and `deriveCrashPointWithHmacHex(input): Promise<{crashPoint, hmacHex, first13Hex}>`. Both call a single shared internal helper `computeHmacHexInternal({serverSeedHex, message})` that lives in one place and is the SOLE authority for the HMAC byte-encoding contract. The helper does `crypto.subtle.importKey("raw", new TextEncoder().encode(serverSeedHex), {name: "HMAC", hash: "SHA-256"}, false, ["sign"])` then `crypto.subtle.sign("HMAC", key, new TextEncoder().encode(message))` then converts the resulting `ArrayBuffer` to a 64-char lowercase hex string. The first 13 hex characters become `intH` via `parseInt(hex, 16)` (safe at 13 hex chars = 52 bits < `MAX_SAFE_INTEGER = 2^53 - 1`, the same range Phase 4 ADR-015 uses). The Bustabit-canon formula `Math.floor((100 * TWO_POW_52 - intH) / (TWO_POW_52 - intH)) / 100` (with the 1-in-101 instant-crash check) is recomputed in this file; constants are imported from `@crash/contracts/provably-fair`'s `formulas.constants.ts` so the bucket / `HEX_CHARS` / `TWO_POW_52` cannot drift.
- `packages/contracts/src/provably-fair-browser/sha256.async.ts` — async `sha256OfHexEncodedSeed(hexString): Promise<string>`. Does `crypto.subtle.digest("SHA-256", hexToBytes(hexString))` then converts to 64-char lowercase hex. This is the OPPOSITE encoding from the HMAC path — the hex string is hex-decoded to its 32-byte payload before hashing, matching Node's `createHash("sha256").update(seed, "hex")` byte-semantics. JSDoc on the function and the file documents the byte contract with a worked example and references the Phase 4 chain-proof code path (`packages/contracts/src/provably-fair/generate-seed-chain.ts`).
- `packages/contracts/src/provably-fair-browser/index.ts` — re-exports `deriveCrashPointAsync`, `deriveCrashPointWithHmacHex`, `sha256OfHexEncodedSeed`, `hexToBytes`, `bytesToHex`.
- `packages/contracts/package.json` `exports` map gains `"./provably-fair-browser": "./src/provably-fair-browser/index.ts"`. The root barrel is unchanged — the FE never imports it; the FE imports only the `./multiplier` (Phase 7) and `./provably-fair-browser` (Phase 8) subpaths plus the `./ws` schemas (Phase 7), so `node:crypto` never appears in the Vite dependency graph.
- `packages/contracts/src/provably-fair-browser/derive-crash-point.async.test.ts` — the Phase 4 locked-byte 2.94 oracle test: `(serverSeed = 0x0000…0001, clientSeed = "test", nonce = 0n, instantCrashBucket = 101)` MUST resolve to `crashPoint = 2.94` AND the intermediate `hmacHex` MUST equal `a9aa7f591433757689bc898f5167109490f954c4d895901f65042c332b8c050b` AND `first13Hex` MUST equal `a9aa7f5914337` (verbatim Phase 4 fixture from `packages/contracts/tests/derive-crash-point.test.ts`). Test 1 in the determinism suite (Plan 08-08) anchors the same 2.94 unconditionally with a `node:crypto` sync fallback used ONLY in the test runner (NEVER bundled). A future-maintainer reversal of the two encodings (or a substitution of `hexToBytes(serverSeed)` for the HMAC key) fails this test on the next CI run.

The 08-01 grep evidence confirms the lock held: the `@crash/contracts/provably-fair-browser` subpath imports no `node:` modules; the root `@crash/contracts` barrel was untouched; the FE bundle (`bun run build`) contains no `node:crypto` symbol; the Phase 4 2.94 oracle reproduces byte-for-byte under the new async path; the JSDoc on `computeHmacHexInternal` documents the HMAC key = UTF-8 of hex string contract, and the JSDoc on `sha256OfHexEncodedSeed` documents the opposite chain-proof = hex-decode-then-hash contract.

### Why NOT `js-sha256` (Option B)

The decisive argument is "the browser already audits crypto for free; do not ship a hand-rolled crypto into the bundle to avoid a Promise". The byte-encoding traps that Option A locks are *not smaller* in Option B — the maintainer still has to know that HMAC keys on the hex-text and SHA-256 hashes the hex-decoded bytes, and the test still needs to anchor 2.94 — so the synchronous API is the only real "win", and that win is paid for in bundle weight (every byte the user downloads to verify a round) + a non-native crypto surface in arguição. The `crypto.subtle` Promise plumbing is one `await` in three places (the drawer's `sha256OfHexEncodedSeed`, the verify route's `deriveCrashPointWithHmacHex`, the determinism test's `deriveCrashPointAsync` — all already async because they fetch the round first); there is no DX or correctness gain that justifies hand-rolled crypto in the bundle.

### Why NOT `node:crypto` polyfill (Option C)

The decisive argument is that the polyfill masks the structural problem rather than fixing it. The Phase 7 spike's finding was specifically that the root barrel leaks `node:crypto` into the FE — that is an *import-boundary* problem solved by isolating the browser-safe surface at the package level (the `exports` map gates it; Plan 08-01 ships it). A polyfill substitutes 30-50KB of JS reimplementation of `node:crypto` into the bundle, ships its own byte-encoding semantics that may not match Node's exactly (a third silent-3.02 vector on top of the two the implementation already has to lock), and leaves the root barrel's `node:crypto` import intact so any future contracts addition silently leaks whatever Node-specific behavior the polyfill happens to support — defensively the worst of the three options.

## Consequences

- **Locked in (subpath isolation)**: the FE imports ONLY `@crash/contracts/multiplier` (Phase 7), `@crash/contracts/ws` (Phase 7), and `@crash/contracts/provably-fair-browser` (this ADR). The root `@crash/contracts` barrel may keep importing `node:crypto` for backend/CLI consumers; the FE bundle never reaches it. A future plan that imports the root barrel from the FE re-opens this decision.
- **Locked in (two byte-encoding contracts in source + tests)**: the HMAC key is the UTF-8 bytes of the `serverSeed` hex string (matches Node `createHmac("sha256", serverSeed)`); the SHA-256 chain proof is the hex-decoded 32-byte payload of the `serverSeed` hex string (matches Node `createHash("sha256").update(seed, "hex")`). Both contracts are JSDoc'd in `computeHmacHexInternal` + `sha256OfHexEncodedSeed`. The Plan 08-01 2.94 oracle test fails on either reversal.
- **Locked in (single shared internal helper)**: `computeHmacHexInternal` is the only HMAC implementation in the browser subpath; `deriveCrashPointAsync` and `deriveCrashPointWithHmacHex` both call it. A regression in byte-encoding lives in one file; a regression of the formula lives in another. JSDoc on the helper points back here.
- **Locked in (CLAUDE.md frontend rule observed)**: the Vite bundle contains no `node:crypto` symbol after Plan 08-01; verified by `bun run build` + grep in the build output.
- **Locked in (async-by-design)**: the three call sites (`VerificationDrawer` chain proof via `sha256OfHexEncodedSeed`, `/verify` route via `deriveCrashPointWithHmacHex`, determinism test via `deriveCrashPointAsync`) are already async (network fetches the round first); the `await` is incidental.
- **Foreclosed (Option B)**: hand-rolled JS crypto in the bundle when the browser ships a native audited implementation; adds bundle weight + a non-native crypto surface in arguição; the byte-encoding traps are no smaller.
- **Foreclosed (Option C)**: a `node:crypto` polyfill masks the import-boundary problem instead of fixing it; ships ~30-50KB of polyfill JS for functionality the browser already has natively; introduces a third silent-3.02 vector via the polyfill's own byte-encoding semantics; leaves the root-barrel `node:crypto` import intact for future leaks.
- **Operational cost**: zero new dependencies; `crypto.subtle` is a browser primitive on the locked tier of supported browsers (per Phase 7 STACK choices). The `derive-crash-point.async.ts` parallel implementation is intentional (Option A's only structural cost) and is gated by the 2.94 oracle + Plan 08-08 determinism E2E.
- **Pitfall 4 fallback (recorded for context, not introduced by this ADR)**: the drawer surfaces a locked Alert when `crypto.subtle` is unavailable (insecure origin / non-HTTPS / older browser missing the API), telling the user to open the app via http://localhost or HTTPS. This was implemented in Plan 08-05 on top of the subpath.
- **Anticipated recruiter question 1**: "Why two encodings of the same hex string?" — defended: Node's `createHmac("sha256", serverSeed)` consumes `serverSeed` as a string and keys the HMAC on its UTF-8 bytes; Node's `createHash("sha256").update(seed, "hex")` consumes `serverSeed` as hex and hex-decodes it to 32 bytes before hashing — they are different APIs with different byte-semantics, and the browser-safe re-implementation has to honor both because both are part of the locked Phase 4 protocol; the README walkthrough (Plan 08-09) reproduces the empirically-confirmed `3.02` MISMATCH when the encodings are reversed.
- **Anticipated recruiter question 2**: "Why not `js-sha256`?" — defended: the browser ships `crypto.subtle` natively and audits it as part of the platform; shipping a JS crypto library into the bundle adds weight for functionality that is already free + replaces an audited native implementation with a hand-rolled one + does not reduce the byte-encoding test surface; the only "win" is sync flow, and the call sites are already async because they fetch the round first.

Cross-references: ADR-015 (Phase 4 — the original `deriveCrashPoint` formula + HMAC contract this subpath mirrors), ADR-028 (client-seed derivation — what the `clientSeed` input to `deriveCrashPointAsync` actually is), ADR-031 (replay modal — the replay path does NOT call `deriveCrashPointAsync` per frame; it reads the stored `crashPoint` and replays the curve to it; this subpath is consumed by the drawer + `/verify` route only), Plan 08-01 SUMMARY (subpath + tests), Plan 08-05 SUMMARY (drawer consumer), Plan 08-06 SUMMARY (`/verify` route consumer), Plan 08-08 SUMMARY (determinism E2E anchor), Plan 08-09 SUMMARY (recruiter README walkthrough documenting both encodings); REQ-FE-09, REQ-FE-10, REQ-FAIR-04 (pure-function provably-fair module).

## Alternatives Rejected

- **Option B — Pure-JS `js-sha256` library with synchronous API** — ships hand-rolled crypto into the bundle when the browser ships a native audited implementation; adds bundle weight for free-on-the-platform functionality; the byte-encoding traps still have to be locked in tests, so the only real win is sync flow — paid for in bundle weight and a non-native crypto surface in arguição.
- **Option C — Vite/Rollup `node:crypto` polyfill** — masks the import-boundary problem instead of fixing it; ships ~30-50KB of polyfill JS for functionality the browser already has natively; introduces a third silent-3.02 vector via the polyfill's own byte-encoding semantics; leaves the root barrel's `node:crypto` import intact for future leaks.
