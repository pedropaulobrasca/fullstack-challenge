# ADR-031: Replay Modal Over Live Game with 1x/2x/4x Speed Selector

**Status**: Accepted
**Date**: 2026-05-30
**Phase**: 8

## Context

REQ-REPLAY-02 requires the FE to expose a Replay button on every history-strip chip; the click produces an animated replay of that historical round with bet/cashout overlays. ROADMAP success criterion 3 layers the real-time-speed requirement on top ("modal animating at real-time speed"). The Phase 8 question this ADR resolves is the UX shape: should replay be a dedicated route (`/replay/$roundId`) the player navigates to, or a modal overlaid on the live game route?

The live game route is a continuous experience — the multiplier curve is rising, the bet panel is in a phase-aware state (BETTING countdown, RUNNING cashout button, CRASHED freeze), the WS connection is open, the history strip is refreshing, the fairness badge is pulsing. Replay sits next to all of that: the player is *also* engaging with the live game while inspecting a past round. The verification drawer (Plan 08-05) already lives in this UX register — it slides in from the right, the live curve keeps animating behind a blurred scrim, the player closes the drawer and is back in the live flow seamlessly. Replay is the same shape of "look at past data while the live game continues" interaction; treating it as a separate route would force the player to navigate away from the live game, drop the WS subscription, lose phase context, and navigate back to find the live flow in a different state than they left.

The other UX axis is the speed selector. The 1x default satisfies the ROADMAP "real-time speed" criterion; the 2x/4x options let the player speed past the boring early rise (the curve climbs from 1.0x slowly for the first second or so) to inspect the interesting part of a historical round without watching 15 seconds of slow rise in real time. The speed selector also stress-tests the determinism invariant (REQ-REPLAY-01, ADR-029): replay must be byte-identical at every speed because speed only changes the wall-clock rate at which the renderer reads the same `multiplierAt(growthRate, t)` curve — the underlying simulation grid is unchanged. The locked property is `sampleReplayMultiplier(state with speed=k, t) === sampleReplayMultiplier(state with speed=1, k*t)` for every `k`, which Plan 08-08 Test 3 anchors as a unit assertion at k ∈ {2, 4}. The available speeds must include 1 (the real-time-speed criterion) — the config validator hard-asserts this.

The ROADMAP anticipated this under the labels "ADR-023/024" (D-02 + D-03 in `08-CONTEXT.md`), but Phases 5/6/7 consumed 019..027 before Phase 8 closed; the decision takes the next-free number ADR-031 with the renumber note recorded in Phase 8's closeout.

## Considered

- **Option A — Modal mounted at `__root.tsx`, auto-play at 1x, 1x/2x/4x ToggleGroup (chosen, locked by Plan 08-07)** — the `ReplayModal` is a shadcn `Dialog` mounted at `__root.tsx` as a sibling of `<Outlet />` (mirroring the Plan 08-05 `VerificationDrawer` mount precedent); the history-chip click writes `roundId` to `useReplayStore` which opens the modal; the modal auto-plays at 1x (`getConfig().replay.autostart && getConfig().replay.speeds[0] === 1`); the speed selector is a shadcn `ToggleGroup` over `getConfig().replay.speeds` (default `[1, 2, 4]` from `VITE_REPLAY_SPEEDS`); the live game route renders behind a blurred scrim and continues animating (the Phase 7 rAF loop never pauses); Esc / scrim-click closes the modal. Pros: matches the verification-drawer UX register (live continues behind, no navigation away); the WS connection + phase state never drop; the player closes the modal and is exactly where they were in the live flow; the modal lives outside the route tree so navigating between routes does not unmount it (Pitfall 5 "render survives navigation"); auto-play at 1x satisfies the ROADMAP real-time criterion; the 2x/4x options accelerate inspection of long historical rounds without breaking determinism (Plan 08-08 Test 3); speeds are env-tunable via `getConfig().replay.speeds` (UI-SPEC § Config-driven); D-03 invariant "must include 1" is hard-asserted in `buildConfig` at app boot. Cons: two rAF loops run simultaneously (the live game's `useRafCurve` + the replay modal's `useRafCurve` driven by the replay driver) — accepted with monitoring per Pitfall 3, and verified at Plan 08-10 closeout (the dual-rAF smoke check confirms no contention/jank/leak on the locked browser tier).
- **Option B — Separate route + linked chip click** — `/replay/$roundId` is a TanStack Router file-based route; the history-chip is a `<Link to="/replay/$roundId">`; clicking navigates away from the game route; the replay surface owns the whole viewport. Pros: cleaner single-rAF profile (the live game route unmounts on navigation; the replay route mounts a fresh `useRafCurve` driven by the replay driver); the replay surface is a shareable URL. Cons: forecloses the "live continues behind" UX (the live game route unmounts on navigation; the player navigates back and finds a different phase, possibly a different round); doubles the auth/socket context surface (the replay route has to enforce login + re-establish socket subscription + re-hydrate the round + re-mount the WS dispatch — all of which the live route was already doing); breaks player flow (replay becomes an interrupting trip); the verification drawer (Plan 08-05) already established the modal/drawer-over-live-game UX register; a sibling Replay surface with a different register (whole-viewport route) would be visually inconsistent; the recruiter's mental model of the live loop is broken every time they hit Replay.
- **Option C — Drawer-shaped replay panel sliding from the right** — same shadcn `Sheet` as the verification drawer, opens from the right, renders the replay canvas in a narrower viewport. Pros: same UX register as the drawer (consistent). Cons: the verification drawer is already on the right edge and is the canonical use of that real estate; opening a second right-edge drawer simultaneously is visually cluttered and unclear about which takes precedence (Z-order, scroll containment); the replay canvas needs a wider aspect ratio than a side-drawer allows (the live curve renders centerwise in the live game so the player can see the full sweep — a narrow drawer truncates the curve); the UI-SPEC explicitly committed to modal for the replay (the drawer is reserved for verification + future drill-downs); two sibling drawers fights with the dark-casino visual hierarchy.

## Decision

**Option A — `ReplayModal` is a shadcn `Dialog` mounted at `__root.tsx` as a sibling of `<Outlet />`; auto-plays at 1x via `getConfig().replay.autostart`; the speed selector is a shadcn `ToggleGroup` over `getConfig().replay.speeds` (default `[1, 2, 4]`, env-tunable via `VITE_REPLAY_SPEEDS`, D-03 invariant "must include 1" hard-asserted in `buildConfig`).** A separate `/replay/$roundId` route is rejected because it forecloses the "live continues behind" UX, breaks player flow with a navigation trip, and doubles the auth/socket context surface; a sibling right-edge drawer is rejected because the verification drawer already owns that real estate, the replay canvas needs a wider aspect ratio than a drawer allows, and the UI-SPEC committed to modal.

The locked implementation is the 08-04 + 08-07 wiring:

- `frontend/.env.example` adds `VITE_REPLAY_SPEEDS=1,2,4`, `VITE_REPLAY_AUTOSTART=true`, `VITE_REPLAY_DRAWER_SLIDE_MS=220`. `lib/config.ts` parses the comma-separated speeds into `number[]`, sorts ascending, hard-asserts the array is non-empty and contains `1` (D-03 invariant); failed assertion crashes app boot — the env-tunable surface cannot ship a config that violates the real-time-speed criterion.
- `frontend/src/features/replay/replay.store.ts` (Plan 08-04) — Zustand store holding `{ roundId, speed, paused, startedAtWall }`. `openReplay(roundId)` sets `roundId + startedAtWall = performance.now() + speed = 1 + paused = false`; `setSpeed(s)` mutates `speed` only (the driver closure reads it per frame, so the renderer sees the new speed immediately without rebuilding the stepper); `togglePause()` flips `paused`; `closeReplay()` resets to initial.
- `frontend/src/components/replay-modal.tsx` (Plan 08-07) — shadcn `Dialog open={roundId !== null} onOpenChange={(o) => !o && closeReplay()}`; the body extracts to `ReplayModalBody` so hooks for the loaded round are only called when `roundId !== null` (correct hook discipline); the body fetches the round via `useRoundDetail(roundId)` (TanStack Query against `/games/rounds/$roundId/verify`, disabled when `roundId === null`, retry: false, typed not-settled/not-found/network errors); on success it builds `makeReplayDriver({ roundId, growthRate, crashPoint })` via `useMemo([roundId, growthRate, crashPoint])` and renders `<CrashCurve driver={replayDriver} ariaLabel="Replay of round {roundId}" />` (the SAME renderer — see ADR-029); the modal chrome holds the `ReplaySpeedToggle` + Play/Pause + `ReplayOverlays` (bet list with masked playerIds + Money payouts).
- `frontend/src/components/replay-speed-toggle.tsx` (Plan 08-07) — shadcn `ToggleGroup type="single"` over `getConfig().replay.speeds`; the selected value mutates `useReplayStore.getState().setSpeed(...)`; the active speed reads `useReplayStore((s) => s.speed)` with `subscribeWithSelector` so the toggle re-renders on change but the modal body does not (ADR-026 isolation pattern extended to replay).
- `frontend/src/components/history-strip.tsx` chip click (Plan 08-07) — `onClick={() => openReplay(chip.roundId)}`; the chip gains a lucide `History` icon + tooltip "Replay" via shadcn Tooltip.
- `frontend/src/routes/__root.tsx` — `<ReplayModal />` mounted as sibling of `<Outlet />` (Plan 08-07), mirroring the Plan 08-05 `VerificationDrawer` mount precedent; render survives navigation (Pitfall 5).

The 08-07 grep evidence confirms the lock held: one `ReplayModal` mount in the route tree; the speed array reads `getConfig().replay.speeds` (no hardcoded `[1, 2, 4]` in the toggle or modal); the auto-start branch reads `getConfig().replay.autostart` (no hardcoded `true`); the driver memo deps are `[roundId, growthRate, crashPoint]` only (speed/paused are not in deps — the closure reads `useReplayStore.getState()` per frame, Pitfall 7 mitigation); Plan 08-08 Test 3 locks the speed-time equivalence in source.

### Why NOT a separate `/replay/$roundId` route (Option B)

The decisive argument is that replay is a "look at past data while the live game continues" interaction — the same shape as the verification drawer — and routing away breaks the live continuity that defines that interaction class. Specifically: the live game route unmounts on navigation, the player loses phase context (was BETTING, returns to find RUNNING already past their preferred bet window), the WS subscription drops + re-establishes (a small reconnect blip on the badge), the round-store rehydrates (history might shift), and the replay surface has to enforce auth + re-mount socket + re-hydrate everything that the live route already had cached. The verification drawer is the precedent: the recruiter clicks the Fairness badge, the drawer slides in, the live curve keeps animating behind the scrim, the recruiter inspects the prior round's seed, closes the drawer, and is back where they were. Replay is the same UX register applied to a different inspectable artifact (the historical round's curve instead of the prior round's seed); modeling it as a navigation is a visual + UX mismatch.

### Why NOT a sibling right-edge drawer (Option C)

The decisive argument is real-estate + aspect-ratio. The verification drawer canonically owns the right edge — it slides in from the right with the seed + verdict + explainer + "Open full verification" link. A second right-edge drawer is visually incoherent (which one takes precedence? what is the Z-order? do they nest? do they overlap?) and the replay surface needs a wider aspect ratio than a side-drawer allows because the curve is the centerpiece of the inspection — narrowing it to 420px on the right cuts off the multiplier sweep the player came to see. The UI-SPEC committed to modal for exactly this reason, and the dark-casino visual hierarchy makes the modal-with-scrim chrome more readable than a second drawer competing with the first.

## Consequences

- **Locked in (modal, mounted at `__root.tsx`)**: `<ReplayModal />` is a sibling of `<Outlet />`, rendered outside the route tree, survives navigation (Pitfall 5). A future plan that moves it inside a route, or replaces it with `<Link to="/replay/...">`, re-opens this decision.
- **Locked in (auto-play at 1x)**: `getConfig().replay.autostart` defaults to `true`; the modal opens with `speed = 1` and `paused = false`; the 1x default satisfies the ROADMAP real-time-speed criterion (D-03). Operators can flip `VITE_REPLAY_AUTOSTART=false` to require a manual Play click — the modal still opens at 1x by default.
- **Locked in (1x/2x/4x ToggleGroup, env-tunable)**: the speed selector reads `getConfig().replay.speeds` (default `[1, 2, 4]` via `VITE_REPLAY_SPEEDS=1,2,4`); the parser hard-asserts the array contains `1` (D-03 invariant — "must include 1"); a future operator wanting `[0.5, 1, 2, 4]` flips the env without code change; an operator config without `1` crashes app boot rather than silently shipping a replay that cannot match the live game.
- **Locked in (live continues behind)**: the scrim blurs the live game but the Phase 7 rAF loop never pauses; the live curve keeps animating + the live multiplier store keeps updating; closing the modal returns the player to exactly where they were in the live flow.
- **Locked in (dual rAF accepted, monitored)**: the live game's `useRafCurve` + the replay modal's `useRafCurve` (driven by the replay driver) both run; the 16ms budget per frame is generous on the supported browser tier; Plan 08-10 closeout dual-rAF smoke check verifies no contention, no jank, no leak on the locked tier. Pitfall 3 documents the accept-with-monitoring posture.
- **Locked in (driver closure reads live state)**: the speed toggle mutates `useReplayStore.getState().speed`; the driver's `multiplier()` closure reads the store per frame; the renderer sees the new speed immediately without the modal body re-rendering or the stepper rebuilding (ADR-029 + ADR-026 isolation).
- **Foreclosed (Option B)**: a separate `/replay/$roundId` route would force a navigation that unmounts the live game, drops the WS subscription, loses phase context, and breaks player flow; the verification-drawer UX register already establishes the modal-over-live-game pattern this decision aligns with.
- **Foreclosed (Option C)**: a sibling right-edge drawer fights with the verification drawer for real estate and aspect ratio; the UI-SPEC committed to modal; the replay canvas needs a wider sweep area than a narrow drawer.
- **Anticipated recruiter question 1**: "Why not a separate route?" — defended: replay is a 'look-at-past-while-live-continues' interaction (same shape as the verification drawer), routing away unmounts the live game and breaks the continuity that defines the interaction class; the modal preserves WS subscription + phase context + player flow; the URL bar still works (a future stretch can add a `?replay={roundId}` query param to the game route if a shareable replay surface is needed without re-opening this ADR).
- **Anticipated recruiter question 2**: "How do you keep determinism at 2x/4x?" — defended: the speed selector mutates only `useReplayStore.speed`; the driver's `multiplier()` reads `t * speed` and the underlying `sampleReplayMultiplier({startedAtWall, speed, paused, ...}, t)` formula reduces to `multiplierAt(t * speed, growthRate)`; the locked invariant `sample(speed=k, t) === sample(speed=1, k*t)` is asserted as a unit test at k ∈ {2, 4} in Plan 08-08 Test 3; speed changes the wall-clock rate at which the renderer reads the same curve, not the curve itself; the byte-match guarantee (ADR-029) holds at every speed.

Cross-references: ADR-025 (Phase 7 — Canvas 2D renderer reused by the modal), ADR-026 (Phase 7 — isolated multiplier store; the replay store is a sibling isolation), ADR-027 (Phase 7 — modal-over-live UX register precedent via the verification drawer parallel), ADR-029 (driver-injection seam — the modal mounts `<CrashCurve driver={replayDriver} />`), ADR-030 (browser-safe contracts subpath — the `/verify` route shares the data path the modal fetches via `useRoundDetail`), Plan 08-04 SUMMARY (env + Zustand stores), Plan 08-07 SUMMARY (ReplayModal + speed toggle + history-chip wiring), Plan 08-08 SUMMARY (Test 3 speed-time equivalence); REQ-REPLAY-02 (replay modal on every history entry), REQ-REPLAY-01 (byte-for-byte reproduction), 08-UI-SPEC (modal vs drawer commitment).

## Alternatives Rejected

- **Option B — Separate `/replay/$roundId` route** — forecloses the "live continues behind" UX that defines the look-at-past-while-live-continues interaction class; navigating away unmounts the live game (loses phase context + drops WS subscription + interrupts player flow); doubles the auth/socket re-establishment surface; visually inconsistent with the Plan 08-05 verification-drawer UX register that already established modal/drawer-over-live for this interaction class.
- **Option C — Sibling right-edge drawer** — fights the Plan 08-05 verification drawer for the right-edge real estate; the replay canvas needs a wider aspect ratio than a side-drawer allows (centerpiece curve gets cut off); UI-SPEC committed to modal; two sibling drawers create unclear Z-order and visual clutter against the dark-casino hierarchy.
