# ADR-032: Light CQRS Leaderboard Read Model (Projector-Populated, No Event Sourcing)

**Status**: Accepted
**Date**: 2026-05-30
**Phase**: 9

## Context

REQ-LEAD-01 requires a 24h rolling leaderboard of top players by net profit (sum of payouts minus sum of bets within a 24h window). REQ-LEAD-02 requires that the leaderboard be populated via a projector consuming `game.events` — explicitly framed in the requirement as "light CQRS — no event sourcing". ROADMAP Phase 9 success criterion 5 layers the operational invariant on top: "projector failure does not block the write path", meaning bets must continue to settle even when the leaderboard projector is broken. The 09-CONTEXT decision D-05 names the architecture pattern: light CQRS with a denormalized read model that the write path emits into but does not depend on.

The crash-game domain already has the substrate this pattern needs: every settled bet writes `bet.cashed_out` (Plan 09-06, Rule 2 fix), `bet.refunded` (Plan 03-03 timeout sweep + saga-level paths), or `bet.lost` (Plan 09-03 crash sweep) to the `game.events` topic exchange via the Phase 2 outbox spine. The outbox guarantees at-least-once delivery with the inbox dedupe gate guaranteeing exactly-once application — exactly the consistency profile a projector wants. The question is what data shape the read side stores and how the live FE updates.

The 24h window is the wrinkle. A true 24h rolling window requires either continuous data (event sourcing — fold all events with timestamps > NOW() - 24h) or a denormalized table that captures `last_settled_at` per player and filters at read time. Event sourcing brings infrastructure tax (event store, snapshot strategy, replay tooling) that the v1 submission does not need — the leaderboard has no audit-trail business requirement and no need to time-travel past states. The denormalized table is the lighter approach: a single `leaderboard_24h` row per player holding the cumulative `net_profit_cents` + `win_count` + `total_bet_count` + `last_settled_at`, with on-read window filtering via `WHERE last_settled_at > NOW() - INTERVAL N HOURS`.

The write-side coupling is the second wrinkle. If the projector subscribes inline with the same TX as the bet settlement, projector failure would roll back the bet — violating the SC5 independence requirement. The decoupling has to be asynchronous: the bet settles + writes its outbox row in one TX (already the case), the broker delivers to the projector queue, the projector applies the delta in its own TX. A broken projector backs up its own queue (DLX after `x-delivery-limit=5`) without touching the bet write path.

The third wrinkle is the FE update cadence. Emitting `leaderboard:updated` on every event is wasteful — most events do not change the top-N ranking (a player at rank 23 going from -1500 to -1700 does not affect the top 10). The system needs a throttle that fires only when ranks actually shift. A pure-function diff over ordered playerId arrays is the lightest gate: `LeaderboardSnapshot.diff(before, after).changed === true` iff the top-N ordering changed; net-profit delta is explicitly NOT part of the equality test (a rank-1 player widening their lead does not trigger an emit).

The ROADMAP anticipated this under the label "ADR-025", but Phases 5/6/7/8 consumed 019..031 before Phase 9 closed; the decision takes the next-free number ADR-032 with the renumber note recorded in Phase 9's closeout.

## Considered

- **Option A — Full event sourcing + on-demand fold** — store every domain event in an event store; the leaderboard read is a fold over the last 24h of events. Pros: complete audit trail; time-travel capable; conceptually pure CQRS. Cons: infrastructure tax (event store, snapshot policy, replay/rebuild tooling) for which v1 has no business requirement; the leaderboard has no audit need (it is a UX surface, not a regulatory artifact); read latency unbounded as event volume grows (24h × N bets per round × players); rebuild story is non-trivial; foreclosed by the explicit "no event sourcing" language in REQ-LEAD-02.
- **Option B — Light CQRS with denormalized read model + `@IdempotentSubscribe` projector (chosen, locked by Plans 09-04 + 09-06)** — a `leaderboard_24h` table holds one row per player with cumulative `net_profit_cents` + `win_count` + `total_bet_count` + `last_settled_at`; a `LeaderboardProjectorService` decorated `@IdempotentSubscribe({ exchange: EXCHANGES.GAME_EVENTS, routingKey: ['bet.cashed_out', 'bet.refunded', 'bet.lost'], queue: 'leaderboard-projector.q' })` consumes the three settlement events and UPSERTs the row; window filtering happens at read time via parameterized `WHERE last_settled_at > NOW() - ((? || ' hours')::INTERVAL)`; top-N diff gate (`LeaderboardSnapshot.diff`) over ordered playerId arrays gates the in-process `GAME_EVENTS.LEADERBOARD_UPDATED` emit before the WS gateway re-broadcasts to `lobby`. Pros: zero new infrastructure (reuses outbox/inbox spine + quorum queues + DLX from Phase 2); write path stays one-TX-per-aggregate (no projector coupling); on-read window filter is one indexed query; rank-change throttle prevents lobby flood; refund no-op is one line of code (Pitfall 8); projector failure routes to DLX after 5 deliveries, write path keeps settling bets (SC5 proven by Plan 09-06 chaos test). Cons: not a "pure" CQRS (the projector reads bet events, not domain events from a separate write store) — accepted because the outbox payload is the canonical event for this purpose.
- **Option C — On-the-fly aggregation from `bets` table via JOIN at query time** — no projector, no read-model table; `GET /games/leaderboard` runs a SQL aggregate over `bets` with `WHERE settled_at > NOW() - INTERVAL`, `GROUP BY player_id`, `ORDER BY SUM(payout) - SUM(amount) DESC LIMIT N`. Pros: zero projector to maintain; no event consumption; always consistent with the write store. Cons: O(round_count × player_count × bets_per_round) per request — at 30 rounds per minute × 24h × N players this is millions of rows even at modest concurrency; even with composite indexes the aggregate touches every row in the window; no natural WS update mechanism (would require either polling or a database trigger fan-out); foreclosed by performance + the "projector consuming game.events" REQ-LEAD-02 language.

## Decision

**Option B — Light CQRS with a denormalized `leaderboard_24h` table populated by `@IdempotentSubscribe` projector consuming `bet.cashed_out` + `bet.refunded` + `bet.lost` on `leaderboard-projector.q`, on-read window filter via parameterized INTERVAL, top-N diff gate over ordered playerId arrays before WS emit, projector failure DLX-routed after 5 deliveries without blocking write path.** Option A is rejected because event sourcing is over-engineered for a UX leaderboard with no audit-trail requirement and is explicitly excluded by REQ-LEAD-02. Option C is rejected because the JOIN-at-query-time approach does not scale past trivial volume even with indexes and has no clean WS update mechanism.

The locked implementation is the 09-04 + 09-06 + 09-07 wiring:

- `services/games/src/infrastructure/persistence/migrations/20260530002-create-leaderboard-24h.ts` (Plan 09-04) creates `leaderboard_24h (player_id UUID PK, net_profit_cents BIGINT, win_count INT CHECK >= 0, total_bet_count INT CHECK >= 0, last_settled_at TIMESTAMPTZ)` + composite index `(net_profit_cents DESC, player_id)`. The index is NOT partial because Postgres requires IMMUTABLE predicates and `NOW() - INTERVAL` is not — window filtering is parameterized at read time.
- `services/games/src/domain/leaderboard/leaderboard-snapshot.value-object.ts` (Plan 09-04) — pure VO `LeaderboardSnapshot.diff(before, after)` compares ordered `playerId` arrays only; `netProfitCents` deltas are explicitly NOT part of equality (Q12 + RESEARCH recommendation); locked by unit test 1.
- `services/games/src/infrastructure/persistence/repositories/mikro-leaderboard-repository.ts` (Plan 09-04) exposes `applyCashedOut` + `applyRefunded` (no-op per Pitfall 8) + `applySettledLoss` + `fetchTopN` + `fetchSnapshot`; uses Postgres `INSERT … ON CONFLICT (player_id) DO UPDATE SET … += EXCLUDED.…`; `fetchTopN` hydrates `last_settled_at` via `toDate()` helper (Phase 6 Pitfall 1 enforced).
- `services/games/src/application/use-cases/cash-out.use-case.ts` (Plan 09-06 Rule 2 fix) emits `bet.cashed_out` to the outbox in the same `em.transactional` as `wallet.credit` with `correlationId === causationId === messageId`; the schema lives at `packages/contracts/src/wallet/bet-cashed-out.event.ts` as `BetCashedOutEventV1`.
- `services/games/src/application/leaderboard/leaderboard-projector.service.ts` (Plan 09-06) `@IdempotentSubscribe({ exchange: EXCHANGES.GAME_EVENTS, routingKey: ['bet.cashed_out', 'bet.refunded', 'bet.lost'], queue: 'leaderboard-projector.q' })` — the spine decorator widened to accept `string | string[]` for this plan. The handler extracts to `handleEnvelope` for unit testability (mirroring `WalletDebitedHandler`); fetches a snapshot before, applies the delta, fetches a snapshot after, and emits in-process `GAME_EVENTS.LEADERBOARD_UPDATED` only when `LeaderboardSnapshot.diff(before, after).changed === true`.
- `services/games/src/infrastructure/ws/game-ws.gateway.ts` (Plan 09-06) `@OnEvent(GAME_EVENTS.LEADERBOARD_UPDATED)` maps `entries[].playerId` through `maskPlayerId(PlayerId(...))` to an 8-char SHA-256 hex (raw UUIDs cannot reach the wire), converts `netProfitCents: bigint` to string (BigInt JSON-safe), then `server.to('lobby').emit('leaderboard:updated', payload)`.
- `services/games/src/presentation/http/leaderboard.controller.ts` (Plan 09-07) `@Get()` calls `leaderboard.fetchTopN(env.LEADERBOARD_TOP_N, { windowHours: env.LEADERBOARD_WINDOW_HOURS })` — no hardcoded N or hours per CLAUDE.md §Configuration; the response shape is the same `leaderboardUpdatedPayloadSchema` from `@crash/contracts/ws` that the WS event uses.
- `services/games/tests/integration/leaderboard-projector-chaos.test.ts` (Plan 09-06) overrides the projector provider to throw on every delivery, places a bet, asserts the bet still reaches terminal status AND `leaderboard_24h` stays empty — SC5 proof.

### Why NOT event sourcing (Option A)

The decisive arguments are scope and explicit requirement language. REQ-LEAD-02 names "light CQRS — no event sourcing" verbatim; the requirement is not "implement event sourcing for the leaderboard". The leaderboard is a UX surface (top 10 by net profit, masked playerId, refresh on rank change) — not a regulatory artifact, not an audit log, not a time-travel surface. Event sourcing would impose an event store, a snapshot policy, a replay/rebuild story, and a separate query-side projection layer to read efficiently from. The denormalized table is one migration + one repository + one projector + one in-process event constant; event sourcing would multiply that by an order of magnitude for zero v1 business value.

### Why NOT JOIN-at-query-time (Option C)

The decisive arguments are performance and the absence of a clean WS update mechanism. At ~30 rounds per minute over 24h, with N bets per round, the bets table grows by ~50K rows per day per player. A `GROUP BY player_id, ORDER BY SUM(payout - amount) DESC LIMIT 10` over the last 24h scans every row in the window even with composite indexes — there is no natural way to push the aggregation into the index. More fundamentally, REQ-LEAD-04 requires WS live updates when ranks shift; with no projector there is no natural trigger point for an emit (a Postgres `LISTEN/NOTIFY` from a trigger is possible but moves business logic into the database). The projector pattern gives a clean hook for the rank-change throttle and is the only path that satisfies REQ-LEAD-02 + REQ-LEAD-04 together.

## Consequences

- **Locked in (light CQRS, no event sourcing)**: the leaderboard is one denormalized table + one projector + one in-process event constant + one rank-change diff gate; no event store, no snapshot policy, no replay tooling. A future feature that needs audit-trail or time-travel would have to introduce event sourcing as a separate decision and reopen this ADR.
- **Locked in (projector subscribes via `@IdempotentSubscribe`)**: the spine's inbox dedupe gate runs before the projector's `handleEnvelope`, so a redelivery (broker NACK + redeliver) is idempotent at the read-model level. Locked by the Plan 09-06 spine routing-key widening test asserting per-message inbox `tryClaim` regardless of which routing key matched the array.
- **Locked in (refund is a no-op)**: `applyRefunded` does not touch `net_profit_cents`, does not touch `last_settled_at`, does not increment `total_bet_count`. Per Pitfall 8 + RESEARCH Q1: refunds restore the player to the pre-bet state, so the leaderboard should also see no change. Locked by Plan 09-06 unit test 2 asserting no other apply method is called when the projector receives `bet.refunded`.
- **Locked in (on-read window filter, parameterized INTERVAL)**: `fetchTopN` filters via `WHERE last_settled_at > NOW() - (($N || ' hours')::INTERVAL)`. T-09-14 SQL-injection mitigation: `grep "INTERVAL '"` against the repository returns zero matches — no template-string interval. The composite index `(net_profit_cents DESC, player_id)` handles `ORDER BY net_profit_cents DESC LIMIT N` in index time.
- **Locked in (rank-change throttle)**: `leaderboard:updated` fires only when the top-N ordered playerId array changes. A rank-1 player widening their lead from +5000 to +6000 does NOT emit; a rank-23 player overtaking rank-9 DOES emit. Locked by Plan 09-06 unit tests 5 + 6 (rank-change emits / same-order throttles).
- **Locked in (write path independent from projector)**: the bet's settlement TX writes its own `bet.cashed_out` / `bet.lost` outbox row and commits; the broker delivers to `leaderboard-projector.q` asynchronously; a poisoned projector backs up its own queue then routes to DLX after `x-delivery-limit=5` (Phase 2 topology). The bet status, the wallet credit, and the player's HTTP response are all decoupled from the projector's health. SC5 proven by `leaderboard-projector-chaos.test.ts`.
- **Locked in (BigInt-safe wire format)**: the gateway converts `netProfitCents: bigint` to string before emit; the contract schema `moneySnapshotSchema.amount` regex `/^-?\d+$/` accepts signed integers (the leaderboard legitimately holds negative net profit for losing players inside the window).
- **Foreclosed (Option A — event sourcing)**: no event store, no snapshot policy, no replay tooling; a future audit-trail requirement would reopen this decision and propose a separate event-sourced subsystem.
- **Foreclosed (Option C — JOIN-at-query-time)**: no per-request aggregation over `bets`; the denormalized table is the canonical read path for the leaderboard and the only path that supports the WS update mechanism.
- **Anticipated recruiter question 1**: "Why not event sourcing?" — defended: REQ-LEAD-02 explicitly says "no event sourcing"; the leaderboard is a UX surface with no audit requirement; the v1 scope is to demonstrate CQRS shape, not to ship an event-sourced subsystem; the denormalized read model gives the same query-side ergonomics without the infrastructure tax.
- **Anticipated recruiter question 2**: "What happens when the projector dies?" — defended: bets continue to settle (proved by SC5 chaos test); failed messages back up on `leaderboard-projector.q` (quorum queue, durable) then route to DLX after 5 redeliveries; the leaderboard goes stale, the WS stops emitting, but the write path keeps writing. On projector recovery the queue drains and the projector catches up event-by-event; idempotency via `@IdempotentSubscribe` means no double-application.
- **Anticipated recruiter question 3**: "Why throttle on rank change instead of every event?" — defended: the leaderboard FE re-renders the top-N list; emitting on every event would re-render even when the visible state did not change (a rank-23 player drifting from -1500 to -1700 is invisible at top-10); the pure VO diff over ordered playerId arrays is the cheapest gate that captures exactly when the FE state changes; locked by unit tests 5 + 6 plus the integration test asserting a single emit on a rank-shifting sequence.

Cross-references: ADR-013 (txEm propagation — the projector's `em.transactional` flows through `@IdempotentSubscribe`), ADR-014 (Bet as own aggregate — the `bet.cashed_out` / `bet.lost` outbox rows live in the same TX as the bet transition), ADR-018 (Money rounding — the projector deltas are computed in BigInt cents, never floats), ADR-019 (orchestration over choreography — the projector is downstream choreography off the saga, not part of the saga itself), ADR-021 (single lobby room — the `leaderboard:updated` emit fans out to `lobby` not per-user rooms), Plan 09-04 SUMMARY (table + repository + snapshot VO), Plan 09-06 SUMMARY (projector + WS emit + chaos test + Rule 2 cash-out outbox fix), Plan 09-07 SUMMARY (controller + shared payload schema); REQ-LEAD-01 (24h rolling top-N), REQ-LEAD-02 (light CQRS projector), REQ-LEAD-03 (GET endpoint), REQ-LEAD-04 (WS live updates); Pitfalls 6 (rank-change throttle), 7 (refund no-op), 8 (refund semantics), 12 (window filter parameterization).

## Alternatives Rejected

- **Option A — Full event sourcing + on-demand fold** — over-engineered for a UX leaderboard with no audit-trail business requirement; infrastructure tax (event store, snapshot policy, replay/rebuild tooling) buys nothing v1 needs; explicitly excluded by the REQ-LEAD-02 "no event sourcing" language.
- **Option C — On-the-fly aggregation from `bets` table via JOIN at query time** — O(round_count × player_count × bets_per_round) per request even with indexes; the aggregation must scan the entire 24h window per request; no natural WS update mechanism (would require Postgres LISTEN/NOTIFY or trigger fan-out, moving business logic into the database); foreclosed by performance + the REQ-LEAD-02 "projector consuming game.events" language.
