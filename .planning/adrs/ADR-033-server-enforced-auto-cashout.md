# ADR-033: Server-Enforced Auto-Cashout via In-Process ROUND_TICK + AutoCashoutTickService (Ratifies ADR-023)

**Status**: Accepted
**Date**: 2026-05-30
**Phase**: 9

## Context

REQ-AUTO-01 requires the player to set an auto-cashout target multiplier and the server to enforce it — comparing each tick's multiplier to the target and auto-issuing the cashout when the target is reached. The decisive UX guarantee is that disconnects must not cost the player: if the WS drops at `multiplier = 1.5x` with a target of `2.0x`, the bet must still cash out at `2.0x` when the multiplier reaches it. ROADMAP Phase 9 success criterion 1 codifies this as the disconnect-safety E2E (force-close the socket mid-round, assert `bet.status === 'CASHED_OUT'` AND `cashedOutMultiplier === 2.0`).

The 30Hz tick loop is the obvious hook point — that is where the server already knows the current multiplier and emits `round:tick` over the WS to clients. The question is how to wire the auto-cashout check without breaking the broadcast loop's single responsibility (which Phase 6 codified as the canonical volatile-emit owner per ADR-022).

Three forces shape the decision. First, the broadcast loop runs at 30Hz on a recursive `setTimeout` and must not block on DB work (a synchronous `findAutoCashoutCandidates` query per tick would tighten the loop and miss frames). Second, the cashout race resolution invariant from ADR-023 (server-stamped `acceptedAt` at the controller's first executable line) generalizes — the auto-cashout's `acceptedAt` must be stamped at the listener's first executable line, before any await, so the race resolution honors the same single-clock principle. Third, the cashout payout must use the player's `autoCashoutTarget` (e.g., 2.0x) NOT the current tick's multiplier (e.g., 2.05x — IEEE-754 timing slop) — the player asked for 2.0x, the player gets 2.0x.

The auto-cashout candidates query is naturally indexed: Plan 09-02 added the partial index `idx_bets_auto_cashout_candidates ON (round_id, auto_cashout_target_centi_x) WHERE status='ACTIVE' AND auto_cashout_target_centi_x IS NOT NULL`. At 30Hz with the partial index, the query is microseconds per tick even at high concurrency.

The ROADMAP anticipated this under the label "ADR-026", but Phases 5/6/7/8 consumed 019..031 before Phase 9 closed; the decision takes the next-free number ADR-033 with the renumber note recorded in Phase 9's closeout.

## Considered

- **Option A — Inline check in `MultiplierBroadcastService.fireTick()`** — `fireTick` does the volatile emit, then synchronously queries `findAutoCashoutCandidates`, then invokes `CashOutUseCase` for each candidate. Pros: one fewer service to wire; the cashout decision is co-located with the multiplier source. Cons: couples broadcast SRP with DB work + cashout orchestration (the broadcast service becomes a god-object); blocks the tick loop on the DB query + the cashout saga (CashOutUseCase does an `em.transactional` + outbox write + saga state update — non-trivial latency); a single slow query stalls the 30Hz cadence for every connected client; the broadcast service was canonized in Phase 6 P6.04 as the SOLE volatile-emit owner with explicit SRP; rejected per the 09-CONTEXT D-06 canonical references.
- **Option B — In-process `GAME_EVENTS.ROUND_TICK` event from `fireTick` → new `AutoCashoutTickService` `@OnEvent({ async: true })` listener (chosen, locked by Plan 09-05)** — `MultiplierBroadcastService.fireTick()` emits `GAME_EVENTS.ROUND_TICK` in-process via injected `EventEmitter2` AFTER the existing `volatile.emit('round:tick', ...)` line, wrapped in a sibling try/catch so a misbehaving listener cannot break the volatile broadcast (Pitfall 3); a new `AutoCashoutTickService` `@OnEvent(GAME_EVENTS.ROUND_TICK, { async: true })` listens; the handler stamps `const acceptedAt = new Date()` as its literal first executable statement (ratifies ADR-023); queries `BetRepository.findAutoCashoutCandidates(roundId, ceilingCentiX)` against the Plan 09-02 partial index; loops invoking the existing `CashOutUseCase.execute({ playerId, multiplier: bet.autoCashoutTarget, acceptedAt })` — passing the bet's stored target, NOT the current tick multiplier. Pros: broadcast SRP preserved (the service emits + delegates); the listener runs async so the volatile tick is never blocked; the partial index makes the query hot-path-cheap; the existing `CashOutUseCase` is reused verbatim (no new aggregate logic — the auto-path is just another caller); the in-process bus is the same `@nestjs/event-emitter` that Phase 6 P6.05 already uses for lifecycle events (no new infrastructure); ADR-023's first-line `acceptedAt` invariant generalizes to the listener entry. Cons: the in-process bus is fire-and-forget so a listener crash is logged but not retried (accepted — the next tick is 33ms away and will retry the same candidate set).
- **Option C — Per-tick callback on `RoundLoopService`** — wire the auto-cashout check into `RoundLoopService` as a per-tick callback. Pros: the round loop is the orchestration owner. Cons: `RoundLoopService` does NOT tick at 30Hz — it manages FSM transitions (BETTING / RUNNING / CRASHED / SETTLED) at coarse-grained intervals; it is the wrong cadence source; using it would either require reshaping the round loop to tick at 30Hz (duplicating the broadcast loop) or accepting that auto-cashout only fires at FSM transitions (which is the opposite of "the server checks each tick"); foreclosed by cadence mismatch.

## Decision

**Option B — `MultiplierBroadcastService.fireTick()` emits in-process `GAME_EVENTS.ROUND_TICK` after the volatile emit; `AutoCashoutTickService` `@OnEvent({ async: true })` listens, stamps `acceptedAt = new Date()` as its literal first statement (ratifies ADR-023), queries `findAutoCashoutCandidates` against the Plan 09-02 partial index, invokes the existing `CashOutUseCase` with the bet's stored `autoCashoutTarget` as the multiplier (NOT the current tick).** Option A is rejected because it couples broadcast SRP with DB + saga work and blocks the 30Hz volatile loop on slow paths. Option C is rejected because `RoundLoopService` is not the 30Hz cadence source — using it would force auto-cashout into FSM-transition cadence, the wrong shape for "the server checks each tick".

The locked implementation is the 09-05 wiring:

- `services/games/src/application/game-events.ts` (Plan 09-05) — `GAME_EVENTS.ROUND_TICK = 'round.tick'` constant + `RoundTickPayload { roundId: RoundId, multiplier: number, t: number }` type.
- `services/games/src/infrastructure/ws/multiplier-broadcast.service.ts` (Plan 09-05) — `fireTick` retains the volatile emit `server.to('lobby').volatile.emit('round:tick', { multiplier, t })` as its first action (ADR-022 + ADR-021 invariants preserved), then emits `this.eventEmitter.emit(GAME_EVENTS.ROUND_TICK, { roundId, multiplier, t })` wrapped in a sibling try/catch so a listener exception cannot stall the volatile loop. The production DI ctor is `(ModuleRef, EventEmitter2)` — the Phase 6 P6.05 ModuleRef cycle-break for `RoundLoopService ↔ MultiplierBroadcastService` is preserved while EventEmitter2 is added as a direct injection (no cycle on the emitter). A 3-arg overload `(roundLoop, gateway, eventEmitter)` exists for direct-ref test fixtures.
- `services/games/src/application/auto-cashout/auto-cashout-tick.service.ts` (Plan 09-05) — `@Injectable` application-layer service decorated `@OnEvent(GAME_EVENTS.ROUND_TICK, { async: true })`. The `onTick(payload: RoundTickPayload)` handler is:

  1. `const acceptedAt = new Date();` — LITERAL FIRST executable statement (source-inspection regex `/async\s+onTick[^{]*\{\s*const\s+acceptedAt\s*=\s*new\s+Date\(\)/` locked in the unit suite, mirroring Phase 5 P5.06 controller-line-69 gate);
  2. `const ceilingCentiX = Math.floor(payload.multiplier * 100);` — bet's stored `auto_cashout_target_centi_x` is the integer centi-multiplier; the index lookup is `WHERE auto_cashout_target_centi_x <= ceilingCentiX`;
  3. `const candidates = await this.bets.findAutoCashoutCandidates(payload.roundId, ceilingCentiX);` — single indexed SELECT against `idx_bets_auto_cashout_candidates` (Plan 09-02 partial index, hot path at 30Hz);
  4. for each candidate, `await this.cashOut.execute({ playerId: bet.playerId, multiplier: bet.autoCashoutTarget, acceptedAt });` — passes the bet's stored target (NOT `payload.multiplier`), so the player gets exactly 2.0x even when the tick reads 2.05x (Pitfall 4 + T-09-21 mitigation; unit test asserts `arg.multiplier === bet.autoCashoutTarget` and `!== payload.multiplier`).

- Error handling: `RoundNotRunningError` + `BetNotCashableError` thrown by `CashOutUseCase` are swallowed (legitimate FSM-guarded races — Pitfall 11); other error classes are logged at error level via `this.logger.error('Unexpected auto-cashout error', err)` per CLAUDE.md §"Saga / messaging" observability-over-silence.
- Module wiring: registered in `GameCoreModule.providers`; `@OnEvent` self-registers via `@nestjs/event-emitter` so no other wiring is needed.
- E2E (Plan 09-05): `services/games/tests/e2e/auto-cashout-disconnect.e2e.test.ts` connects socket.io to `ws://localhost:4101/ws` with the seeded `player/player123` JWT, waits for `round:running`, POSTs `/games/bet` with `autoCashoutTarget = 2.0`, on the first `round:tick` with `multiplier >= 1.5` force-closes the socket, then polls `GET /games/bets/me` every 500ms for up to 30s and asserts `status === 'CASHED_OUT'` AND `cashedOutMultiplier === 2.0`. The test retries up to 3 round cycles if a deterministic seed crashes the round below 2.0x.

### Why NOT inline-in-fireTick (Option A)

The decisive arguments are SRP and broadcast-loop hygiene. The broadcast service was canonized in Phase 6 P6.04 as the SOLE owner of `volatile.emit` for `round:tick` (ADR-022) — its single responsibility is "push the server clock to clients at 30Hz". Inlining the auto-cashout check would (a) couple broadcast SRP with DB + cashout-saga orchestration, (b) block the 30Hz tick on the candidates query + the `em.transactional` of `CashOutUseCase` + the outbox writes for `bet.cashed_out` + `wallet.credit` — a single slow path stalls the tick for every connected client. The in-process event bus decouples the cadence source from the action: `fireTick` does its one job + emits; the listener does its one job + awaits.

### Why NOT RoundLoopService callback (Option C)

The decisive argument is cadence. `RoundLoopService` ticks at FSM-transition cadence — it transitions BETTING → RUNNING after the betting window, RUNNING → CRASHED at the crash point, CRASHED → SETTLED after the reveal interval, SETTLED → BETTING after the cooldown. These are coarse-grained intervals (seconds), not the 30Hz the auto-cashout check needs. The 30Hz cadence lives in `MultiplierBroadcastService.fireTick`; auto-cashout needs to live on that cadence; using `RoundLoopService` would either require duplicating the 30Hz loop (defeats the point) or accept FSM-transition cadence (defeats the requirement).

## Consequences

- **Locked in (broadcast SRP preserved)**: `MultiplierBroadcastService.fireTick` retains the single responsibility "push the server clock at 30Hz"; it emits + delegates via the in-process bus; no DB work, no saga orchestration, no auto-cashout decision logic lives in the broadcast loop. A future plan that inlines work into `fireTick` re-opens this decision.
- **Locked in (`acceptedAt` first-line invariant generalizes — ratifies ADR-023)**: every code path that decides the cashout-vs-crash race stamps `acceptedAt = new Date()` as its literal first executable statement. The HTTP controller (`bet-command.controller.ts:69`) and the auto-cashout listener (`auto-cashout-tick.service.ts`) both honor this; the source-inspection regex is locked in both unit suites. ADR-023's race-resolution canon now covers both manual + auto paths.
- **Locked in (auto-cashout pays the player's target, not the current tick)**: `CashOutUseCase` is invoked with `multiplier: bet.autoCashoutTarget`, so a bet with `autoCashoutTarget = 2.0` cashes out at exactly 2.0x even when the tick reads 2.05x (IEEE-754 slop). The player's contract is honored; the unit test asserts `arg.multiplier === bet.autoCashoutTarget` and `!== payload.multiplier`. T-09-21 mitigation.
- **Locked in (broadcast loop never blocks on listener)**: `@OnEvent({ async: true })` runs the handler off the emit call stack; the sibling try/catch in `fireTick` swallows any synchronous throw from the emitter itself; the 30Hz cadence is preserved even when a listener takes seconds. Plan 09-05 integration test asserts mean tick interval 23-43ms over 1s under async listener load AND under deliberate listener-throw.
- **Locked in (partial index hot path)**: the `findAutoCashoutCandidates(roundId, ceilingCentiX)` query hits `idx_bets_auto_cashout_candidates ON (round_id, auto_cashout_target_centi_x) WHERE status='ACTIVE' AND auto_cashout_target_centi_x IS NOT NULL` — index scan, microseconds at 30Hz, no full-table scan even at saturation.
- **Locked in (existing CashOutUseCase reused verbatim)**: the auto-path is just another caller of `CashOutUseCase.execute(...)`; no aggregate behavior duplication, no parallel cashout code path, no risk of drift between manual + auto cashout semantics. A bug fixed in `CashOutUseCase` is fixed for both paths automatically.
- **Locked in (FSM-guarded race errors swallowed)**: `RoundNotRunningError` + `BetNotCashableError` are legitimate races (the round may CRASH between the tick emit and the listener's await) and are swallowed silently — these are not "errors" in any operationally meaningful sense; Pitfall 11. Other errors are logged at error level via `this.logger.error('Unexpected auto-cashout error', err)`.
- **Locked in (disconnect-safety E2E)**: the SC1 recorded proof is `auto-cashout-disconnect.e2e.test.ts` — drops the socket at `multiplier >= 1.5`, asserts the bet cashes at `autoCashoutTarget = 2.0`. The test name is `.e2e.test.ts` (not `.e2e.ts`) so Bun's test matcher picks it up.
- **Foreclosed (Option A)**: no inline DB / saga work in `fireTick`; the broadcast loop's SRP is locked.
- **Foreclosed (Option C)**: `RoundLoopService` does not host per-tick logic; FSM-transition cadence is the wrong source for 30Hz checks.
- **Anticipated recruiter question 1**: "What if the WS drops mid-round?" — defended: server-enforced, not client-driven; the 30Hz tick loop runs server-side regardless of WS state; `AutoCashoutTickService` listens on the in-process bus, queries the DB for ACTIVE bets with auto targets at or below the current tick multiplier, fires the cashout via the existing `CashOutUseCase`. SC1 E2E proves the disconnect case end-to-end.
- **Anticipated recruiter question 2**: "What if the tick reads 2.05x when my target was 2.0x?" — defended: the cashout pays `bet.autoCashoutTarget`, not the tick's `payload.multiplier`. The player asked for 2.0x, the player gets 2.0x. The 30Hz cadence + IEEE-754 timing slop produce tick multipliers in tiny over-shoots, but the contract is the player's stored target; the unit test locks this.
- **Anticipated recruiter question 3**: "What about the race between the auto-fire and the round crashing?" — defended: ADR-023's single-clock principle covers this — `acceptedAt` is stamped first; `CashOutUseCase` runs the RUNNING-phase guard against the round's authoritative `crashedAt`; if `acceptedAt > crashedAt` the cashout is rejected with `RoundNotRunningError`, which the listener swallows (Pitfall 11). The race resolution is identical to the manual cashout path.

Cross-references: ADR-022 (30Hz volatile tick — the cadence source this listener hooks), ADR-023 (server-authoritative `acceptedAt` — the first-line invariant this ADR generalizes from controllers to listeners), ADR-014 (Bet as own aggregate — `bet.autoCashoutTarget` is on the Bet aggregate from Plan 09-02), ADR-018 (Money rounding — `CashOutUseCase` pays `bet × multiplier` with banker's rounding, called identically by manual + auto paths), ADR-019 (orchestration over choreography — `CashOutUseCase` is the orchestrated cashout saga, reused for the auto path), ADR-032 (light CQRS projector — the `bet.cashed_out` outbox emit from `CashOutUseCase` feeds the leaderboard projector regardless of whether the cashout was manual or auto); Plan 09-02 SUMMARY (partial index + autoCashoutTarget field), Plan 09-05 SUMMARY (ROUND_TICK event + AutoCashoutTickService + SC1 E2E); REQ-AUTO-01 (server-enforced auto-cashout, disconnect-safe); Pitfalls 2 (broadcast SRP), 3 (sibling try/catch), 4 (target-not-tick), 9 (in-process bus async), 11 (FSM-guarded race swallow).

## Alternatives Rejected

- **Option A — Inline check in `MultiplierBroadcastService.fireTick()`** — couples broadcast SRP with DB + cashout-saga orchestration; blocks the 30Hz volatile loop on the candidates query + the `em.transactional` + outbox writes; the broadcast service was canonized in Phase 6 P6.04 as the SOLE volatile-emit owner with explicit SRP and ADR-022 lock.
- **Option C — Per-tick callback on `RoundLoopService`** — `RoundLoopService` does not tick at 30Hz (it manages FSM transitions only — BETTING / RUNNING / CRASHED / SETTLED at coarse intervals); using it would either duplicate the 30Hz loop (defeats the point) or accept FSM-transition cadence (defeats the requirement); cadence mismatch with the "server checks each tick" REQ-AUTO-01 language.
