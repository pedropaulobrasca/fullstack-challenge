# ADR-034: Per-Session Auto-Bet Config — Zustand No-Persist + FE-Driven Stops + Server-Stateless

**Status**: Accepted
**Date**: 2026-05-30
**Phase**: 9

## Context

REQ-AUTO-02 requires auto-bet strategies (fixed + Martingale). REQ-AUTO-03 requires stop-loss and stop-win thresholds that halt auto-bet when cumulative P/L crosses either threshold. REQ-AUTO-04 makes the UX choice explicit: auto-bet configuration is per-session (client-side store) — does not survive page reload by default. REQ-AUTO-05 requires the Auto tab in the bet panel with target / strategy / stop inputs and a Start / Stop toggle. The 09-CONTEXT decisions D-01 (per-session, no persist) + D-03 (cumulative since Start, FE-driven stops) together lock the architectural posture this ADR codifies.

The decisive UX argument for no-persist is the "surprise factor" of a persisted strategy. Imagine a player configures Martingale with `base = 10`, `stop-loss = 200`, walks away from the browser, comes back the next day, refreshes the page, and the auto-bet is still running with whatever state it had — placing bets the player does not remember asking for. The persist-on-reload story has two failure modes: (a) the player loses money they did not authorize, and (b) the support story for "I came back and my balance was wrong" is unprovable without a full session audit. The no-persist default makes the contract explicit: every reload is a fresh session; the player has to explicitly re-arm the strategy. The tradeoff is that auto-bet does not survive browser reloads — accepted as a safety property, not a feature loss.

The decisive architectural argument against server-side stops is infrastructure tax. A server-enforced stop-loss / stop-win would require: a per-player session row with cumulative P/L, a fan-out from every bet settlement to that row, a check on every `placeBet` against the stored thresholds, a clear-on-Start mechanism, and a sync surface between FE and BE so the player knows their current cumulative state. The FE-driven cumulative-since-Start approach makes the same UX contract — the player clicks Start, the FE driver tracks session P/L from `bet:my_cashed_out` / `bet:my_refunded` events, the driver stops itself when the threshold is breached — without any new server-side state. The server stays stateless on stops. The defense against runaway sessions is the same wallet-level defense that always existed: `BET_MAX_CENTS` + the wallet balance check + the non-negative-balance Postgres CHECK constraint. The Martingale strategy cannot overflow the wallet because the wallet refuses to debit below zero (ADR-014 + Phase 3 invariants).

The auto-cashout target is a separate concern. REQ-AUTO-01 requires server enforcement of the target (so disconnects don't cost the player); that is ADR-033's scope (`AutoCashoutTickService` checks each tick against `bet.autoCashoutTarget` and fires the cashout server-side). The auto-bet driver on the FE just POSTs `placeBet` with `autoCashoutTarget` from the configured value; the server enforcement is downstream of the bet placement. So auto-bet stops are FE-only, but auto-cashout enforcement is server-side; the two REQ-AUTO concerns are decoupled.

The strategy semantics also lock here. REQ-AUTO-02 names Martingale (double on loss, reset on win); the ambiguous question is what the "base" amount is for the doubling — the player's configured initial amount, or the previous bet amount. The CONTEXT-locked answer is "configured initial" — Martingale doubles from the previous bet, but resets to the configured initial on win, NOT to the previous bet on win. The strategy is implemented as a pure function `nextBetAmount({ strategy, base, lastBet, lastOutcome })` so the test suite can exhaustively assert the doubling + reset behavior without entangling Zustand state.

The ROADMAP anticipated this under the label "ADR-027", but Phases 5/6/7/8 consumed 019..031 before Phase 9 closed; the decision takes the next-free number ADR-034 with the renumber note recorded in Phase 9's closeout.

## Considered

- **Option A — DB-persisted per-player strategy config + server-enforced stops** — a `player_auto_bet_state` table holds strategy / base / stop-loss / stop-win / cumulative P/L / `isRunning` per player; every `placeBet` checks the table; every settled bet updates the cumulative; the player's Start click writes the row; reload reads the row and resumes auto-bet. Pros: state survives reload; server is the single source of truth; auditable. Cons: infrastructure tax (new table + new aggregate + migration + repository + repository tests + projector for cumulative P/L + sync surface for FE display + clear-on-Start semantics + the "is this row stale from a session that timed out?" problem); UX surprise factor on reload (the player comes back the next day to find a strategy they don't remember starting still placing bets); auditability is unprovable in dispute without a full session log; foreclosed by REQ-AUTO-04 ("does not survive page reload by default — UX explicit choice") + the safety-over-continuity preference.
- **Option B — Per-session FE Zustand store, NO persist middleware, FE-driven cumulative-since-Start stops (chosen, locked by Plan 09-08)** — auto-bet state lives in a Zustand slice `useAutoBetStore` declared WITHOUT the `persist` middleware (REQ-AUTO-04 grep gate `grep "persist" frontend/src/stores/auto-bet.store.ts` returns zero); the player's Start click captures the config + initializes `sessionPnL = 0`; the FE driver subscribes to `bet:my_cashed_out` + `bet:my_refunded` WS events and accumulates session P/L; on each `round:started` the driver POSTs `placeBet` with `autoCashoutTarget` from the configured value + amount from `nextBetAmount` strategy fn; the driver halts cleanly when `sessionPnL <= -stopLossCents` (stop-loss) or `sessionPnL >= stopWinCents` (stop-win), with a deduped amber toast indicating the halt reason; backend stays stateless on stops; the autoCashoutTarget IS server-enforced (separate concern per ADR-033). Pros: zero new server-side state (no table, no aggregate, no projector); no UX surprise on reload (fresh session every time, defensible); simpler architecture (the entire feature lives in two FE files: a pure strategy fn + a Zustand slice + a driver); auditability is unnecessary because the server is not the source of truth for session config; defense against runaway sessions is the existing wallet `BET_MAX_CENTS` + balance check + non-negative-balance CHECK (Martingale cannot overflow because the wallet refuses to debit below zero); the Manual tab is disabled while Auto is running (Lock affordance per UI-SPEC) so the player cannot accidentally place a manual bet that confuses the driver's session P/L tracking; the driver is event-only (NO setInterval — RESEARCH Anti-Patterns gate) so reactive cadence matches the actual round lifecycle. Cons: auto-bet does not survive browser reloads — accepted as safety property.
- **Option C — localStorage-persisted FE config** — same FE driver, but the Zustand slice uses the `persist` middleware to write to localStorage; reload restores the config + `isRunning` flag; if `isRunning === true` on hydrate, the driver auto-resumes. Pros: state survives reload without server-side infrastructure. Cons: same UX surprise factor as Option A but worse (no server-side audit at all); a corrupt localStorage entry can put the driver into an unrecoverable state; the player might be running a strategy from a different machine's session if they sync localStorage across devices; the safety contract is unclear; the explicit "no persist" guard in Plan 09-08 (REQ-AUTO-04 grep gate) was added to PREVENT this option from sneaking in.

## Decision

**Option B — Per-session FE Zustand store WITHOUT persist middleware (REQ-AUTO-04 grep gate enforces); pure `nextBetAmount` strategy fn (Martingale doubles from previous bet, resets to configured initial on win, NOT to previous bet); event-only auto-bet driver subscribing to round + private bet events via `subscribeWsEvent` (NO setInterval); cumulative session P/L tracked since the Start click via `bet:my_cashed_out` + `bet:my_refunded` WS events; stops halt the driver client-side with a deduped amber toast; backend stays stateless on stops; the autoCashoutTarget IS server-enforced via the existing ADR-033 path; Manual tab disabled with Lock affordance while Auto is running; defense against runaway = wallet `BET_MAX_CENTS` + balance check + Postgres non-negative-balance CHECK.** Option A is rejected because it adds infrastructure tax (new table + aggregate + projector + sync) for marginal UX value AND introduces the reload-surprise failure mode REQ-AUTO-04 explicitly avoids. Option C is rejected because localStorage-persisted state is the same surprise factor as Option A without any server-side audit; the grep gate exists to prevent it.

The locked implementation is the 09-08 wiring:

- `frontend/src/features/auto-bet/strategy.ts` (Plan 09-08) — pure function `nextBetAmount({ strategy, base, lastBet, lastOutcome }): Money`:
  - `strategy === 'fixed'` → returns `base` (same amount every round, regardless of `lastOutcome`);
  - `strategy === 'martingale'` + `lastOutcome === 'win'` → returns `base` (RESETS to configured initial, NOT to `lastBet`);
  - `strategy === 'martingale'` + `lastOutcome === 'loss'` → returns `lastBet * 2`;
  - first round (no `lastOutcome`) → returns `base`.
  - The unit test suite anchors all four branches + the CONTEXT-locked "base = configured initial, NOT previous bet" semantics (Pitfall 5 mitigation).
- `frontend/src/stores/auto-bet.store.ts` (Plan 09-08) — Zustand slice declared WITHOUT `persist` middleware (REQ-AUTO-04 grep gate `grep "persist" frontend/src/stores/auto-bet.store.ts` returns zero). Shape: `{ isRunning, config: { strategy, base, autoCashoutTarget, stopLossCents, stopWinCents }, lastBet, lastOutcome, sessionPnL: { amount, sign }, start(config), stop(reason), recordOutcome(outcome) }`. The session P/L is stored as a `(Money, sign: -1 | 0 | 1)` tuple to keep Money VO discipline while supporting negatives (the Money VO refuses negative construction).
- `frontend/src/features/auto-bet/auto-bet-driver.ts` (Plan 09-08) — event-only driver, NO `setInterval` (RESEARCH Anti-Patterns gate). On `useAutoBetStore.start(config)` the driver subscribes via the new `subscribeWsEvent` pub-sub surface on `ws-dispatch.ts` to `round:started` / `round:settled` / `bet:my_cashed_out` / `bet:my_refunded`. On `round:started`: compute `amount = nextBetAmount(...)`, POST `placeBet({ amount, autoCashoutTarget: config.autoCashoutTarget })`; on 402 (insufficient balance) halt with reason `insufficient-balance`; on 409 (transient FSM race) do NOT halt (next round will retry); on `bet:my_cashed_out` / `bet:my_refunded`: update `lastOutcome` + accumulate `sessionPnL`; check stop conditions — halt if `sessionPnL <= -stopLossCents` (stop-loss) or `sessionPnL >= stopWinCents` (stop-win) with deduped amber toast. On `useAutoBetStore.stop()` the driver unsubscribes.
- `frontend/src/components/bet-panel.tsx` (Plan 09-08) — refactored to shadcn `Tabs` with `defaultValue='manual'`; the Manual trigger has a Lock icon when `isAutoRunning === true`; the Auto trigger has a pulsing accent dot when `isAutoRunning === true`. The Manual tab content wraps the Phase 7 form verbatim AND adds Lock + Alert + `opacity-50` + HTML-disabled inputs when `isAutoRunning === true` (the player cannot accidentally place a manual bet while Auto is driving the session P/L tracker).
- `frontend/src/components/auto-bet-form.tsx` (Plan 09-08) — five fields (target + strategy `RadioGroup` + base + stop-loss + stop-win) with Start button (accent fill when valid) + Stop button (variant `outline` + `border-destructive` + `text-destructive` — NO `bg-destructive` per UI-SPEC §Color grep gate).
- `frontend/src/components/auto-bet-session-panel.tsx` (Plan 09-08) — renders session P/L using accent for positive / `muted-foreground` for negative (NOT red — UI-SPEC §Color grep gate).

### Why NOT DB-persisted server-enforced stops (Option A)

The decisive arguments are infrastructure tax and the reload-surprise UX. The infrastructure tax is non-trivial: a new `player_auto_bet_state` table + a Mikro aggregate + a migration + a repository + repository tests + a projector that fans out from `bet.cashed_out` / `bet.lost` to update cumulative P/L + a sync surface so the FE can display current cumulative P/L without re-deriving it from the WS event stream + clear-on-Start semantics so an old stale row doesn't poison a fresh Start + the "is this row from a session that timed out?" reconciliation question. The reload-surprise UX is also a real problem: a strategy persisted across reloads can place bets the player does not remember authorizing — the support story for "I came back and my balance was different" becomes unprovable without a full session audit log. REQ-AUTO-04 explicitly names the safety-first posture ("does not survive page reload by default — UX explicit choice"); Option A directly contradicts that.

### Why NOT localStorage persist (Option C)

The decisive argument is that localStorage adds the reload-surprise factor WITHOUT any of Option A's server-side audit safety. A corrupted localStorage entry can put the driver into an unrecoverable state where it tries to place bets with stale config; a cross-device localStorage sync (some browsers do this with iCloud Tabs / Chrome Sync) can resurrect a session on a different device the player never asked for; the safety contract is impossible to defend in dispute. Plan 09-08 added the explicit grep gate `grep "persist" frontend/src/stores/auto-bet.store.ts` returns zero to PREVENT this option from sneaking in via a copy-paste from another store that uses persist middleware.

## Consequences

- **Locked in (per-session, no persist — REQ-AUTO-04 grep gate)**: `frontend/src/stores/auto-bet.store.ts` declares Zustand WITHOUT the `persist` middleware; the grep gate is part of the CI lint surface; every reload is a fresh session by construction. A future plan that adds `persist(...)` to this store re-opens this decision.
- **Locked in (FE-driven cumulative-since-Start stops)**: the driver tracks session P/L by subscribing to `bet:my_cashed_out` / `bet:my_refunded` since the Start click; resets to zero on Stop + on Start; backend stays stateless on stops. A future plan that adds server-side stop enforcement re-opens this decision.
- **Locked in (Martingale base = configured initial, NOT previous bet on win)**: `nextBetAmount({ strategy: 'martingale', lastOutcome: 'win' })` returns `base`, not `lastBet`. The CONTEXT-locked semantics; locked by unit test.
- **Locked in (event-only driver, NO setInterval)**: the driver is reactive on `round:started` / `round:settled` / `bet:my_cashed_out` / `bet:my_refunded` via the `subscribeWsEvent` pub-sub surface; the grep gate `grep "setInterval" frontend/src/features/auto-bet/auto-bet-driver.ts` returns zero (RESEARCH Anti-Patterns gate). A future plan adding a polling cadence re-opens this decision.
- **Locked in (autoCashoutTarget IS server-enforced)**: the auto-cashout target is sent in the `placeBet` body and enforced by `AutoCashoutTickService` per ADR-033. The auto-bet FE concern (Option B no-persist) and the auto-cashout server concern (ADR-033 server-enforced) are deliberately decoupled.
- **Locked in (defense against runaway = existing wallet invariants)**: Martingale cannot overflow the wallet because Phase 3's wallet enforces non-negative balance via Postgres CHECK constraint + the conditional UPDATE returns `affectedRowCount = 0` when the debit would drop balance below zero, surfacing `INSUFFICIENT_FUNDS` to the saga which compensates back to the player. The driver halts cleanly on the resulting 402. No additional server-side guard needed beyond what already exists.
- **Locked in (Manual tab disabled while Auto running)**: the Manual tab content shows Lock + Alert + opacity-50 + HTML-disabled inputs when `isAutoRunning === true`. The player cannot accidentally place a manual bet that confuses the driver's session P/L tracking; the Lock affordance per UI-SPEC is the visual cue.
- **Locked in (session P/L Money VO discipline)**: the session P/L is stored as `(Money, sign: -1 | 0 | 1)` to keep Money VO non-negative discipline (the VO refuses negative construction by design); the AutoBetSessionPanel renders accent for positive / muted-foreground for negative (NEVER red — UI-SPEC §Color grep gate, the same gate that protects against destructive-color misuse in the Stop button).
- **Foreclosed (Option A — DB-persisted server-enforced stops)**: no `player_auto_bet_state` table, no aggregate, no projector for cumulative P/L; the server is intentionally stateless on stops. A future regulatory or audit requirement would have to re-open this decision and propose a separate persisted-state subsystem.
- **Foreclosed (Option C — localStorage persist)**: no `persist` middleware on the Zustand slice; the grep gate exists to prevent its accidental introduction; cross-device localStorage sync cannot resurrect a session the player didn't authorize on a different device.
- **Anticipated recruiter question 1**: "Why doesn't auto-bet survive reload?" — defended: explicit UX safety choice (REQ-AUTO-04); the "surprise factor" of finding a strategy still running after a long-away reload is worse than the cost of re-arming the strategy explicitly; the persist-on-reload story has unprovable support stories for "my balance was different when I came back"; the no-persist default makes the contract clear — every reload = fresh session.
- **Anticipated recruiter question 2**: "What stops Martingale from overflowing the wallet?" — defended: the wallet enforces non-negative balance via Postgres CHECK constraint + the conditional UPDATE refuses debits that would drop balance below zero; the saga compensates the bet on `INSUFFICIENT_FUNDS`; the driver halts on the resulting 402 with reason `insufficient-balance` + deduped amber toast. The FE stop-loss threshold is the soft halt; the wallet's hard invariant is the safety net.
- **Anticipated recruiter question 3**: "Why FE-driven stops instead of server-enforced?" — defended: server-enforced stops would require a per-player session table + aggregate + projector + sync surface for marginal UX value (the player has the WS event stream to derive cumulative P/L from anyway); the CONTEXT D-03 picked FE-driven cumulative-since-Start to keep the server stateless on stops; auto-cashout IS server-enforced (separate concern per ADR-033) because the auto-cashout disconnect-safety guarantee genuinely requires server enforcement, but stops do not.

Cross-references: ADR-014 (Bet aggregate — `autoCashoutTarget` field added in Plan 09-02), ADR-018 (Money rounding — session P/L is `(Money, sign)` to keep VO discipline), ADR-021 (single lobby room — the WS events the driver subscribes to fan out from lobby + user rooms), ADR-026 (Zustand slice-per-concern + isolated multiplier store — the auto-bet store is a sibling isolation), ADR-027 (oidc-spa multi-tab refresh — the auto-bet driver lives in a single tab, multi-tab is the auth-only concern), ADR-031 (modal-over-live UX register — the Auto tab vs Manual tab tabbing is the bet-panel sibling pattern), ADR-033 (server-enforced auto-cashout — the autoCashoutTarget is server-enforced separately from the FE stops); Plan 09-02 SUMMARY (autoCashoutTarget field on Bet), Plan 09-08 SUMMARY (FE store + driver + strategy + form + tabbed BetPanel); REQ-AUTO-02 (fixed + Martingale strategies), REQ-AUTO-03 (stop-loss + stop-win), REQ-AUTO-04 (per-session, no persist), REQ-AUTO-05 (Auto tab with Start / Stop); Pitfall 5 (Martingale wallet overflow defense), Pitfall 10 (driver state syncs from server events).

## Alternatives Rejected

- **Option A — DB-persisted per-player strategy config + server-enforced stops** — infrastructure tax (new table + aggregate + migration + repository + projector + FE-BE sync surface + clear-on-Start semantics + stale-row reconciliation) for marginal UX value over the FE-driven approach; introduces the reload-surprise failure mode REQ-AUTO-04 explicitly avoids; auditability claim is unprovable in dispute without a full session log; defense against runaway sessions is already covered by the existing wallet non-negative-balance invariant.
- **Option C — localStorage-persisted FE config** — same reload-surprise failure mode as Option A without any server-side audit safety; corrupted localStorage can put the driver into an unrecoverable state; cross-device localStorage sync (iCloud Tabs / Chrome Sync) can resurrect sessions on different devices the player didn't authorize; the safety contract is impossible to defend in dispute; the Plan 09-08 grep gate `grep "persist" frontend/src/stores/auto-bet.store.ts` returns zero specifically to prevent this option from sneaking in.
