# ADR-035: OpenTelemetry SDK + nestjs-otel + Jaeger All-in-One

**Status**: Accepted
**Date**: 2026-05-31
**Phase**: 10

## Context

REQ-OBS-01 requires both backend services to emit OpenTelemetry traces with W3C TraceContext propagation across HTTP, AMQP, and WebSocket boundaries; REQ-OBS-02 layers Prometheus metrics on top; REQ-OBS-03 demands a recruiter can open Grafana with pre-provisioned dashboards on first `docker:up`. ROADMAP Phase 10 success criterion is that a single bet placed from the FE can be traced end-to-end from the React `placeBet` mutation through the HTTP controller, into the saga, across the `wallet.command.debit` AMQP round-trip, through the `WalletDebitedHandler` projector, into the WS `bet:my_active` emit — all under one `traceId` visible in a UI a reviewer can open.

The 10-CONTEXT decision D-05 names the SDK shape (`@opentelemetry/sdk-node` + `nestjs-otel` bridge + `getNodeAutoInstrumentations` covering http, express/nest, amqplib, pg) and D-01 names the trace backend (Jaeger all-in-one container in compose, OTLP exporter at `:4318`). The remaining question is whether to commit to those choices or take one of the well-known alternatives — commercial APM (Datadog / Splunk / Honeycomb) or Tempo + Grafana for traces — that the broader observability ecosystem offers.

Two forces shape the decision. First, the submission is play-money, behind Kong, local Docker only — there is no production deployment, no SaaS budget, no operational pager rotation, no PII residency concern. The observability stack exists to *prove correctness to a reviewer*, not to keep an operator on call. Second, OTel SDK init is the famous Footgun #1 of distributed tracing in Node: the SDK MUST run before any instrumented module is imported, or http auto-instrumentation never patches the listen call and the FIRST request goes untraced. Phase 10 Plan 10-03 already shipped the literal-first-import pattern (`import "./tracing"` as line 1 of `main.ts` in both services); this ADR ratifies the SDK choice retroactively while the import discipline is fresh in the codebase.

The ROADMAP anticipated this under the label "ADR-028", but Phases 5/6/7/8/9 consumed 019..034 before Phase 10 closed; the decision takes the next-free number ADR-035 with the renumber note recorded in Phase 10's closeout — same precedent set by Phase 7 (ADR-019..022 → 024..027), Phase 8 (ADR-023/024 → 028..031), and Phase 9 (ADR-025/026/027 → 032..034).

## Considered

- **Option A — `@opentelemetry/sdk-node` + `nestjs-otel` bridge + `getNodeAutoInstrumentations` + Jaeger all-in-one (chosen, locked by Plans 10-03 + 10-04)** — SDK initialized as the literal-first import of `main.ts` in both services; OTLP HTTP exporter posts to `http://jaeger:4318/v1/traces`; auto-instrumentations cover http (HTTP server + outbound axios), nest (controllers + providers), amqplib (publish + consume spans), pg (query spans). Jaeger all-in-one container exposes UI at `:16686`. Pros: open standard (W3C TraceContext rides in `traceparent` HTTP header + AMQP message properties + WS handshake header — no proprietary protocol); recruiter familiarity is high (Jaeger is the canonical OSS trace UI; the bet→saga→cashout span tree visualizes cleanly); single Jaeger container vs Tempo's required Grafana hookup; no SaaS credentials; existing Phase 2 outbox envelope's `correlationId` already rides alongside OTel `traceId` without disruption. Cons: OTel JS SDK is 0.x semver — periodic minor-version bumps required, breaking changes uncommon but occasionally land (especially around resource attribute helpers).
- **Option B — Commercial APM (Datadog / Splunk Observability / Honeycomb)** — proprietary agent + SaaS backend; auto-instrumentation typically richer than OTel auto-instrumentations; APM-grade alerting + anomaly detection bundled. Pros: zero compose containers (agent ships to SaaS); production-grade alerting story; richer instrumentation depth. Cons: SaaS credentials required (recruiter cannot reproduce the trace UI without provisioning an account); operational cost meaningful at any non-trivial scale; vendor lock-in (proprietary wire format would require re-instrumentation if switched); recruiter unfamiliarity — Datadog/Splunk dashboards are not part of standard fullstack-engineer prep; the submission framing is "local docker-compose only, no production deployment, no SaaS"; foreclosed by D-05 + scope.
- **Option C — Tempo + Grafana for traces (over Jaeger)** — Grafana Tempo is the Grafana-stack trace backend with the same OTLP exporter on the producer side; trace UI is the Grafana Explore tab. Pros: single Grafana UI for metrics + traces + logs (the famous "three pillars in one pane" pitch); shared identity/auth with the metrics dashboards. Cons: requires a second container (Tempo backend) alongside the already-present Grafana, where Jaeger is a single container with self-contained UI; Grafana's trace Explore tab is more friction than Jaeger's purpose-built trace timeline UI; the metrics dashboards (REQ-OBS-03) already exist in Grafana, but traces don't need to be in the same pane; the user-visible UX gain of unified pane is marginal when the reviewer will open both tabs once and screenshot them; foreclosed by D-01 ("2 extra containers for marginal UX gain when Grafana already exists for metrics").

## Decision

**Option A — `@opentelemetry/sdk-node` + `nestjs-otel` bridge + `getNodeAutoInstrumentations` (http + nest + amqplib + pg) + Jaeger all-in-one container exposing OTLP HTTP at `:4318` and UI at `:16686`.** Option B is rejected because the submission scope is "local docker-compose only, no SaaS, no production"; SaaS credentials would block recruiter reproduction. Option C is rejected because Jaeger is a single self-contained UI container vs Tempo's required Grafana hookup for marginal UX gain when Grafana already serves metrics.

The locked implementation is the 10-03 + 10-04 wiring:

- `services/games/src/tracing.ts` + `services/wallets/src/tracing.ts` (Plan 10-03) — instantiate `NodeSDK` with `OTLPTraceExporter({ url: env.OTEL_EXPORTER_OTLP_ENDPOINT })` + `getNodeAutoInstrumentations({ '@opentelemetry/instrumentation-fs': { enabled: false } })` (fs disabled per Footgun #2: noisy, low-signal spans flood the trace UI) + `resourceFromAttributes({ [ATTR_SERVICE_NAME]: env.OTEL_SERVICE_NAME })` + synchronous `sdk.start()` + SIGTERM `sdk.shutdown()` hook.
- `services/games/src/main.ts` + `services/wallets/src/main.ts` (Plan 10-03) — literal first line is `import "./tracing"`. Footgun #1 gate: `head -1 services/<svc>/src/main.ts | grep 'import "./tracing"'` matches in both services; the gate is enforced by the Plan 10-03 init-order test.
- `services/games/src/observability/observability.module.ts` + `services/wallets/src/observability/observability.module.ts` (Plan 10-03) — composes `OpenTelemetryModule.forRoot({ metrics: { apiMetrics: { enable: true } } })` (the `nestjs-otel` bridge) alongside the `LoggerModule.forRootAsync` pino enrichment that reads `trace.getActiveSpan()?.spanContext()` for the per-log `traceId` + `spanId` correlation.
- `docker-compose.yml` (Plan 10-04) — `jaeger` service at `jaegertracing/all-in-one:1.62` exposing `4318` (OTLP HTTP) and `16686` (UI), depended on by `games` + `wallets`; healthcheck on `/` returning 200.
- W3C TraceContext propagation rides automatically across HTTP via the http instrumentation's `traceparent` header injection/extraction; AMQP rides via amqplib instrumentation patching the `properties.headers` of published messages; the WS handshake span is created in `JwtIoAdapter` and links to the upstream HTTP trace via the `traceparent` cookie/header the FE forwards.

### Why NOT commercial APM (Option B)

The decisive arguments are scope + reproducibility. The submission is local docker-compose only — no production deployment, no SaaS budget. A recruiter cloning the repo and running `bun run docker:up` MUST get the trace UI for free without provisioning a Datadog account, signing a Honeycomb contract, or configuring an API key. Commercial APMs are also vendor-locked: switching from Datadog to Honeycomb requires re-instrumentation, where OTel-instrumented services can swap backends by changing only the exporter URL. The "open standard" property is the explicit anti-vendor-lock-in argument for this submission.

### Why NOT Tempo + Grafana for traces (Option C)

The decisive argument is container count vs UX gain. Jaeger all-in-one is ONE container with a self-contained, purpose-built trace timeline UI; Tempo requires a separate backend container PLUS the Grafana hookup PLUS dashboard provisioning, just to land in Grafana's Explore tab which is general-purpose, not trace-specialized. The "single pane of glass" UX argument is real for an ops team running 24/7 incident response across metrics + traces + logs, but a reviewer opening the submission for a one-time audit will visit each pane once — the unified-pane gain is marginal. The 10-CONTEXT D-01 explicitly cites "2 extra containers for marginal UX gain when Grafana already exists for metrics" as the rejection rationale.

## Consequences

- **Locked in (SDK init is the literal-first import of `main.ts`)**: Footgun #1 is closed by source-line discipline + a Plan 10-03 grep gate (`head -1 services/<svc>/src/main.ts | grep 'import "./tracing"'`). Any future plan that wants to add bootstrap code before `import "./tracing"` re-opens this decision because that line MUST be first.
- **Locked in (auto-instrumentations: http, nest, amqplib, pg)**: the trace UI shows the bet→saga→cashout span tree without per-service hand-rolled spans; explicit custom spans are added only where saga handlers cross queue boundaries to keep the parent-trace link visible across the AMQP hop. fs instrumentation is explicitly disabled because file-system spans flood the UI without contributing to correlation.
- **Locked in (W3C TraceContext, not Zipkin B3 or Jaeger uber-trace-id)**: HTTP `traceparent`/`tracestate` headers; AMQP `properties.headers.traceparent`. Foreclosed: any consumer that expects B3/uber-trace headers would need explicit propagator config; documented out-of-scope because this is a single-organization closed system.
- **Locked in (OTLP HTTP at `:4318`, not gRPC at `:4317`)**: HTTP exporter is the simpler payload format and the default for `nestjs-otel` examples; gRPC adds proto compilation friction without throughput gain at submission scale. Foreclosed: high-throughput production setups that prefer gRPC's smaller wire format would need explicit reconfiguration.
- **Locked in (Jaeger all-in-one over Tempo + Grafana)**: one container, one UI; no Grafana data-source provisioning required for traces. Foreclosed: any future feature that wants traces + metrics in a single Grafana Explore pane would re-open the decision and migrate the trace backend to Tempo.
- **Locked in (no commercial APM)**: zero SaaS credentials in the submission; recruiter reproduces the full trace UI from `bun run docker:up`. Foreclosed: any production deployment story that needs APM-grade alerting + anomaly detection would re-open the decision and propose Datadog/Honeycomb as a layered addition on top of the OTel SDK (the SDK choice itself stays — OTel exports to any backend).
- **Locked in (3 new compose containers — Jaeger, Prometheus, Grafana — collectively about 1.5GB of pulled images)**: container count grew from the Phase 9 baseline; the CI free-disk-space pre-step (Plan 10-08) was sized to absorb this growth (10-08 already prunes ~4GB of unused image layers). On macOS dev laptops, the disk delta is ~1.5GB additional after first pull.
- **Locked in (OTel SDK 0.x semver bumps require periodic minor-version sweeps)**: the SDK is not yet 1.0 for all auto-instrumentations; minor-version bumps occasionally break API surface (resource attribute helpers were renamed once in 2024-2025). The submission pins to the Plan 10-02 lock; any future bump must re-verify the auto-instrumentations against the bet→saga→cashout span tree.
- **Anticipated recruiter question 1**: "Why not Datadog?" — defended: scope is local docker-compose only with zero SaaS credentials in the submission; Jaeger gives the trace UI for free; OTel's open-standard property means a future production deployment can swap to Datadog by changing only the exporter URL — the instrumentation is portable.
- **Anticipated recruiter question 2**: "Why Jaeger over Tempo?" — defended: Jaeger is one self-contained UI container; Tempo requires a separate backend plus Grafana Explore plumbing for traces, which lands in a general-purpose pane rather than Jaeger's purpose-built trace timeline; the 10-CONTEXT D-01 calls out the "2 extra containers for marginal UX gain" trade-off.
- **Anticipated recruiter question 3**: "What about the SDK init order?" — defended: Footgun #1 is the literal-first-import discipline in `main.ts` for both services; the Plan 10-03 init-order test asserts the line via a grep gate; any plan that wants to inject bootstrap code before `tracing.ts` is treated as a re-opening of this decision.

Cross-references: ADR-007 (hand-rolled outbox/inbox — the AMQP envelope this OTel context propagates alongside), ADR-008 (amqplib publisher + golevelup consumer — the amqplib auto-instrumentation patches both client sides), ADR-021 (single global lobby — the WS gateway span this trace links to), Plan 10-02 SUMMARY (deps install gated by package-legitimacy checkpoint — OTel SDK + nestjs-otel locked at versions), Plan 10-03 SUMMARY (literal-first-import + ObservabilityModule + pino enrichment), Plan 10-04 SUMMARY (Jaeger + Prometheus + Grafana compose stack); REQ-OBS-01 (OTel traces across HTTP+AMQP+WS), REQ-OBS-04 (pino + traceId enrichment — the per-log correlation that rides this SDK choice).

## Alternatives Rejected

- **Option B — Commercial APM (Datadog / Splunk / Honeycomb)** — vendor lock-in; SaaS credentials block recruiter reproduction; operational cost; foreclosed by submission scope (local docker-compose only, no SaaS).
- **Option C — Tempo + Grafana for traces** — 2 extra compose containers (Tempo backend + Grafana data-source plumbing) for marginal UX gain (trace UI lands in Grafana's general-purpose Explore tab vs Jaeger's purpose-built trace timeline); foreclosed by 10-CONTEXT D-01.
