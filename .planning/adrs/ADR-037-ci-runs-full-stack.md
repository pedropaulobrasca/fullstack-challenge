# ADR-037: CI Runs Full `docker:up` Stack on Every Push and PR

**Status**: Accepted
**Date**: 2026-05-31
**Phase**: 10

## Context

REQ-CI-02 requires CI to run `bun run docker:up` on a fresh clone, wait for healthchecks, run E2E + Playwright against the live stack, then tear down — explicitly framed as "proving the zero-step bootstrap claim". The headline submission claim from Phase 1 (REQ-INFRA-01) is that a fresh clone reaches a fully working state with no manual steps: realm import, migrations, exchange/queue topology, Kong routes, demo user, wallet seed all load via `docker:up`. The only way to prove that claim is to have an automation independently clone the repo, run `docker:up`, and observe success — anything less is a self-assertion the recruiter can't verify without running the stack themselves.

The naive CI shape is a unit-test-only pipeline with mocked external services — fast, cheap, low-risk. It is also the wrong shape for this submission, because it does not exercise the artifacts where REQ-INFRA-01 lives: compose healthchecks, Keycloak realm import, `games-migrate` + `wallets-migrate` init containers, RabbitMQ topology bootstrap, Kong route loading, OIDC end-to-end. A green unit-only run says nothing about whether the bootstrap claim holds; the recruiter would have to take the README's word for it.

Three forces shape the decision. First, the headline claim demands a full-stack proof; the only honest gate is to actually run the stack. Second, the GitHub Actions free runner has ~14GB free disk against the ~10GB pulled compose image set (Postgres + RabbitMQ + Keycloak + Kong + Jaeger + Prometheus + Grafana + 2 service images + Playwright chromium with deps); without disk hygiene the runner OOMs during `docker compose pull` (Pitfall 8). Third, CI cost matters but is not the binding constraint at submission scale — a single push triggers a single ~10 min run on a free runner; multiple pushes are cancel-per-ref so concurrent in-flight runs collapse to one.

The ROADMAP anticipated this under the label "ADR-030" (Phase 10 CI strategy), but Phases 5/6/7/8/9 consumed 019..034 before Phase 10 closed; the decision takes the next-free number ADR-037 with the renumber note recorded in Phase 10's closeout.

## Considered

- **Option A — Single GitHub Actions ubuntu-latest job: free-disk + bun + lint + typecheck + ADR-index-check + unit + `bun run docker:up` + smoke probes + INTEGRATION=1 + Playwright + always() teardown + failure() Playwright artifact (chosen, locked by Plan 10-08 + 10-09 Task 1)** — single workflow file `.github/workflows/ci.yml`; concurrency cancel-per-ref so multiple pushes collapse to one in-flight run; pre-step `sudo rm -rf /usr/share/dotnet /opt/ghc /usr/local/share/boost "$AGENT_TOOLSDIRECTORY" && docker image prune -af` frees ~4GB to accommodate the compose image set; `bun run docker:up` (already bakes `--wait`) blocks until all healthchecks pass; `scripts/smoke-health.sh` runs 47 probes for infra liveness; INTEGRATION=1 runs the games + wallets integration suites against the live stack; Playwright chromium runs the 2 REQ-TEST-05 specs (Plan 10-07); `always()` teardown ensures the stack stops even on test failure; `failure()`-gated `actions/upload-artifact@v4` uploads `e2e/playwright-report/` + `e2e/test-results/` for triage (the `.auth/` storageState file is explicitly excluded — T-10-19 mitigation). Pros: proves REQ-INFRA-01 end-to-end on every push + PR; gives recruiters a green badge they can trust without running the stack themselves; catches integration regressions (realm import drift, Kong route reorder, OIDC redirect misconfig) that unit suites can't see. Cons: ~8-15 min wall-clock per run; pulls ~10GB of images per fresh runner (cached layers help on subsequent runs but free runners don't persist cache aggressively); actions-minutes consumption (free tier 2000/mo is plenty for solo work; would matter at high PR volume).
- **Option B — Unit-only pipeline with mocked external services** — `bun install` + `bun test` + maybe lint. No compose, no migrations, no Playwright. Pros: fast (<2 min); free-tier-friendly; no disk pressure. Cons: does NOT exercise the bootstrap claim — a green unit run says nothing about whether `docker:up` works on a fresh clone; the recruiter cannot trust the badge without running the stack themselves, which defeats the headline submission claim; misses every integration regression (Keycloak realm drift, Kong route reorder, RabbitMQ topology mismatch, OIDC redirect misconfig); cannot run Playwright (FE has no live backend to talk to in a mocked-deps world). Foreclosed by REQ-CI-02 — the requirement is literally "prove the zero-step bootstrap claim".
- **Option C — Self-hosted runner with persistent docker layer cache** — provision a dedicated runner with a warm docker cache; CI runs full stack but skips the ~3-5 min pull step. Pros: faster CI; cache layers persist across runs. Cons: operational burden disproportionate for a submission (runner uptime, OS patching, secret rotation, geographic redundancy, runner version drift); recruiter cannot easily reproduce the runner setup; the GitHub-hosted free runner gives sufficient performance at submission scale; foreclosed by operational scope (the submission is "local docker-compose only, no production deployment", and self-hosted runners are squarely production-ops territory).

## Decision

**Option A — Single GitHub Actions ubuntu-latest job with timeout-minutes 30, concurrency cancel-per-ref, 13-step pipeline (free-disk → setup-bun → install → lint → typecheck → ADR-index-check → unit → `docker:up` with OTLP endpoint env → smoke probes → integration → chromium install → Playwright → always() teardown), failure()-gated artifact upload of `e2e/playwright-report/` excluding `.auth/`.** Option B is rejected because a unit-only pipeline does not exercise the REQ-INFRA-01 bootstrap claim and CI is the only honest gate for that claim. Option C is rejected because self-hosted runners impose operational burden disproportionate to a submission's scope.

The locked implementation is the 10-08 + 10-09 Task 1 wiring:

- `.github/workflows/ci.yml` (Plan 10-08 + Plan 10-09 Task 1) — single workflow named `CI` triggered on `push: branches: [main]` and `pull_request:`; `concurrency: group: ${{ github.workflow }}-${{ github.ref }}, cancel-in-progress: true` collapses concurrent runs for the same branch; `timeout-minutes: 30` is the upper bound (typical run completes in ~10-12 min).
- Free-disk-space pre-step: `sudo rm -rf /usr/share/dotnet /opt/ghc /usr/local/share/boost "$AGENT_TOOLSDIRECTORY" && docker image prune -af` reclaims ~4GB; the runner has ~14GB free before the step and ~18GB after — Pitfall 8 mitigation against the ~10GB compose image set.
- `oven-sh/setup-bun@v2` with `bun-version-file: .bun-version` (NOT a hardcoded version string — Plan 10-08 sanctioned the `-file` variant over the RESEARCH-cited `bun-version: 1.3.11` because the file is the single source of truth).
- `bun install --frozen-lockfile` — fails CI if `bun.lock` drifts from `package.json`.
- `bun run lint` + `bun run typecheck` + `bun run docs:adr-index:check` + `bun test` — host-side fast-fail before paying the docker-boot cost; the ADR-index check (Plan 10-09 Task 1) sits between typecheck and unit tests so a stale README short-circuits before the ~30s unit suite runs.
- `bun run docker:up` (the root script already bakes `--wait` — Plan 10-08 confirmed it is not double-passed) with `env: OTEL_EXPORTER_OTLP_ENDPOINT: http://localhost:4318/v1/traces` so the OTel SDK (ADR-035) exports to the Jaeger container alongside the services.
- `bash scripts/smoke-health.sh` runs all 47 infra-liveness probes; failures here fast-fail before the heavier integration + Playwright suites.
- `INTEGRATION=1 bun --cwd services/games test tests/integration` + `INTEGRATION=1 bun --cwd services/wallets test tests/integration` — exercises the saga round-trips against the live RabbitMQ + Postgres.
- `cd frontend && bunx playwright install --with-deps chromium` then `bunx playwright test --config=e2e/playwright.config.ts` runs the 2 REQ-TEST-05 specs from Plan 10-07 against the live frontend + backend.
- `always()` teardown step `bun run docker:down` ensures the stack stops even on test failure (otherwise the runner dies with the containers still running, leaking actions-minutes on idle infrastructure).
- `failure()`-gated `actions/upload-artifact@v4` uploads `e2e/playwright-report/` + `e2e/test-results/` at `retention-days: 14` for post-failure triage; the upload pattern explicitly excludes `e2e/.auth/` (the storageState file holding the demo user's session cookie — never artifact'd, T-10-19 mitigation).
- Green-run attestation: the first push triggers the workflow; once green, the README CI badge (Plan 10-09 Task 3) reflects it; REQ-CI-01 + REQ-CI-02 close at the workflow-file level on plan 10-08 land, with the end-to-end green-run attestation deferring to the user's first push.

### Why NOT unit-only with mocks (Option B)

The decisive argument is the requirement's plain language. REQ-CI-02 says "CI runs `bun run docker:up` on a fresh clone, waits for healthchecks, runs E2E + Playwright against the live stack, then tears down — proving the zero-step bootstrap claim". A unit-only pipeline mocks away precisely the artifacts the claim is about. The recruiter looking at the green badge would have no evidence the bootstrap actually works; they would have to clone the repo and run it themselves, which is the friction the badge is supposed to eliminate. The bootstrap claim is also the most-cited evidence of senior-level engineering in the submission framing — gating it behind a unit-only badge would undercut the headline.

### Why NOT self-hosted (Option C)

The decisive argument is operational scope. Self-hosted runners are production-ops territory — runner uptime, OS patching, version drift, secret rotation, geographic redundancy. The submission framing is "local docker-compose only, no production deployment" (per REQ-INFRA-01 + the explicit Out of Scope list). A self-hosted runner would be the only production-ops artifact in the submission, disproportionate to the scope and impossible for a recruiter to reproduce without provisioning their own infrastructure. The GitHub-hosted free runner at ~10-12 min per run is fast enough for solo work and the free-tier 2000 actions-minutes/mo is plenty.

## Consequences

- **Locked in (CI proves REQ-INFRA-01 end-to-end on every push + PR)**: a green badge means the full stack came up from a fresh clone, all healthchecks passed, integration suites passed against live RabbitMQ + Postgres, and the 2 REQ-TEST-05 Playwright specs passed against the live FE + BE. Foreclosed: any future PR that breaks the bootstrap claim cannot merge silently — CI fails first.
- **Locked in (cancel-per-ref concurrency)**: a rapid sequence of pushes to the same branch collapses to one in-flight run; the runner that was mid-stack-boot for the older commit is cancelled and a fresh runner starts on the newer commit. Saves actions-minutes and ensures the badge reflects the latest commit, not a stale in-flight run.
- **Locked in (free-disk pre-step)**: ~4GB reclaimed from the runner before `docker compose pull` runs; Pitfall 8 mitigation against the ~10GB compose image set growing from Phase 9's ~7GB baseline by ~3GB for the Jaeger + Prometheus + Grafana additions (ADR-035 stack). Foreclosed: any future plan that adds a non-trivial container (e.g., a search index, a queue broker) must verify the free-disk margin is still positive.
- **Locked in (timeout-minutes 30 with typical ~10-12 min wall-clock)**: budget is 3x typical, leaving room for a slow `docker compose pull` on a cold runner or a flaky Playwright spec; runs that exceed 30 min are forcibly cancelled, preventing runaway-loop actions-minutes leaks.
- **Locked in (failure-only artifact upload, never `.auth/`)**: green runs do not produce artifacts (saves storage); failed runs upload the Playwright HTML report + test-results for triage at 14-day retention; the storageState file `e2e/.auth/` is explicitly excluded — T-10-19 mitigation (the storageState holds a Keycloak session cookie that would be leaked via the public actions artifact storage if accidentally included).
- **Locked in (ADR-index-check between typecheck and unit tests)**: the Plan 10-09 Task 1 gate sits at the fastest fast-fail position — a stale README short-circuits before the ~30s unit suite + the ~6-8 min docker boot, saving ~7-8 min per drift run.
- **Locked in (no self-hosted runner)**: zero ops infrastructure in the submission; recruiter clones the repo, watches Actions tab, sees green. Foreclosed: any future scale-out (multi-OS matrix, GPU-accelerated tests) would re-open the decision; the current scope does not motivate it.
- **Foreclosed (Option B)**: no unit-only pipeline; CI gates the full bootstrap claim or it does not gate the claim at all.
- **Foreclosed (Option C)**: no self-hosted runner; CI runs on GitHub-hosted ubuntu-latest.
- **Anticipated recruiter question 1**: "Does the CI actually run the docker stack or is it mocked?" — defended: CI runs `bun run docker:up` on a fresh ubuntu-latest runner with no warm cache, waits for all healthchecks, then runs integration + Playwright against the live stack; the green badge means the bootstrap claim held end-to-end on this commit.
- **Anticipated recruiter question 2**: "Why not self-hosted for speed?" — defended: self-hosted runners are production-ops territory (uptime, patching, version drift, secret rotation); the submission framing is "local docker-compose only, no production deployment"; GitHub-hosted runners at ~10-12 min/run are fast enough for solo work and the free-tier actions-minutes are plenty.
- **Anticipated recruiter question 3**: "How do you handle Playwright flake in CI?" — defended: the 2 REQ-TEST-05 specs were authored Rule-1-fixed for live races (instant-crash retry via `page.reload`, fresh-BETTING-window poll against `/games/rounds/current` `bettingEndsAt` with >=3.5s floor — Plan 10-07); failed runs upload the HTML report + traces for post-mortem; consistent green across 3 consecutive runs on plan 10-07 land.

- **Option B — Unit-only pipeline with mocked external services** — does not exercise the REQ-INFRA-01 bootstrap claim; recruiter cannot trust the badge without running the stack themselves, defeating the badge's purpose; misses every integration regression (realm import drift, Kong route reorder, RabbitMQ topology mismatch, OIDC redirect misconfig); cannot run Playwright against a mocked-deps backend; foreclosed by REQ-CI-02 plain language.
- **Option C — Self-hosted runner with persistent docker cache** — operational burden disproportionate for a submission (uptime, patching, version drift, secret rotation); recruiter cannot reproduce without provisioning their own runner; the submission framing is "local docker-compose only, no production deployment"; foreclosed by operational scope.
