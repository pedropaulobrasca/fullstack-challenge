<objective>
Pin the runtime baseline of the monorepo so every downstream task (shared-kernel install, service Dockerfiles, CI in Phase 10) resolves to a single known-good Bun version, and expose the root npm scripts that subsequent plans assume exist.

Purpose: Bun 1.3.10 broke NestJS controllers (regression oven-sh/bun#27526). Bun 1.3.11 fixed it. Pin to `1.3.11` exact in `.bun-version` AND `packageManager` so a floating tag cannot silently regress mid-development.

Output: `.bun-version`, an expanded root `package.json` (scripts + packageManager + minimal dev deps), and a `.gitignore` that covers env files and build artifacts.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| developer machine → repo | Unpinned tooling versions silently change runtime behavior |
| repo → CI / Docker images | Floating tags pull surprise upstream changes |
| repo → git history | `.env` files may carry secrets and must never be committed |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-01-01 | Tampering | Bun runtime | mitigate | Exact pin via `.bun-version=1.3.11` and `packageManager=bun@1.3.11`; matched by Dockerfile tag in P1.3 |
| T-01-02 | Tampering | npm dependency tree | mitigate | `bun.lock` committed; future installs use `--frozen-lockfile` (enforced in Dockerfile in P1.3) |
| T-01-03 | Information Disclosure | `.env` files | mitigate | `.gitignore` lists each `.env*` variant explicitly (avoids `.env*` glob masking `.env.example`) |
| T-01-04 | Tampering | npm packages (eslint, prettier, typescript, typescript-eslint, bun-types) | accept | All packages are universally known and either Microsoft-published, eslint-foundation-published, or Oven-published. No `[ASSUMED]`/`[SUS]` packages introduced in this plan. RESEARCH.md `## Package Legitimacy Audit` covers the broader Phase 1 install set. |
| T-01-SC | Tampering | npm install supply chain (general) | mitigate | RESEARCH §Package Legitimacy Audit reviewed; no `[SLOP]` packages introduced. New packages flagged `[ASSUMED]` belong to P1.4/P1.5/P1.6 where their slopcheck checkpoints live, not this plan. |
</threat_model>
