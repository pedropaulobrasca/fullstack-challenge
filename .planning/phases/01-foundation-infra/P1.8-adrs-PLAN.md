**ADR-002-money-dinero-vo.md** — Title: "Money representation — Dinero.js v2 wrapped in local VO"
- Status: Accepted
- Phase: 1
- Context: REQ-DOM-06 forbids `number` for money everywhere. Float math is an instant disqualifier in the rubric. Three candidates: dinero.js v2, raw bigint+scale, decimal.js.
- Considered: dinero.js v2 (just-stable March 2026; bigint native; isomorphic; Martin Fowler Money pattern) / raw bigint+scale (max control, max bugs — hand-roll formatting, rounding, currency mismatch) / decimal.js (general-purpose, no currency concept, used internally by Prisma but overkill here).
- Decision: dinero.js v2, wrapped in a project-local `Money` value object (`packages/shared-kernel/src/money/money.ts`). Wrapper enforces non-negative invariant, currency mismatch, exposes only `add/subtract/multiply/compareTo/isZero` — dinero is an implementation detail. Snapshot JSON shape `{ amount: string, currency, scale: number }` — amount is STRING (not bigint) for JSON safety (bigint does not serialize natively).
- Consequences: Money VO becomes the only sanctioned monetary path (enforced by ESLint rule in ADR-006). Snapshot wire format is locked across services and frontend. Banker's rounding is dinero's default and is acceptable for Phase 1; formal rounding-policy lock for `multiply` happens in Phase 4 ADR-011 alongside cashout-payout computation.
- Alternatives Rejected: list three with one-line "why not."

**ADR-003-bun-pinning.md** — Title: "Bun + NestJS pinning strategy"
- Status: Accepted
- Phase: 1
- Context: Bun 1.3.10 introduced a NestJS controller-decorator regression (oven-sh/bun#27526) fixed in 1.3.11. Floating `oven/bun:1-alpine` tag risks pulling 1.3.10 (or a future regression) mid-development. Decorator metadata must be emitted reliably for NestJS DI + MikroORM entities.
- Considered: Pin exact `.bun-version=1.3.11` and `oven/bun:1.3.11-alpine` (no floating) / Pin minor `>=1.3.11` (allows future patches) / Use `1.3` floating tag (current scaffold default).
- Decision: Exact pin `1.3.11` in `.bun-version`, `packageManager: bun@1.3.11` in root `package.json`, `oven/bun:1.3.11-alpine` in every service Dockerfile. Additionally, `emitDecoratorMetadata: true` AND `experimentalDecorators: true` are set EXPLICITLY in every service's `tsconfig.json` (not inherited) — Bun's reaction to `emitDecoratorMetadata: true` flipped between 1.3.10 (TC39 standard semantics) and 1.3.11 (legacy semantics), so explicit settings document intent and survive Bun upgrades.
- Consequences: Requires manual `.bun-version` bump (and Dockerfile bump) to take new Bun versions — deliberate friction. Forecloses silent upgrades. Phase 10 CI will use the same pinned image. If a future Bun release regresses again, all instances of `1.3.11` are searchable and update-in-place.
- Alternatives Rejected: list three.

**ADR-004-config-source-of-truth.md** — Title: "Configuration source-of-truth shape"
- Status: Accepted
- Phase: 1
- Context: REQ-INFRA-05 forbids hardcoded business constants. Every operator-tunable (19 constants in REQUIREMENTS §Open Configuration Values) must flow from env. NestJS `@nestjs/config` returns `string | undefined` and forces per-consumer parsing — exactly the pattern that causes "INITIAL_BALANCE_CENTS leaked as a number" bugs.
- Considered: zod-parsed typed `defaults.ts` per service (single consumer; fail-fast at boot) / `@nestjs/config` alone (returns untyped strings; per-consumer parse) / convict (env+schema lib; one more dep with overlap).
- Decision: `.env.example` per service (committed) + root superset `.env.example` + per-service `src/config/defaults.ts` that imports `sharedEnvSchema` from `@crash/shared-kernel`, extends with service-specific keys, parses `process.env`, `Object.freeze`s the result, and exports typed `env`. - Consequences: One place to look for env contract per service (the schema file). Adding an env var requires updating both the schema and the `.env.example`. Forecloses ad-hoc `process.env.X` access. `mikro-orm.config.ts` is exempted from the ESLint ban because the CLI config runs before NestJS bootstrap.
- Alternatives Rejected: list three.

**ADR-006-eslint-plugin-location.md** — Title: "ESLint money-guard plugin location and authoring approach"
- Status: Accepted
- Phase: 1
- Context: REQ-DOM-06 requires `Money` VO usage and bans `number` on money-named identifiers. ESLint is the enforcement vector. Two open sub-decisions: (a) where does the custom rule live? (b) how is the rule authored?
- Considered: (a-1) Inline rule in `eslint.config.js` (no package, no test fixtures, hard to evolve) / (a-2) Workspace package `packages/eslint-plugin` (clean separation, fixture tests possible, future rules co-located) / (a-3) Repo-local `tools/eslint-plugin` directory (workspace-but-not-a-package; loses Bun symlink benefits). (b-1) Hand-roll `module.exports = { rules: {} }` (no types, no doc URLs) / (b-2) `@typescript-eslint/utils` `ESLintUtils.RuleCreator` (typed rule context, doc URL helper, AST_NODE_TYPES enum).
- Decision: (a) Workspace package `packages/eslint-plugin` consumed from root `eslint.config.js` flat-config via `import crashPlugin from "@crash/eslint-plugin"`. (b) Author with `@typescript-eslint/utils` `ESLintUtils.RuleCreator` and `@typescript-eslint/rule-tester` for fixture-driven tests. Both authoring choices align with current typescript-eslint guidance (8.x).
- Consequences: Adding new rules later requires only a new file in `packages/eslint-plugin/src/rules/`. Tests live with the rule. Known limitation: the rule's regex matches identifier NAMES — a developer renaming `totalAmount: number` to `total: number` evades the rule (code review must catch it). Documented as accepted trade-off; future enhancement could integrate type-flow analysis but adds significant complexity for diminishing returns.
- Alternatives Rejected: inline rule, hand-rolled rule, repo-local non-package directory.
