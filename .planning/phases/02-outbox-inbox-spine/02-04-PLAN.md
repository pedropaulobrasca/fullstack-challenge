<objective>
Implement the write side of the outbox: the repository the application uses to enqueue events inside its own TX, the dedicated pg LISTEN client that wakes the poller sub-second, and the polling publisher that drains the outbox to RabbitMQ with at-least-once confirms semantics. This plan owns every artifact a service needs to PUBLISH; the consume side (inbox decorator + dead-letter handler) is plan 02-05.

Purpose: REQ-WALL-06 is satisfied by the combination of `OutboxRepository.add` (same-TX dual-write fix) plus `OutboxPublisher` (confirmSelect + waitForConfirms + FOR UPDATE SKIP LOCKED batch claim). The dedicated `pg.Client` for LISTEN is a non-negotiable architecture choice (PITFALLS-derived: MikroORM's pool starves if LISTEN blocks one of its connections, per 02-RESEARCH §Pattern 3 and §Pitfall 1).

Output: Four files implementing the write-side outbox lifecycle, ready for plan 02-06 to compose into MessagingSpineModule.forRootAsync.
</objective>

| Threat ID | Category | Component | Disposition | Mitigation Plan |

| T-02-09 | Tampering | Dual-write loss (commit succeeds, broker publish lost) | mitigate | em.transactional wraps the claim+publish+mark; waitForConfirms throws → TX rolls back → rows stay PENDING for next poll. Verified by plan 02-09 kill-9-recovery integration test. |
