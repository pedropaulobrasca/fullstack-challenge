  <action>Author four ADR files following the canonical 5-section template (Context / Considered / Decision / Consequences / Alternatives Rejected):

  **ADR-007: Hand-rolled @crash/messaging-spine workspace package over nestjs-outbox / pg-transactional-outbox**
  - Context: Phase 2 needs outbox + inbox + DLQ + confirm-channel publisher + LISTEN/NOTIFY wake. Two libraries exist (nestjs-outbox by fullstackhouse, pg-transactional-outbox).
  - Considered: (a) nestjs-outbox — supports LISTEN/NOTIFY with MikroORM driver but ~600 weekly downloads, single maintainer, hides confirm channel; (b) pg-transactional-outbox — couples to WAL replication strategy too tightly for our polling needs; (c) MikroORM blog OutboxEvent pattern — no inbox at all, no DLX; (d) hand-roll in workspace package.
  - Decision: Hand-roll in `packages/messaging-spine/` as @crash/messaging-spine. ~600 LOC across the implementation lets recruiters read every decision in the repo — central to the 25% DDD/Architecture score. Code is auditable in arguição without diving into a transitive dependency.
  - Consequences: We own the polling loop, the confirm channel lifecycle, the inbox dedup contract, the DLQ persister. Maintenance burden is real but matches the "demonstrate engineering depth" core value. Future archival/metrics work goes into the same package.
  - Alternatives Rejected: Each listed (a)-(c) above with one-line rejection rationale tied to scoring or scope.

  **ADR-008: amqplib raw publisher + @golevelup/nestjs-rabbitmq consumer split, over @nestjs/microservices RMQ transport alone**
  - Context: Outbox publisher needs `confirmSelect` + `waitForConfirms`; consumers need ergonomic `@RabbitSubscribe` decorators and connection-lifecycle management.
  - Considered: (a) raw amqplib end-to-end; (b) @nestjs/microservices RMQ transport end-to-end; (c) @golevelup/nestjs-rabbitmq end-to-end; (d) the chosen split — raw amqplib confirm channel inside OutboxPublisher, @golevelup for consumer-side @RabbitSubscribe.
  - Decision: Use both intentionally. Raw amqplib in OutboxPublisher because we own the confirm-channel lifecycle (createConfirmChannel + waitForConfirms + close on shutdown). @golevelup on the consumer side because @RabbitSubscribe wraps queue-binding + connection reconnection cleanly, and our @IdempotentSubscribe decorator stacks naturally on top of it.
  - Consequences: One AMQP connection (managed by @golevelup AmqpConnection) hosts both directions. We pay a small mental-model cost ("two APIs for the same broker") in exchange for full confirm semantics + clean decorator ergonomics. Documented as the explicit reason @nestjs/microservices was rejected.
  - Alternatives Rejected: (a) and (b) and (c) per above.

  **ADR-009: DLX with x-delivery-limit on the DLQ itself (quorum queues, RabbitMQ 4.2)**
  - Context: Per PITFALLS C4 and joaovieira.ca, a DLQ without its own `x-delivery-limit` allows a poison message that fails further routing to loop indefinitely, which has documented track record of taking down clusters.
  - Considered: (a) classic queues with manual retry/ack (rejected — no first-class poison handling); (b) quorum queues with `x-delivery-limit` on main only (insufficient — DLQ poison loops); (c) quorum queues with limits on BOTH main and DLQ (chosen).
  - Decision: Every main queue declares `x-queue-type=quorum`, `x-delivery-limit=RMQ_DELIVERY_LIMIT_MAIN` (env-default 5), `x-dead-letter-exchange=<dlx>`. Every DLQ declares `x-queue-type=quorum`, `x-delivery-limit=RMQ_DELIVERY_LIMIT_DLQ` (env-default 3). The DeadLetterConsumer (plan 02-05/02-07) consumes the DLQ and persists exhausted messages to `dead_letter_messages` table, always acks.
  - Consequences: Bounded poison absorption: 5 attempts main + 3 attempts DLQ. After dead_letter_messages persist fails, the broker drops the message after the third DLQ attempt — acceptable last-resort behavior because logs surface it. Operators inspect `dead_letter_messages` via SQL (Phase 10 may add a replay endpoint).
  - Alternatives Rejected: As above.

  **ADR-010: Dedicated pg.Client for LISTEN/NOTIFY, separate from MikroORM pool**
  - Context: 02-RESEARCH §Pattern 3 + §Pitfall 1 — LISTEN blocks a connection. If we LISTEN on a MikroORM pool connection, the pool starves; concurrent application queries hang.
  - Considered: (a) borrow a connection from MikroORM (rejected — pool starvation); (b) increase pool size by 1 and reserve one for LISTEN (rejected — fragile, hard to enforce); (c) dedicated `pg.Client` with reconnect + watchdog (chosen).
  - Decision: `OutboxListenerService` instantiates `new pg.Client({ connectionString: opts.databaseUrl })` separately from MikroORM. Registers `LISTEN outbox_new_message`, watchdog SELECT 1 every 30s, exponential reconnect on error/end events. Per PITFALLS-derived rationale, this is the canonical pattern in every production outbox writeup.
  - Consequences: One extra Postgres connection per service. Trivial cost relative to MikroORM's pool. Failure modes (silent LISTEN death) are handled by the watchdog. Documented in plan 02-04 (OutboxListenerService).
  - Alternatives Rejected: As above.
