<objective>
Patch `@crash/messaging-spine` to resolve Phase 2 carry-forwards OI-1 (envelope double-wrap) and OI-3 (EM identity-map flush) before any Phase 3 handler is written. The fix is surgical: unwrap the nested `rawPayload.payload` and thread the transactional EntityManager (`txEm`) into the wrapped handler signature. Re-run the existing Phase 2 unit + integration suites to prove blast radius is bounded.

Purpose: Without this, every Phase 3 AMQP handler would need raw SQL for entity persistence (defeating ADR-001) AND would have to walk `envelope.payload.payload.x` to read fields (anti-DRY across future handlers).
Output: Patched decorator, regression test, green Phase 2 suites, and a public-API change documented for ADR-013.
</objective>

Current wrapped handler signature (line 88-92): `(rawPayload: unknown, msg: ConsumeMessage) => undefined | Nack`
NEW wrapped handler signature after this plan: `(envelope: { ...meta, payload }, msg: ConsumeMessage, txEm: EntityManager) => undefined | Nack`

OI-1 root cause (line 121-129): the decorator builds a synthetic envelope where `payload: rawPayload`, but `rawPayload` IS itself the already-parsed envelope wire body (publisher serialised `buildEnvelope({ payload })` whole to AMQP), so reading `envelope.payload.field` requires one extra hop (`envelope.payload.payload.field`).

OI-3 root cause (line 113): the decorator opens `host.em.transactional(async () => { ... })` and calls `original.call(host, envelope, msg)`. The handler's `host.em` is the root EM, NOT the transactional fork — entity mutations on `host.em` either run outside the TX or fail to flush deterministically. The fix passes the inner `txEm` as the third arg.
