<objective>
Persist the Phase 3 domain model. Define MikroORM EntitySchema for Wallet and Transaction (POJO row classes, no decorators), write two MikroORM migrations creating the `wallets` and `transactions` tables with their constraints (CHECK on balance, UNIQUE on player_id and message_id, FK from transactions to wallets), and register the new schemas in `mikro-orm.config.ts` so the migrate container picks them up.

Purpose: REQ-DOM-03 needs a DB-level fail-closed safety net (the CHECK constraint) alongside the domain invariant; REQ-WALL-07 needs an immutable ledger with a UNIQUE(message_id) so the DB refuses duplicate ledger entries even if the application-layer inbox somehow missed a dedup. The Wallet aggregate (Plan 03-02) is the source of truth for fields; this plan only adds the storage shape.
Output: Two entities + two migrations + updated config. The next compose run's wallets-migrate step creates the tables.
</objective>

- Domain field is `Money` (Value Object); persistence stores `balance_cents BIGINT NOT NULL`.
- The EntitySchema does NOT auto-convert Money to bigint; the repository (Plan 03-06) handles the conversion via `Money.of(BigInt(row.balanceCents))` on read and `money.toCents()` on write.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Application repo → Postgres | Application sends parameterized SQL; never string concatenation |
| Domain invariant → DB constraint | Aggregate enforces balance >= 0 first; DB CHECK is fail-closed backstop |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-03-07 | Tampering | Wallet balance bypass | mitigate | Postgres CHECK (balance_cents >= 0) rejects any write that would drive balance negative; this is the documented backstop for the atomic UPDATE in Plan 03-06 |
| T-03-08 | Repudiation | Mutated Transaction row | mitigate | TransactionEntitySchema has no onUpdate hooks; Plan 03-06 uses INSERT-only via repository.append; no UPDATE/DELETE handler exists |
| T-03-09 | Tampering | Double provisioning of a wallet | mitigate | UNIQUE constraint on wallets.player_id; second concurrent insert fails with unique_violation, caught by Plan 03-05's idempotent usecase |
| T-03-10 | Tampering | Duplicate Transaction insert | mitigate | UNIQUE constraint on transactions.message_id; defensive backstop alongside Phase 2 inbox dedup |
</threat_model>
