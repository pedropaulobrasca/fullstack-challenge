<objective>
Install the JWT validation surface for every wallets-service request: depend on `jose`, configure JWKS + iss + aud env vars (writing them to both `.env.example` files and `defaults.ts`), align Keycloak's `iss` claim by setting `KC_HOSTNAME=localhost` in docker-compose, decide on the audience strategy (add an audience mapper to the realm-export OR loosen `KEYCLOAK_AUDIENCE` to `account` — see Task 3 checkpoint), and ship `JwtGuard` with unit tests covering valid / invalid / expired / mismatched-iss / mismatched-aud cases.

Purpose: REQ-AUTH-04 says each service validates JWTs via cached JWKS. Kong is configured as a pure router (no JWT plugin) — see `docker/kong/kong.yml` — so the wallets service is the only line of defence. The `jose` library brings JWKS cache + cooldown built-in (no `jwks-rsa` + `passport-jwt` chain that fights Bun's SWC per PITFALLS M1). The `iss` alignment in docker-compose closes the cross-network mismatch described in 03-RESEARCH Pitfall 2.
Output: Working guard, decision on aud claim, env-var trio captured in three places (root + service .env.example + defaults.ts), and a unit-test suite covering five outcomes.
</objective>

  <name>Task 3: Decide audience strategy — realm mapper vs accept aud=account</name>
  <decision>How does the issued JWT carry an `aud` claim that the backend can validate?</decision>
  <context>The realm-export.json sets `publicClient: true` for `crash-game-client`. Keycloak does NOT add the client id to the `aud` claim of public-PKCE tokens by default; the token typically carries `aud: "account"` (the Keycloak management audience). The JwtGuard MUST validate `aud` (REQ-AUTH-04). Two options exist; pick one and document in ADR-012 (Plan 03-10).</context>
  <options>
    <option id="option-a">
      <name>Option A: Add an audience mapper to realm-export.json</name>
      <pros>Token explicitly carries `aud: "crash-game-client"` (or a dedicated resource audience like `crash-game-api`); semantically correct; matches OAuth2 best practice; future-proofs for a games-service guard reusing the same audience</pros>
      <cons>Requires editing the realm export to add a `protocolMappers` entry with `protocol-mapper-type: oidc-audience-mapper`; needs a stack restart to re-import; small risk of typos breaking the realm import</cons>
    </option>
    <option id="option-b">
      <name>Option B: Set KEYCLOAK_AUDIENCE=account in defaults.ts and .env.example</name>
      <pros>Zero realm changes; works immediately with current realm-export.json; less surface area for typos</pros>
      <cons>Backend trusts Keycloak's default management audience for game traffic — semantically misleading; another service (Phase 6 games-service) reusing this guard inherits the same misnamed audience</cons>
    </option>
  </options>
  <resume-signal>Type "option-a" or "option-b" and the human-confirmed final KEYCLOAK_AUDIENCE value.</resume-signal>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Internet → Kong → wallets-service | Bearer JWT must validate; no Kong JWT plugin so the service IS the gate |
| wallets-service → Keycloak (JWKS endpoint) | HTTP fetch in-network; trust based on TLS for prod (Phase 10), service name + healthcheck for dev |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-03-11 | Spoofing | Forged JWT | mitigate | jose.jwtVerify checks signature against JWKS, issuer claim against KEYCLOAK_ISSUER, audience claim against KEYCLOAK_AUDIENCE, and expiry — any failure throws 401 |
| T-03-12 | Spoofing | Cross-environment Keycloak instance issuing tokens | mitigate | Explicit KEYCLOAK_ISSUER pin; iss claim mismatch raises 401 |
| T-03-13 | Tampering | alg:none attack | mitigate | jose.jwtVerify rejects `alg:none` and any non-asymmetric algorithm by default (audited library behaviour) |
| T-03-14 | Information Disclosure | Token leaked to logs | mitigate | Guard never logs the raw token; only the error class is recorded |
| T-03-15 | Spoofing | Stale JWKS after key rotation | accept | jose respects Cache-Control with cacheMaxAge ceiling 10 min and 30s cooldown — bounded staleness window acceptable for play money |
| T-03-SC | Tampering | npm install of jose | mitigate | jose@6.2.3 verified in 03-RESEARCH §Package Legitimacy Audit (panva/jose, 30M+ weekly downloads, OIDC-certified author); audit recorded |
</threat_model>
