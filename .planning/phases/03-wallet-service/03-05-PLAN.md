<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| HTTP request → JwtGuard | Authorization header validated before any controller logic runs |
| Controller → UseCase | playerId is the only field passed from the request layer; no client-supplied wallet id, balance, or correlationId |
| UseCase → Repository | All writes go through `em.transactional`; provisioning resolves race via UNIQUE constraint + 23505 catch |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-03-16 | Spoofing | Player A provisioning wallet as Player B | mitigate | `req.user.playerId` from JWT sub claim is the ONLY identity used; no body/query parameter for playerId |
| T-03-17 | Tampering | Client posting a custom initial balance | mitigate | ProvisionWalletRequestDto schema is `z.object({}).strict()` — extra fields rejected by ZodValidationPipe |
| T-03-18 | DoS | Provisioning DoS via spam POST | mitigate | Idempotent contract — second+ calls are O(1) SELECTs; UNIQUE constraint blocks DB churn; rate limiting deferred to Phase 10 per ROADMAP |
| T-03-19 | Information Disclosure | Raw bigint on the wire | mitigate | WalletView.from uses serializeMoney; response DTO schema enforces moneySnapshotSchema (string amount, not bigint) |
| T-03-20 | Tampering | Two concurrent POST /wallets calls (browser two-tab) creating two wallets | mitigate | wallets.player_id UNIQUE + 23505 catch path; second call returns the existing wallet |
</threat_model>
