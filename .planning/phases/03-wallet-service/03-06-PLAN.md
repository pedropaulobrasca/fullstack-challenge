<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| AMQP broker → wallet consumer | Envelope must be parseEnvelope-validated AND payload zod-validated before any side-effect |
| Decorator TX → handler | All side-effects (atomic UPDATE, Transaction append, outbox row) must use txEm — the inbox dedup row already lives in this TX |
| Domain invariant → DB CHECK | Conditional UPDATE WHERE clause is primary defence; Postgres CHECK is fail-closed backstop if balance ever went negative through another path |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-03-21 | Tampering | Balance race (two concurrent debits) | mitigate | Atomic conditional UPDATE: WHERE balance_cents >= amount; rowcount 0 unambiguously means INSUFFICIENT_FUNDS; no read-then-write window |
| T-03-22 | Tampering | Replay attack (same messageId twice) | mitigate | @IdempotentSubscribe inbox dedup via UNIQUE (consumer_name, message_id) — second invocation never runs the handler body |
| T-03-23 | Tampering | Outbox write outside the side-effect TX | mitigate | OutboxRepository.add called with txEm (or via RequestContext) so the row commits with the wallets row in a single Postgres TX |
| T-03-24 | Tampering | Forged envelope payload | mitigate | walletDebitPayloadSchema.parse runs at handler entry; malformed payloads throw and are routed to DLX by the decorator's error path |
| T-03-25 | Information Disclosure | BigInt JSON serialization throw | mitigate | All Money on the outbox payload uses Money.toSnapshot — string amounts only |
| T-03-26 | Repudiation | Lost Transaction row | mitigate | Transaction.append uses txEm; the row commits with the wallet UPDATE and the outbox row in one TX; UNIQUE(message_id) on transactions blocks duplicate append |
</threat_model>
