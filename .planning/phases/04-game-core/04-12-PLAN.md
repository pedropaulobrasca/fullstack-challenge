    - ADR-015 (Crash-point formula + client seed derivation): Context — Bustabit's canonical Rust impl keys HMAC by chain-iteration hash and uses a fixed-public-salt as the HMAC message (Bitcoin block hash). Our challenge has no external entropy source. Considered: (A) Exact Bustabit canon with a globally-fixed public salt env-loaded; (B) HMAC(serverSeed, `${clientSeed}:${nonce}`) with per-round derivable clientSeed; (C) Future Bitcoin block hash dependency (external entropy, infeasible for the challenge). Decision: (B). The clientSeed for round N derives via `SHA256(prevRound.id + ":" + prevRound.crashedAt.toISOString())` — public, deterministic, derivable from the previous round's CRASHED-time data which is observable before round N's BETTING window opens. Round 1 (genesis) uses `SHA256("genesis")`. Consequences: anti-operator-collusion property preserved (operator cannot pick the next seed; chain commitment was published at bootstrap); the verifier (`/verify` endpoint + packages/contracts/bin/verify-crash.ts) can re-derive client seed deterministically; documented as a deliberate variant from Bustabit-canon
    - ADR-016 (Hash chain pre-generation depth = 1M): Context — Provably-fair commitment story requires the operator cannot pick a seed after seeing bets. Lazy generation exposes the "current head pointer" attack. Considered: (A) Lazy generation (refill at threshold) — fast bootstrap, attackable; (B) Pre-generated 1M chain at first boot — ~2s gen, ~80MB heap during bootstrap, ~80MB DB storage, immutable commitment; (C) On-demand single-seed generation per round — operator-pickable. Decision: (B). HASH_CHAIN_LENGTH=1000000 env-overridable for non-prod; idempotent bootstrap via `countEntries() > 0n` check; chain[N-1] is the terminal random seed via `randomBytes(32)`; chain[i] = sha256(chain[i+1]) walked in reverse. Consequences: immutable commitment story; ~80MB resident heap during the bootstrap function's lifetime (acceptable per research Risk R3); SeedChainBootstrap implements OnApplicationBootstrap not OnModuleInit (cross-ref ADR-017)
    - ADR-017 (Round loop: recursive setTimeout + OnApplicationBootstrap): Context — The round loop must drive autonomous transitions without external triggers, survive restart, and not exhibit drift. Considered: (A) setInterval — queues up missed ticks under load, drift-prone; (B) Recursive setTimeout — drift-resilient, each iteration schedules its own next fire, clean shutdown via clearTimeout; (C) Worker thread — IPC complexity, transaction-context-sharing break, infeasible for the challenge timeline. Decision: (B) PLUS the lifecycle hook `OnApplicationBootstrap` (NOT `OnModuleInit`) because the loop needs MikroORM to be fully connected before its first DB read; per NestJS docs OnApplicationBootstrap fires after every module's OnModuleInit, while OnModuleInit fires per-module and may race with the MikroORM forRoot module's init under Bun's faster module resolution (research Pitfall 1). Consequences: single-process round loop; scale-out path via `pg_try_advisory_lock('round-loop')` leader election documented but UNIMPLEMENTED in v1 (research Risk R1); kill-9 recovery is the five-branch recoverInFlightRound (Plan 04-06); clean shutdown via OnApplicationShutdown + clearTimeout
