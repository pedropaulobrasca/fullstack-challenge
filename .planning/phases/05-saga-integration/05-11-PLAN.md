    1. Create `ADR-019-orchestration-over-choreography.md`:
       - Status: Accepted, Date: 2026-05-27, Phase: 5.
       - Context: Phase 5 introduces a cross-service flow (Game ↔ Wallet) with at least 3 distinct steps (place → debit → confirm or refund) + branching (insufficient funds, timeout, compensation). Choreography would scatter the FSM across both services; orchestration centralises it in Game via `bet_saga_state`.
       - Considered:
         a. Choreography (each service reacts to events; no central FSM). Pro: looser coupling. Con: timeout / compensation logic distributed → hard to reason about; impossible to express "if Wallet didn't reply in 5s, refund" without polling state from both sides.
         b. Orchestration in Game service (`bet_saga_state` row carries status; Game emits commands and consumes Wallet events; Wallet is a passive participant). Pro: single source of truth for saga progress; timeout/compensation are local; aggregate-FSM discipline carries through. Con: Game owns the cross-service workflow — defensible because the bet IS a Game-domain concept; Wallet's only role is bookkeeping.
         c. Separate orchestrator service (a third service whose only job is to drive sagas). Pro: clean separation. Con: scope inflation; another deployable; another DB; not justified at challenge scale.
       - Decision: Option (b). Game owns saga state and command emission; Wallet stays passive. Justified by microservices.io guidance for ≥3-step + branching flows + the bet being conceptually Game-domain (Wallet is downstream bookkeeping). Phase 10 documents the alternative (separate orchestrator) as a scale-out path.
       - Consequences: Forecloses choreography for bet placement; doesn't preclude Phase 9 leaderboard which IS choreography (projector consuming game.events). Locks the `bet_saga_state` table as the saga's source of truth; restart recovery + timeout sweep + compensation all live in games-service.
    2. Create `ADR-020-bet-202-cashout-200-asymmetry.md`:
       - Status: Accepted, Date: 2026-05-27, Phase: 5.
       - Context: Bet placement requires a cross-service round trip (Game → Wallet → Game) which cannot complete synchronously without holding the HTTP request open across two AMQP hops + two TX commits. Cashout is 1-step in Game (atomic Bet transition + outbox row); Wallet credit is downstream bookkeeping.
       - Considered:
         a. Both endpoints synchronous (200). Bet would block until wallet.debited or rejection arrives. Pro: simpler client semantics. Con: blocks the request thread across AMQP + retries; SAGA_TIMEOUT_MS would manifest as HTTP 504; would have to long-poll or use a request-scoped event listener — ergonomic nightmare and breaks the at-least-once delivery contract (the request might time out while the saga is mid-flight and the bet is committed). Real-time UX would still need WS for "your bet is now ACTIVE" anyway.
         b. Both endpoints async (202 + WS). Cashout returns 202 and the multiplier/payout comes via WS. Pro: symmetric. Con: cashout is the most latency-sensitive operation (player wants the payout number on screen immediately); cashout has no branching that demands a saga (single atomic transition in Game); deferring to WS just adds round-trip latency.
         c. Asymmetric: 202 for bet (PENDING confirmed via WS bet:active), 200 for cashout (synchronous payout). Pro: bet semantics match the actual cross-service workflow; cashout semantics match its locality (one-TX inside Game). Aligned with how Bustabit-style products behave.
       - Decision: Option (c). 202 for `POST /games/bet`; 200 for `POST /games/bet/cashout`. The `bet.active` outbox event (emitted by `WalletDebitedHandler` in plan 05-05) is the WS push that Phase 6 will surface. Cashout response carries `{ multiplier, payoutCents }` synchronously.
       - Consequences: Locks the public REST contract; Phase 6 WS gateway must consume `bet.active` / `bet.refunded` from `game.events` to push to the client. Forecloses a "bet is synchronous" UX — Phase 7 frontend bet panel will show "Pending..." between 202 and the WS push (typically &lt;100ms via OutboxPublisher's LISTEN/NOTIFY trigger from ADR-010).
    3. Both ADRs use the exact heading levels of ADR-018. Cross-link in the Consequences section to ADR-013 (txEm propagation) and ADR-017 (recursive setTimeout — reused by SagaTimeoutSweeper).
