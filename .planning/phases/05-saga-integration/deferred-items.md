Items intentionally postponed to later phases or phase verification. Logged here so they are not lost.

- [ ] Smoke probes 34-37 (`scripts/smoke-health.sh`) timing-sensitive assertions — round duration ~7s is tight for sequential `bet → ACTIVE` observation against the live stack. Probes 34 (POST /games/bet during BETTING returns 202 PENDING + bet settles to ACTIVE), 35 (wallet balance decreases by bet amount after settlement), 36 (POST /games/bet/cashout during RUNNING returns 200 + multiplier > 1), 37 (wallet balance credited by payoutCents after cashout) currently pass the saga end-to-end (verified via DB inspection at P5.10 — `bet_saga_state.status=CONFIRMED` + outbox `bet.active` published) but the smoke script's assertion shape needs to be tolerant of round-timing race. Fix candidates: (a) accept LOST as a valid post-saga terminal state (the saga confirmed but the round terminated before cashout window — proves saga, not cashout), (b) observe `bet_saga_state.status='CONFIRMED'` in DB instead of `bets.status='ACTIVE'` to decouple from round transitions, (c) extend round duration via env override `BETTING_WINDOW_MS=10000` during smoke. Flagged for `/gsd:verify-phase 5` verifier — saga functionality is proven end-to-end, only the smoke assertion shape is brittle.

- [ ] Phase 5 integration test suite (`services/games/tests/integration/`) — 14/15 fail with broker connection refused at the in-process app boot. Root cause: `Test.createTestingModule({imports:[AppModule]}).compile()` triggers `MessagingSpineModule.forRootAsync` to connect to RabbitMQ before the testcontainers broker tunnel is ready. Fix candidates: (a) add a `waitForBrokerReady` helper that polls `amqplib.connect` until success before the AppModule boot, (b) inject a fake `@golevelup/nestjs-rabbitmq` transport in test mode, (c) move broker URL resolution into a NestJS Provider with `useFactory` to defer connection until first publish. Production saga path is verified end-to-end at P5.10 against the live docker stack (`bet_saga_state` row CONFIRMED on round dd098fbe); the integration suite is a robustness investment, not a functional gap. Flagged for a follow-up Phase 5 hardening or Phase 10 entry.

- [ ] Phase 5 deferred from P4: integration test isolation due to frozen env at module-load time + RNG-dependent crashTime — inherited from `.planning/phases/04-game-core/deferred-items.md` line 7. `src/config/defaults.ts` parses `process.env` at first import and `Object.freeze()`s the result; subsequent test files that call `setupIntegrationEnv` overrides (e.g. `BETTING_WINDOW_MS`, `GROWTH_RATE`) do not take effect because the AppModule reads from the cached frozen env. Each file passes in isolation (`bun test path/to/file.ts`) but the suite as a whole races. Fix candidates: (a) make env reloadable for tests via a `setEnvForTests()` helper, (b) move env parsing into Nest `ConfigModule` with dynamic provider so each AppModule boot picks up current `process.env`, (c) use `AUTO_CASHOUT_MAX_X=2` in tests to bound crashTime regardless of GROWTH_RATE. Flagged for a Phase 5 / Phase 10 hardening plan.
