<objective>
Extract a `JwtVerifierService` from the existing `JwtGuard` so the same `jose.createRemoteJWKSet`-backed token verifier can be reused by the WebSocket `io.use()` handshake middleware in Plan 06-03.

Purpose: Plans 06-03 (`JwtIoAdapter`) consume an injectable verifier without duplicating the JWKS cache or audience/issuer wiring. Sharing the verifier preserves REQ-AUTH-04 invariants (cached JWKS, identical `issuer + audience` validation) across HTTP and WS surfaces.

Output: `JwtVerifierService` provider; `JwtGuard` rewritten to delegate; AppModule registers the new provider; unit tests cover verifier success + failure paths and confirm `JwtGuard` still attaches `req.user`.
</objective>

Existing `JwtGuard` shape:
- constructor reads `env.KEYCLOAK_JWKS_URI`, `env.KEYCLOAK_ISSUER`, `env.KEYCLOAK_AUDIENCE` via `loadEnvOptions()` fallback when `@Optional() options?: JwtGuardOptions` is absent
- builds `this.jwks = createRemoteJWKSet(new URL(jwksUri), { cacheMaxAge: 600_000, cooldownDuration: 30_000 })`
- `canActivate(ctx)` reads `Authorization` header, strips `Bearer `, calls `jwtVerify(token, this.jwks, { issuer, audience })`, sets `req.user = { playerId, tokenExp }`
- `AuthenticatedRequest` interface exported from same file: `{ headers, user?: { playerId, tokenExp } }`

Target `JwtVerifierService` shape (new file):
- `verify(token: string): Promise<{ playerId: string; tokenExp: number }>`
- throws `UnauthorizedException("INVALID_TOKEN")` on `jwtVerify` rejection OR when `payload.sub`/`payload.exp` are missing/typed wrong
- builds JWKS once in constructor with the same `cacheMaxAge` + `cooldownDuration` constants from the existing guard

Rewritten `JwtGuard`:
- constructor injects `JwtVerifierService` (no `@Optional()` anymore — the verifier is a required Nest provider)
- still extracts bearer header (preserve `MISSING_BEARER_TOKEN` error code on missing header)
- delegates token verification to `verifier.verify(token)`
- preserves the `AuthenticatedRequest` export

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Keycloak → games-service | Untrusted JWT crosses here; verified via cached JWKS before request reaches any business handler |
| services/games internal | JwtVerifierService is the only path to mint a verified `playerId`; both HTTP `JwtGuard` and (future) `JwtIoAdapter` MUST go through it |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-06-01 | Spoofing | JwtVerifierService | mitigate | `jwtVerify` with `issuer` + `audience` claims pinned to env-loaded Keycloak realm; missing/typed-wrong `sub` or `exp` rejected at `verify()` boundary |
| T-06-02 | Information Disclosure | JwtVerifierService error path | mitigate | All verification failures throw uniform `UnauthorizedException("INVALID_TOKEN")` — no jose stack trace leaked to caller |
| T-06-03 | Denial of Service | JWKS endpoint hammering | mitigate | `createRemoteJWKSet` cache (`cacheMaxAge: 600_000ms`, `cooldownDuration: 30_000ms`) preserved verbatim from existing guard |
</threat_model>
