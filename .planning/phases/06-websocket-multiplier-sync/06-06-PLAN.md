<objective>
Bridge the outbox to the WebSocket layer: a `WsBridgeConsumer` subscribed to `game.events` (the exchange the outbox already publishes `bet.active`, `bet.refunded`, `bet.cashed_out`, `bet.placed` to) translates each AMQP envelope into one or two Socket.IO emits — public masked variant on `lobby` plus private un-masked variant on `user:{playerId}`.

Purpose: REQ-WS-03 enumerates `bet:placed`, `bet:cashed_out` (lobby) and `bet:my_active`, `bet:my_cashed_out`, `bet:my_refunded` (user). Per RESEARCH §Pattern + RESEARCH Anti-Pattern "Emitting bet events from WalletDebitedHandler directly to the gateway", the outbox must remain the single source of truth (Phase 2 ADR-007). Consuming `game.events` from a presentation-adjacent consumer preserves that invariant.

Output: `WsBridgeConsumer` provider in `AppModule`; routing-key-discriminated handler that emits both lobby (masked) and user-private events for each bet lifecycle transition; unit tests verify routing per event type, payload shape, and masking determinism.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| RabbitMQ game.events → WsBridgeConsumer | Inbound AMQP payload is trusted (same trust zone as the publisher — both inside games-service), but parsed against zod schemas defensively |
| WsBridgeConsumer → Socket.IO emit | Lobby vs. user-room separation enforces per-player privacy |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-06-15 | Information Disclosure | playerId leaked to lobby | mitigate | Lobby events always emit `playerIdMasked = sha256(playerId).slice(0, 8)`; the raw playerId never reaches the lobby room |
| T-06-16 | Information Disclosure | Bet payout amount leaked to lobby | mitigate | `bet:cashed_out` lobby payload contains multiplier only; absolute payout amount stays on the private `bet:my_cashed_out` user-room emit |
| T-06-17 | Tampering | Malformed inbound envelope | mitigate | Each routing case parses payload via zod before emit; parse failures throw and the envelope is NACK'd back to RabbitMQ (golevelup default) so the DLQ + delivery-limit policy applies — never silently emit malformed data to clients |
| T-06-18 | Repudiation | Replay of cashout event | accept | At-least-once delivery means the same `bet:my_cashed_out` may reach a client twice; FE deduplicates by `betId` (documented in REQ-WS-03 consumer contract for Phase 7) — replay carries no harm because the emit is idempotent at the rendering layer |
</threat_model>
